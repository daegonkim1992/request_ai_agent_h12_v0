# 정의서 해석 기록

구현하면서 업무정의서가 정하지 않았거나 모호해서 해석한 곳이다. 새 항목은 **확인 필요**로 올리고, 결정되면 정의서에 반영한 뒤 **반영** 버전을 적는다.

| ID | 정의서 | 질문 | 결정 | 상태 |
|---|---|---|---|---|
| G-1 | 3.2, 3.4-4 | 취소 요청이 대기 중일 때 다른 기능을 할 수 있는가 | 취소 대기로 올라간다. 관리자가 승인·거절하기 전에는 다른 모든 기능과 의뢰서 수정을 막고, 관리자 할 일에만 넣는다 | 반영 v1.1 |
| G-2 | 3.2, 3.4-4 | 진행 중 변경 요청이 대기 중일 때 보완 요청·보류를 할 수 있는가 | 해석 단계 보완 요청은 막는다(먼저 수락·거절). 보류는 허용하고 변경 요청은 대기한 채로 남는다 | 반영 v1.1 |
| G-3 | 3.4-12 | 담당자가 보류한 뒤 재배정되면 누가 재개하는가 | 보류 책임이 새 담당자에게 넘어간다. 관리자 보류는 유지한다 | 반영 v1.1 |
| G-4 | 3.2 재제출 | 재제출에 실제 내용 변경이 필요한가 | 필요 없다. 바뀌지 않아도 재제출할 수 있다 | 반영 v1.1 |
| G-5 | 3.2, 8장 | 진행 중 변경 요청의 의뢰서에도 제출 조건을 적용하는가 | 적용한다. 요청 시점에 제안된 의뢰서를 검사한다 | 반영 v1.1 |
| G-6 | 3.2 재배정 | 현재 담당자와 같은 사람으로 재배정할 수 있는가 | 막는다 | 반영 v1.1 |
| G-7 | C.8 | 접수와 배정을 사건 하나로 남기는가 | `ACCEPTED` 하나로 남기고 담당자는 사건 데이터에 둔다 | 반영 v1.1 |
| G-8 | 3.2 | 사유·설명 텍스트에 길이 제한이 있는가 | 두지 않는다 | 반영 v1.1 |
| G-9 | 2장 | 작성 중 의뢰를 누가 보는가 | 한 번도 제출하지 않은 의뢰(제출 전 취소 포함)는 작성자만 본다. 관리자도 보지 않는다 | 반영 v1.1 |
| G-10 | 9장 | 원본 `총조립도 분류체계.xlsx`는 368행(사업부 SAC, RAC, Air Care, ESS, Chiller)인데 정의서는 252행, 사업부 5개(AIDC 포함)다. 어떤 분류를 쓰는가 | h10_v0이 정리한 방식을 따른다. ESS(8행), SAC의 패널·기타·부속·시험 분류(36행), 같은 Platform에 다른 Chassis가 있는 "NA" 행(3행)을 빼고, 중복을 합치고, 오타(`Siganture`)와 앞뒤 공백을 고친다. 결과는 h10의 252개와 같다. 규칙은 `refdata/sources/taxonomy.yaml`에 사유와 함께 둔다 | 반영 v1.2 |
| G-11 | 4.2 | RAC·Air Care 원본의 LEVEL3(LG, Friedrich, Artcool 등)을 어떻게 다루는가 | 정의서 분류는 Chassis까지라 버린다. RAC·Air Care는 LEVEL1 = Product Line-up = Platform, LEVEL2 = Chassis로 읽는다. SAC·Chiller는 LEVEL1·2·3 = Line-up·Platform·Chassis다 | 반영 v1.2 |
| G-12 | 9장, 4.4 | AIDC는 원본에 없고 PMS 프로젝트 파일도 없다 | `AIDC > CDU`(Platform 해당 없음, Chassis 없음)를 직접 추가한다. AIDC는 PMS 프로젝트가 없으므로 "개발 프로젝트" 유형으로 제출할 수 없다(4.4 그대로) | 반영 v1.2 |
| G-13 | 5.3.4, 9장 | Catalog의 비표준(X) 사양은 고를 수 있는가. Micro-Channel의 Fin type은 Catalog에 `Flat(MCE)`, `Flat(MCC)`로 있다. `5+7`, `1+2`, `20+22`처럼 합친 값이 있다 | 비표준 사양도 등록된 실제 조합이고 표준 여부는 표시만 한다. "Flat으로 고정"은 Flat 계열을 뜻하며, 관 직경에 따라 하나로 정해진다. 사양 값은 원본 표기 그대로 문자열로 둔다(`9.52`, `5+7`). 압력손실 측정값은 가져오지 않는다 | 반영 v1.2 |
| G-14 | 4.4, 9장 | PMS 파일의 사업부 이름(CAC)이 제품 분류(SAC)와 다르다. 담당자·작성자 이름 등 개인정보가 들어 있다 | PMS의 CAC는 제품 분류의 SAC다. PMS Project Code, Project, Rep Model, Region, Product Group만 가져온다 | 반영 v1.2 |
| G-15 | 3.4-10 | 기준 데이터 버전을 어떤 단위로 의뢰에 고정하는가. PMS도 고정하는가 | 데이터셋마다 버전 파일을 두고 한번 만들면 고치지 않는다. 릴리스(`refdata/manifest.yaml`)가 데이터셋 버전의 묶음을 가리키고, 의뢰는 확정 시점의 릴리스 ID를 남긴다. PMS는 3.4-10 목록에 없어 고정하지 않으며, 고른 프로젝트 정보를 의뢰에 복사한다 | 반영 v1.2 |
| G-16 | 4.3 | 개발 등급 선택지가 "A, B, Ca, Cb, D, JDM, ODM 계열 등"으로 열려 있다 | 정의서에 적힌 7개와 PMS 원본(2026-09-15)의 Grade 값 전체(29개)에 직접 입력을 더한다. `rules/options.yaml`에 있고, PMS 원본에 새 Grade가 생기면 `tests/reference/test_9_build.py`가 알려 준다 | 반영 v1.2 |
| G-17 | 부록 A, 4.3 | 해석유형과 선택지의 저장 코드가 정의서에 없다 | 해석유형은 영문 코드(`AIRFLOW_RATE` 등, `rules/analysis_types.yaml`), 의뢰 유형도 영문 코드(`DEVELOPMENT_PROJECT` 등)로 정했다. 부록 C에 코드가 있는 해석 범위·결과 활용 목적은 그대로 쓰고, 나머지 선택지는 값이 곧 코드다 | 구현 결정 |

구현하면서 찾아 고친 것: 거절된 변경안이 이력에서 사라지던 문제(3.4-7), 보류 중 취소가 승인될 때 보류 정보가 남던 문제(3.4-12). 둘 다 v1.1에 반영했다.
