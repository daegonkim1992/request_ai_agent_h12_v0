# 해석의뢰 앱 세션 운영 규칙

## 1. 목적

작업을 여러 세션으로 나누더라도 업무 기준, 작업 순서, 결정 이력을 잃지 않도록 한다. 이 문서는 모든 새 세션의 시작·진행·종료 절차다.

## 2. 새 세션 시작 절차

1. `README.md`를 읽어 현재 기준선과 문서 위치를 확인한다.
2. `docs/해석의뢰_업무정의.md`를 읽는다. 현재 작업과 관련된 장은 반드시 원문으로 확인한다.
3. `docs/spec-gaps.md`를 읽어 관련 보류·해석·결정 상태를 확인한다.
4. `docs/ux-작업-로드맵.md`에서 가장 앞선 `대기` 작업 또는 명시적으로 지정된 작업 하나를 선택한다.
5. 선택한 작업을 `진행 중`으로 바꾸고, 해당 작업의 범위·선행 조건·완료 조건을 다시 확인한다.

## 3. 세션 범위 규칙

- 한 세션에는 로드맵의 작업 ID 하나만 처리한다.
- 상위 업무 규칙의 의미를 바꾸는 결정은 임의로 내리지 않는다.
- 범위 밖 문제는 수정하지 않는다. `spec-gaps.md`에 `결정 필요` 또는 `보류`로 남긴다.
- 업무정의서와 UX 문서가 충돌하면 UX 문서를 고치며, 업무정의서의 의미가 모호하면 결정을 요청한다.
- UI·기술 문서가 아직 없는 상태에서 구현 코드나 테스트를 만들지 않는다.

## 4. 보류 항목 처리

| 상황 | 처리 |
|---|---|
| UX 흐름을 결정할 수 없을 정도로 업무 의미가 부족함 | `spec-gaps.md`에 근거·선택지·UX 영향을 기록하고 결정 요청 |
| 상세 값·연동 방식만 미정이며 UX 구조에는 영향이 없음 | 보류 상태와 안내 문구만 표현하고, 값을 가정하지 않음 |
| 문서의 용어·교차 참조·동일 규칙 표현만 불일치 | 근거를 확인한 뒤 편집 수준으로 정리하고 세션 기록에 남김 |

## 5. 세션 종료 절차

1. 선택한 작업의 완료 조건을 모두 확인한다.
2. 산출물의 업무정의서 근거와 보류 항목을 다시 대조한다.
3. 문서 링크·표·목록의 형식 오류를 확인한다.
4. 로드맵의 작업 상태를 `완료`, `검토 대기`, `결정 필요`, 또는 `보류`로 갱신한다.
5. 로드맵의 `세션별 기록` 표에 실제 변경·검토 결과·다음 작업을 남긴다.
6. 다음 세션에 필요한 정보만 짧게 남기고, 다음 작업을 시작하지 않는다.

## 6. 새 세션 요청문 예시

```text
해석의뢰 앱 작업을 이어간다.

먼저 README.md, docs/해석의뢰_업무정의.md,
docs/spec-gaps.md, docs/ux-작업-로드맵.md,
docs/세션-운영-규칙.md를 읽는다.

로드맵 작업 ID [예: 1.2]만 수행한다. 업무정의서가 정한
의미를 바꾸지 말고, 범위 밖 문제는 spec-gaps.md에 기록한다.
완료 시 로드맵의 상태와 세션 기록을 갱신하고, 다음 작업은 시작하지 않는다.
```
