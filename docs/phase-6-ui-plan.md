# 6단계 UI 작업 기록

6단계는 화면을 한 번에 만들지 않는다. 이 문서의 한 단계만 작업하고, 해당 단계의 완료 조건을 만족한 뒤 다음 단계로 간다.

## 새 세션 작업 규칙

새 세션은 작업 전에 `CLAUDE.md`, `docs/spec-gaps.md`, 이 문서를 차례로 읽는다.

1. 시작할 단계의 상태를 `진행 중`으로 바꾸고, 이번 세션에서 다룰 범위를 기록한다.
2. 이전 단계 밖의 결함을 발견하면, 먼저 재현 테스트를 추가하고 원인을 기록한다. 범위가 큰 변경은 현재 단계를 끝낸 뒤 별도 단계 또는 결함 수정 기록으로 분리한다.
3. 완료할 때 바뀐 기능, 실행한 검증 명령과 결과, 남은 제약, 바로 다음 단계를 기록한다.
4. 모든 단계에서 백엔드 전체 테스트, 프런트엔드 build·lint를 실행한다. 화면을 추가·변경한 단계는 해당 UI 테스트와 역할별 수동 확인 또는 E2E도 실행한다.
5. 사용자에게 보이는 입력은 JSON 직접 편집이 아니라 업무용 컨트롤로 만든다. JSON 편집기는 API 점검용 임시 골격이며 최종 UI가 아니다.

## 공통 안전 경계

- 상태 전이, 권한, 제출 가능 여부, Case 재확인 여부는 프런트엔드가 판단하지 않는다. API의 `available_actions`, `can_edit_form`, 검증 오류, `case_confirmation`을 따른다.
- YAML 규칙(선택지, 사유 코드, 조건 매핑)을 프런트엔드에 중복하지 않는다. 화면이 필요한 표시 메타데이터는 서버가 제공하는 읽기 전용 UI 계약으로 받는다.
- 의뢰서 저장은 현재 form 스냅샷을 기반으로 한다. 시스템이 보존해야 하는 의뢰번호, 기준 릴리스, PMS, PCB 이미지 값을 프런트엔드가 삭제하거나 만들어 내지 않는다.
- API 오류의 `fields`, `issues`, 대상 재확정의 `impact`(409)를 공통 오류 처리로 정규화하고, 오류 위치와 메시지를 해당 화면에 표시한다.
- G-22의 측정·판정 기준은 현재 선택 사항이다. 표준값을 임의로 채우지 않는다. G-28의 Case 해시는 서버만 계산한다. G-29에 따라 브라우저에 HMAC 비밀값을 두지 않는다.
