# 해석의뢰 앱 UX 설계 기준서

## 1. 사용자

이 문서는 업무정의서의 역할과 상태를 UX로 해석하는 기준이다. 사용자는 하나의 역할과 하나의 소속 부서를 가지며, 역할과 소속 부서는 세션에서 제공된다는 업무 전제를 사용한다. 실제 로그인, 로그아웃, 계정 관리, 세션 만료와 사용자·권한 운영은 아직 확정되지 않았으므로 업무 UX 범위에 포함하지 않는다.

| 사용자 | 업무상 위치 | 업무 UX에서 다루는 대상 |
|---|---|---|
| 의뢰자 | 해석이 필요한 문제를 의뢰하고 결과를 확인하는 기구설계 엔지니어 | 본인이 만든 의뢰와, 조회만 가능한 같은 소속 부서의 다른 의뢰자가 만든 의뢰 |
| 해석관리자 | 의뢰를 검토해 접수하고 해석담당자를 배정하는 사람 | 한 번 이상 제출된 전체 의뢰 |
| 해석담당자 | 배정된 의뢰의 해석을 수행하고 결과를 회신하는 사람 | 본인에게 배정된 의뢰 |

한 번도 제출하지 않은 의뢰(작성 중 및 제출 전에 취소한 의뢰)는 작성자만 볼 수 있다. 같은 부서 의뢰자는 다른 사람이 만든 의뢰를 조회만 할 수 있고, 업무 행위를 할 수 없다. 종료 상태(완료, 반려, 취소)는 모든 역할에서 조회만 한다.

## 2. 역할·권한·책임

| 역할 | 책임 | 할 수 있는 업무 행위 | 조회 범위 |
|---|---|---|---|
| 의뢰자 | 착수 가능한 의뢰서를 작성하고 결과를 확인한다 | 의뢰 작성·제출, 보완 후 재제출, 진행 중 변경 요청, 취소·취소 요청, 결과 재작업 요청, 결과 확인 | 자기 의뢰, 같은 소속 부서에서 만든 의뢰(조회만) |
| 해석관리자 | 의뢰를 검토해 접수하고 담당자를 배정한다 | 검토·해석 단계 보완 요청, 반려, 접수·배정, 재배정, 보류·재개, 취소 요청 승인·거절 | 전체 의뢰. 단, 한 번도 제출하지 않은 의뢰는 제외 |
| 해석담당자 | 해석을 수행하고 결과를 회신한다 | 해석 단계 보완 요청, 보류·재개, 진행 중 변경 수락·거절, 결과 등록 | 배정받은 의뢰 |

- 새 의뢰는 의뢰자만 만들 수 있다.
- 각 업무 행위는 업무정의서 3.2의 수행 가능 상태에서만 가능하다. 취소 요청이 대기 중이면 관리자의 취소 요청 승인·거절만 가능하다.
- 담당자와 관리자는 의뢰서 내용을 직접 고치지 않는다. 의뢰서 수정은 의뢰자가 가능한 상태에서 수행한다.

## 3. 역할별 사용자 여정

이 절은 역할별 목표, 업무를 시작하는 현재 처리 대상, 성공 기준과 역할별 여정을 정의한다. 현재 처리 대상은 역할이 다음 처리를 책임지거나 작업을 재개해야 하는 할 일이며, 조회 범위나 업무 행위 권한과는 구분한다. 화면·정보 구조는 후속 작업에서 다룬다.

| 역할 | 목표 | 업무 시작점: 현재 처리 대상 | 성공 기준 |
|---|---|---|---|
| 의뢰자 | 해석 목적, 대상 제품, 해석 조건을 빠짐없이 전달하여 해석담당자가 별도 재문의 없이 착수 여부를 판단할 수 있게 하고, 회신된 결과를 확인한다. | 작성 중인 의뢰를 이어 작성하거나, 보완 필요·해석 중 보완 필요 의뢰에 응답하거나, 결과 확인 필요 의뢰의 결과를 판단한다. | 제출할 때는 제출 조건을 충족한 의뢰서를 검토 대상으로 넘긴다. 보완·변경·취소·재작업처럼 본인에게 필요한 후속 행위는 해당 상태에서 요청 또는 재제출한다. 업무의 최종 성공은 결과를 확인하여 의뢰가 완료 상태가 되는 것이다. |
| 해석관리자 | 제출된 의뢰를 검토하여 접수 가능 여부를 판단하고, 접수한 의뢰에 담당자를 배정하며, 관리자의 처리가 필요한 취소 요청·해석 단계 확인·보류를 처리한다. | 검토 중, 취소 요청 대기, 해석 진행 중(관리자 확인 대기), 관리자가 보류한 의뢰를 처리한다. | 검토 중 의뢰마다 보완 요청, 반려, 또는 담당자를 지정한 접수·배정 중 하나로 검토 처리가 끝난다. 취소 요청 대기는 승인 또는 거절로 처리한다. 관리자 확인 대기는 해석 계속·담당자 배정 또는 재보완 요청으로 처리한다. |
| 해석담당자 | 배정된 의뢰의 해석을 수행하고 결과를 회신한다. | 본인에게 배정된 해석 진행 중 의뢰(관리자 확인 대기 제외), 진행 중 변경 수락 대기 의뢰, 본인이 보류한 의뢰를 처리한다. | 해석을 계속할 수 없으면 정의된 보완 요청 또는 보류로 처리하고, 진행 중 변경은 수락 또는 거절한다. 해석이 끝난 의뢰에는 결과 요약을 등록하여 의뢰자가 확인할 수 있는 결과 확인 필요 상태로 만든다. |

### 현재 처리 대상과 관리·조회 대상 적용 원칙

- 의뢰자의 현재 처리 대상은 작성 중, 보완 필요, 해석 중 보완 필요, 결과 확인 필요 의뢰다.
- 관리자의 현재 처리 대상은 검토 중, 취소 요청 대기, 해석 진행 중(관리자 확인 대기), 관리자가 보류한 의뢰다.
- 담당자의 현재 처리 대상은 본인에게 배정된 해석 진행 중 의뢰(관리자 확인 대기 제외), 진행 중 변경 수락 대기 의뢰, 본인이 보류한 의뢰다.
- 취소 요청 대기 의뢰는 관리자에게만 현재 처리 대상으로 들어간다. 그동안 의뢰자와 담당자는 업무 행위를 할 수 없다.
- 관리·조회 대상은 현재 처리 대상이 아니더라도 역할의 조회 범위 안에서 열람하거나, 업무정의서 3.2가 허용하는 상태에서 업무 행위를 할 수 있는 의뢰다. 이 대상은 할 일 목록에 자동으로 들어가지 않는다.

### 의뢰자 정상 여정 (1.2)

이 여정은 보완, 반려, 보류, 진행 중 변경, 취소, 결과 재작업이 없는 정상 경로만 다룬다. 의뢰자는 의뢰서 작성부터 결과 확인까지의 진행 상태를 조회할 수 있으며, 할 일에는 의뢰자가 다음 처리를 해야 하는 상태만 들어간다.

| 순서 | 의뢰자의 상태와 다음 행동 | 인계와 다음 상태 | 정상 경로의 완료 기준 |
|---|---|---|---|
| 1. 작성 시작·계속 | 의뢰자는 새 의뢰를 만들거나 `작성 중` 의뢰를 이어 작성한다. | `작성 중`은 의뢰자의 현재 처리 대상이다. 제출 전 의뢰는 작성자만 볼 수 있다. | 의뢰 대상을 확정할 준비가 된다. |
| 2. 의뢰 대상 확정 | 의뢰자는 제품 분류, 해석유형과 해당되는 해석 범위·냉각 방식을 확정한다. 해석 범위가 `실내·실외 모두`이면 해석 요청 방식과 상황 설명도 확정한다. | 의뢰 대상이 잠기고 의뢰번호가 발급되며, 해석유형에 맞는 조건 구성이 정해진다. 의뢰는 계속 `작성 중`이다. | 확정된 대상에 맞춰 의뢰서·조건·Case를 준비할 수 있다. |
| 3. 의뢰서·조건·Case 준비 | 의뢰자는 의뢰 내용, 해석 제품, 활성 조건을 준비하고 형상과 활성 조건 패키지를 Case로 구성한다. | `작성 중`에서 제출 조건을 충족할 때까지 의뢰자가 계속 처리한다. | 최소 1개 이상의 Case와 제출 조건을 충족한 의뢰서가 준비된다. |
| 4. 제출 | 의뢰자는 제출 조건을 충족한 의뢰서를 제출한다. | 상태가 `검토 중`으로 바뀌고, 관리자가 다음 처리자다. 의뢰자는 검토 결과를 기다리며 진행 상태를 조회한다. | 제출한 의뢰가 관리자 검토 대상으로 인계된다. |
| 5. 접수·배정 후 해석 진행 | 정상 경로에서는 관리자가 의뢰를 접수하고 담당자를 배정한다. 의뢰자는 `해석 진행 중` 의뢰의 진행 상태를 조회한다. | 상태가 `해석 진행 중`으로 바뀌고, 배정된 해석담당자가 다음 처리자다. | 배정된 담당자가 해석을 수행할 수 있다. |
| 6. 결과 수신 | 담당자가 결과 요약을 등록하면 의뢰자는 결과를 확인할 차례가 된다. | 상태가 `결과 확인 필요`로 바뀌며, 의뢰자의 현재 처리 대상이 된다. | 의뢰자가 결과 요약을 바탕으로 결과를 확인할 준비가 된다. |
| 7. 결과 확인 | 의뢰자는 등록된 현재 결과를 확인한다. | 의뢰자가 결과 확인을 하면 상태가 `완료`로 바뀌고, 이후에는 조회만 가능하다. | 의뢰가 완료 상태에 도달한다. |

정상 경로의 인계 순서는 `의뢰자(작성·제출) → 관리자(접수·배정) → 해석담당자(결과 등록) → 의뢰자(결과 확인)`이다. 각 인계 뒤에는 다음 처리자가 행동할 때까지 이전 처리자는 진행 상태를 조회한다. 보완·반려·보류·변경·취소·결과 재작업으로 갈라지는 경우는 1.3에서 정의한다.

### 의뢰자 예외 여정 (1.3)

예외 여정에서도 의뢰자는 의뢰서 내용을 직접 고칠 수 있는 상태에서만 고치고, `해석 진행 중`의 내용 변경은 진행 중 변경 요청으로만 한다. 보완 후 재제출은 내용이 바뀌지 않아도 할 수 있다. 제출, 재제출, 진행 중 변경 수락 때마다 의뢰서의 새 버전이 남는다. 아래의 `조회·대기`는 의뢰자의 현재 처리 대상이나 할 일이 아니며, 다음 처리자의 결정을 기다리며 상태와 이력을 열람하는 대상이라는 뜻이다.

#### 보완과 보류

| 시작 상황 | 의뢰자의 행동 | 인계와 다음 상태 | 의뢰자에게 남는 상태 |
|---|---|---|---|
| 관리자가 `검토 중`에 검토 단계 보완을 요청 | 상태가 `보완 필요`가 되면 의뢰자는 의뢰서를 고치거나 그대로 재제출한다. | 재제출하면 `검토 중`으로 돌아가며, 관리자가 다음 처리자다. | `보완 필요`는 의뢰자의 현재 처리 대상이다. 재제출 뒤에는 조회·대기한다. |
| 배정된 담당자가 `해석 진행 중`에 해석 단계 보완을 요청 | 상태가 `해석 중 보완 필요`가 되면(담당자 요청) 의뢰자는 의뢰서를 고치거나 그대로 재제출한다. | 재제출하면 `해석 진행 중`으로 돌아간다. 재배정이 없었다면 보완을 요청한 담당자가 해석을 이어서 수행한다. 재배정이 있었다면 재제출 뒤 처리자는 `G-31`이 확정될 때까지 정하지 않는다. | `해석 중 보완 필요`는 의뢰자의 현재 처리 대상이다. 재제출 뒤에는 담당자의 해석을 조회·대기한다. |
| 관리자가 `해석 진행 중`에 해석 단계 보완을 요청 | 상태가 `해석 중 보완 필요`가 되면(관리자 요청) 의뢰자는 의뢰서를 고치거나 그대로 재제출한다. | 재제출하면 `해석 진행 중(관리자 확인 대기)`가 되며, 관리자가 다음 처리자다. | 재제출 뒤에는 조회·대기한다. 관리자가 결정하기 전에는 의뢰자가 진행 중 변경이나 취소 요청을 할 수 없다. |
| 관리자가 확인 대기인 재제출을 확인 | 의뢰자는 추가 행동 없이 관리자의 결정을 조회·대기한다. | 관리자는 해석을 계속할 담당자를 배정해 일반 `해석 진행 중`으로 넘기거나, 재보완을 요청해 `해석 중 보완 필요`로 돌린다(관리자 요청). | 전자이면 새로 지정된 담당자가 다음 처리자이고, 후자이면 의뢰자가 다시 현재 처리자가 된다. 관리자가 배정하는 담당자는 기존 담당자와 같을 수 있다. |
| 배정 담당자 또는 관리자가 일정 등의 사유로 보류 | 의뢰자는 `보류` 의뢰를 조회·대기한다. 의뢰자는 재개, 의뢰서 수정, 진행 중 변경을 할 수 없다. 대기 중인 요청이 없을 때의 취소 요청만 예외로 할 수 있다. | 보류한 사람 또는 관리자가 재개하면 `해석 진행 중`이 되어 해석을 이어서 할 처리자에게 인계된다. | `보류`는 의뢰자의 현재 처리 대상이 아니다. 재개 전까지는 조회·대기 대상이다. |

검토 단계 보완은 관리자 검토로 돌아가고, 재배정이 없는 담당자 요청 해석 단계 보완은 담당자 해석으로 돌아간다. 반면 관리자 요청 해석 단계 보완은 반드시 관리자 확인 대기를 거친다. 정보 부족은 보류가 아니라 보완 요청으로 처리한다.

담당자가 보류한 의뢰는 관리자 재배정 뒤 새 담당자가 재개할 수 있으며, 이전 담당자는 더 이상 해당 의뢰를 보거나 재개할 수 없다. 관리자가 보류한 의뢰는 재배정해도 관리자의 보류로 남는다.

#### 진행 중 변경

| 시작 상황 | 의뢰자의 행동 | 인계와 다음 상태 | 의뢰자에게 남는 상태 |
|---|---|---|---|
| 대기 중인 요청이 없는 일반 `해석 진행 중` | 의뢰자는 제출 조건을 충족한 변경 의뢰서와 변경 사유로 진행 중 변경을 요청한다. | 상태는 `해석 진행 중`으로 유지되고 배정 담당자가 변경 수락·거절의 다음 처리자다. | 변경 요청이 대기하는 동안 의뢰자는 조회·대기한다. 취소 요청을 동시에 만들 수 없다. |
| 담당자가 변경을 수락 | 의뢰자는 결정 결과를 조회한다. | 변경 의뢰서가 새 버전으로 남고 `해석 진행 중`에서 담당자가 해석을 계속한다. | 의뢰자는 일반 진행 상태의 허용 범위에서만 후속 요청을 할 수 있다. |
| 담당자가 변경을 거절 | 의뢰자는 거절 사유와 원래 의뢰서를 조회한다. | 원래 의뢰서로 `해석 진행 중`이 계속되고 담당자가 해석을 이어서 수행한다. | 의뢰자는 일반 진행 상태의 허용 범위에서만 후속 요청을 할 수 있다. |

`해석 진행 중(관리자 확인 대기)`에서는 진행 중 변경 요청을 시작할 수 없다. 변경 요청이 대기 중인 동안에는 담당자가 먼저 수락·거절해야 하며, 그 전에는 해석 단계 보완 요청과 결과 등록도 진행되지 않는다.

변경 요청이 대기 중이어도 보류는 할 수 있다. 이 경우 변경 요청은 대기한 채로 남으며, 재개한 뒤 담당자가 수락하거나 거절한다.

진행 중 변경 요청이 대기한 상태에서 재배정되면 수락·거절 처리자는 `G-30`이 확정될 때까지 정하지 않는다.

#### 취소·반려와 결과 재작업

| 시작 상황 | 의뢰자의 행동 | 인계와 다음 상태 | 의뢰자에게 남는 상태 |
|---|---|---|---|
| `작성 중`, `검토 중`, `보완 필요` | 의뢰자는 직접 취소한다. | 상태가 `취소`로 바뀌며 종료한다. | 이후에는 조회만 한다. |
| 대기 중인 요청이 없는 일반 `해석 진행 중`, `해석 중 보완 필요`, `보류` | 의뢰자는 사유를 남겨 취소 요청을 한다. | 상태는 유지되지만 취소 요청은 관리자 승인 대기가 되고, 관리자가 유일한 다음 처리자다. | 요청이 대기하는 동안 의뢰자는 조회·대기만 한다. 재제출, 보완 요청, 보류·재개, 재배정, 결과 등록과 의뢰서 수정을 포함한 다른 업무 행위는 할 수 없다. |
| 관리자가 취소 요청을 승인 또는 거절 | 의뢰자는 결정 결과를 조회한다. | 승인하면 `취소`로 종료한다. 거절하면 요청 전 상태로 그대로 돌아가 해당 상태의 다음 처리자가 처리를 이어 간다. | 승인 뒤에는 조회만 한다. 거절 뒤에는 요청 전 상태의 규칙을 다시 따른다. |
| 관리자가 `검토 중` 의뢰를 반려 | 의뢰자는 반려 사유를 조회한다. | 상태가 `반려`로 바뀌며 종료한다. | 이후에는 조회만 한다. |
| `결과 확인 필요` | 의뢰자는 현재 결과를 확인한 뒤 결과를 확인하거나, 사유를 남겨 결과 재작업을 요청한다. | 결과 확인은 `완료`로 종료한다. 재작업 요청은 `해석 진행 중`으로 돌아가며 같은 담당자가 다음 처리자다. | 결과 재작업은 결과 확인과 다른 행동이다. 재작업 요청 뒤에는 같은 담당자의 해석과 다음 결과 등록을 조회·대기한다. |

`결과 확인 필요`에서는 취소와 취소 요청을 할 수 없다. 결과를 다시 등록하면 회차별 결과가 쌓이고 마지막 결과가 현재 결과가 되며, 의뢰자는 다시 결과 확인 또는 결과 재작업 요청을 판단한다.

#### 의뢰자의 조회·대기 경계

| 상태 또는 대기 | 다음 처리자 | 의뢰자의 처리 위치 |
|---|---|---|
| `검토 중` | 관리자 | 조회·대기 대상 |
| 일반 `해석 진행 중` | 배정 담당자 | 조회 대상이다. 대기 중인 요청이 없을 때만 진행 중 변경 또는 취소 요청을 시작할 수 있다. |
| `보류` | 보류한 사람 또는 관리자 | 조회·대기 대상이다. 재개·수정·진행 중 변경은 할 수 없고, 대기 중인 요청이 없을 때의 취소 요청만 가능하다. |
| `해석 진행 중(관리자 확인 대기)` | 관리자 | 조회·대기 대상이다. 관리자 결정 전에는 진행 중 변경과 취소 요청을 할 수 없다. |
| 취소 요청 대기 | 관리자 | 조회·대기 대상이며, 관리자의 승인·거절 외의 업무 행위는 할 수 없다. |
| `완료`, `반려`, `취소` | 없음 | 종료 상태로 조회만 한다. |

### 관리자 상세 여정 (1.4)

관리자는 한 번 이상 제출된 전체 의뢰를 조회하며, 다음 처리를 책임지는 `검토 중`, 취소 요청 대기, `해석 진행 중(관리자 확인 대기)`, 관리자가 보류한 의뢰를 할 일로 처리한다. 한 번도 제출하지 않은 의뢰와 제출 전 취소 의뢰는 관리자 조회 범위에 없다. 관리자는 의뢰서 내용을 직접 고치지 않으며, 아래 여정의 판단 기준이나 사유 코드 목록은 업무정의서의 검토 대상 규칙을 그대로 따른다.

#### 검토와 접수·배정

`검토 중`은 제출 또는 검토 단계 재제출 뒤 관리자의 현재 처리 대상이다. 관리자는 의뢰서와 이전 버전 대비 변경 내용을 보고, 다음 세 가지 중 하나로 검토를 끝낸다.

| 관리자의 결정 | 필수 기록 | 인계와 다음 상태 |
|---|---|---|
| 검토 단계 보완 요청 | 사유 코드, 설명 | `보완 필요`가 되며 의뢰자가 다음 처리자다. 의뢰자가 재제출하면 다시 `검토 중`으로 돌아와 관리자가 처리한다. |
| 반려 | 사유 코드, 설명 | `반려`로 종료하며 의뢰자는 반려 사유를 조회만 한다. |
| 접수·배정 | 해석담당자 | `해석 진행 중`이 되며 배정된 담당자가 다음 처리자다. 의뢰자는 진행 상황을 조회한다. |

관리자는 보완 요청과 반려에 필요한 사유 코드와 설명을 남기지만, 코드 값의 선택 기준을 이 여정에서 새로 정하지 않는다. 접수·배정 뒤에는 의뢰자와 배정된 담당자가 영향을 받는 사람으로 인계된다.

#### 해석 진행의 관리 개입

일반 `해석 진행 중`은 담당자가 주로 처리하는 상태지만, 관리자는 조회하고 아래의 관리 행위를 할 수 있다. 취소 요청이 대기 중이면 이 표의 행위를 할 수 없으며, 관리자 승인·거절만 처리한다.

| 시작 상태와 조건 | 관리자의 행동 | 인계와 상태 |
|---|---|---|
| 대기 중인 요청과 관리자 확인 대기가 없는 `해석 진행 중` | 정보 부족이면 해석 단계 보완을 요청하고 사유 코드와 설명을 남긴다. | `해석 중 보완 필요`가 되고 의뢰자가 보완·재제출의 다음 처리자다. 관리자가 요청한 보완의 재제출은 관리자 확인 대기로 돌아온다. |
| 일반 `해석 진행 중`, `해석 중 보완 필요`, `보류` | 현재 담당자와 다른 새 담당자 및 사유를 지정해 재배정한다. | 상태는 유지한다. 일반 진행 상태에서는 새 담당자가 다음 처리자가 된다. 진행 중 변경 요청이 대기 중인 재배정 뒤 그 요청의 수락·거절 처리자는 `G-30`이 확정될 때까지 정하지 않는다. 해석 중 보완 필요에서는 의뢰자의 재제출을 기다린다. 보류에서는 보류의 성격과 재개 규칙을 유지한다. |
| 관리자 확인 대기를 제외한 `해석 진행 중` | 일정 등 보완과 다른 사유로 보류하고 사유 코드와 설명을 남긴다. | `보류`가 된다. 관리자가 보류한 의뢰는 관리자의 현재 처리 대상이며, 의뢰자와 담당자는 재개를 기다린다. |
| `보류` | 관리자가 재개한다. | `해석 진행 중`으로 돌아가 현재 배정 담당자가 다음 처리자다. 담당자가 보류했던 의뢰도 관리자가 재개할 수 있다. |

담당자가 보류한 의뢰를 재배정하면 새 담당자가 보류를 이어받아 재개할 수 있고, 이전 담당자는 더 이상 그 의뢰를 보거나 재개할 수 없다. 관리자가 보류한 의뢰는 재배정해도 관리자의 보류로 남으므로, 관리자가 재개하기 전에는 새 담당자가 해석을 시작하지 않는다.

#### 관리자 요청 보완의 확인

관리자가 요청한 해석 단계 보완을 의뢰자가 재제출하면 `해석 진행 중(관리자 확인 대기)`가 되어 관리자의 현재 처리 대상이 된다. 이 대기 동안 담당자는 해석·결과 등록을 할 수 없고 의뢰자는 진행 중 변경·취소 요청을 할 수 없다. 관리자는 다음 둘 중 하나로만 확인을 끝낸다.

| 관리자의 확인 결정 | 필수 기록 | 인계와 다음 상태 |
|---|---|---|
| 해석 계속·담당자 배정 | 해석을 계속할 담당자 | 일반 `해석 진행 중`으로 바뀌며 지정 담당자가 다음 처리자다. 기존 담당자를 다시 지정할 수도 있다. |
| 재보완 요청 | 사유 코드, 설명 | `해석 중 보완 필요`가 되며 의뢰자가 다시 보완·재제출할 차례다. |

관리자 확인 대기에서는 일반 재배정, 보류, 새 해석 단계 보완 요청을 처리하지 않는다. 이 단계의 처리 책임은 특정 보완 요청자에게 고정하지 않고 관리자 역할에 둔다.

#### 취소 요청 처리

의뢰자가 일반 `해석 진행 중`, `해석 중 보완 필요`, `보류`에서 취소 요청을 하면 상태는 유지한 채 취소 요청 대기가 되고, 이는 관리자의 현재 처리 대상이다. 이 대기 동안에는 관리자의 승인·거절 외에 누구도 다른 업무 행위나 의뢰서 수정을 할 수 없다.

| 관리자의 결정 | 입력 또는 이력 | 인계와 결과 |
|---|---|---|
| 승인 | 자동 이력 | `취소`로 종료한다. 보류 중이었다면 보류 정보도 함께 지운다. 알림 초안의 대상은 의뢰자와 배정된 담당자다. |
| 거절 | 거절 사유, 자동 이력 | 요청 전 상태를 유지하고, 요청 전 상태의 다음 처리자가 이어서 처리한다. 이력에 거절과 사유를 남긴다. |

의뢰자가 `작성 중`, `검토 중`, `보완 필요`에서 직접 취소한 의뢰와 `완료`, `반려`, `취소` 상태는 관리자에게 처리 할 일이 없으며 조회만 한다.

#### 관리자 처리·조회 경계

| 상태 또는 대기 | 관리자의 위치 |
|---|---|
| `검토 중` | 검토·보완 요청·반려·접수·배정 중 하나를 처리하는 현재 처리 대상 |
| 취소 요청 대기 | 승인 또는 거절을 처리하는 현재 처리 대상. 그 밖의 업무 행위는 차단됨 |
| `해석 진행 중(관리자 확인 대기)` | 해석 계속·담당자 배정 또는 재보완 요청을 처리하는 현재 처리 대상 |
| 관리자가 보류한 `보류` | 재개할 때까지 현재 처리 대상 |
| 일반 `해석 진행 중`, `해석 중 보완 필요`, 담당자가 보류한 `보류` | 관리·조회 대상. 수행 가능 상태이면 해석 단계 보완 요청·재배정·보류·재개를 할 수 있으나 할 일 목록에는 자동으로 들어가지 않음 |
| `결과 확인 필요` | 관리·조회 대상. 의뢰자의 결과 확인 또는 재작업 요청을 기다리며 관리자의 업무 행위는 없음 |
| `작성 중`, 제출 전 `취소` | 조회·처리 대상 아님 |
| `완료`, `반려`, `취소` | 조회만 가능 |

### 담당자 상세 여정 (1.5)

담당자는 자신에게 배정된 의뢰를 조회하고 해석을 수행해 결과를 회신한다. 담당자의 현재 처리 대상은 본인에게 배정된 일반 `해석 진행 중`, 진행 중 변경 수락 대기, 본인이 보류한 의뢰다. 실제 해석 방법, 메시, 솔버와 수렴 판단은 이 업무 UX 범위 밖이며, 담당자는 의뢰서 내용을 직접 고치지 않는다.

#### 배정 수신과 해석 진행

관리자의 접수·배정, 관리자 확인 뒤 해석 계속·담당자 배정, 또는 결과 재작업 요청으로 담당자에게 일반 `해석 진행 중` 의뢰가 인계된다. 이 의뢰는 담당자의 현재 처리 대상이며, 담당자는 의뢰서와 이전 버전 대비 변경 내용을 확인해 해석을 진행한다. 결과 재작업 요청으로 돌아온 경우에도 같은 담당자가 다음 처리자이며, 이전 결과 회차는 남고 마지막 등록 결과가 현재 결과가 된다.

`해석 진행 중(관리자 확인 대기)`은 담당자가 배정된 의뢰라도 현재 처리 대상이 아니다. 담당자는 상태와 이력을 조회할 수 있으나, 관리자가 해석 계속·담당자 배정 또는 재보완 요청을 처리하기 전에는 해석을 진행하거나 결과를 등록할 수 없다.

#### 해석 단계 보완 요청

| 시작 상태와 조건 | 담당자의 행동 | 인계와 다음 상태 |
|---|---|---|
| 대기 중인 요청과 관리자 확인 대기가 없는 일반 `해석 진행 중` | 정보가 부족하면 해석 단계 보완을 요청하고 사유 코드와 설명을 남긴다. 해석을 멈춘다. | `해석 중 보완 필요`가 되며 의뢰자가 보완·재제출의 다음 처리자다. 담당자 요청 보완을 의뢰자가 재제출하면 일반 `해석 진행 중`으로 돌아가 담당자가 해석을 이어서 수행한다. |
| 관리자가 요청한 해석 단계 보완의 재제출 뒤 | 담당자는 관리자 확인의 진행 상황을 조회한다. | `해석 진행 중(관리자 확인 대기)`에서는 담당자가 보완 요청, 해석 진행, 결과 등록을 할 수 없다. 관리자가 해석 계속·담당자 배정하면 지정 담당자가 다시 처리한다. |

정보 부족은 보류가 아니라 보완 요청으로 처리한다. 담당자가 보완을 요청한 뒤 관리자가 재배정할 수 있으나, 재배정 뒤 의뢰자가 재제출했을 때 원 요청 담당자와 새 담당자 중 누가 해석을 이어받는지는 `G-31`이 확정될 때까지 정하지 않는다.

#### 진행 중 변경 요청 처리

의뢰자가 일반 `해석 진행 중`에서 진행 중 변경을 요청하면 상태는 유지되지만, 배정 담당자는 변경 수락·거절을 처리하는 현재 처리자가 된다. 담당자는 변경 의뢰서, 변경 사유와 이전 의뢰서의 차이를 확인해 다음 중 하나를 처리한다.

| 담당자의 결정 | 필수 입력 | 인계와 결과 |
|---|---|---|
| 수락 | 없음 | 변경 의뢰서가 새 버전으로 남고 일반 `해석 진행 중`에서 담당자가 해석을 계속한다. 의뢰자에게 결정 결과를 알린다. |
| 거절 | 거절 사유 | 원래 의뢰서로 일반 `해석 진행 중`을 계속하며 담당자가 해석을 이어서 수행한다. 제안된 변경 의뢰서와 거절 사유는 이력에 남고, 의뢰자에게 결정 결과를 알린다. |

변경 요청이 대기 중이면 담당자는 먼저 수락 또는 거절해야 해석 단계 보완을 요청할 수 있으며, 결과 등록도 할 수 없다. 보류는 가능하고 변경 요청은 대기한 채 남으며, 재개 뒤 담당자가 수락 또는 거절한다. 이 대기 중 재배정 뒤의 수락·거절 처리자는 `G-30` 확인 전까지 정하지 않는다.

#### 보류·재개와 재배정

| 시작 상태와 조건 | 담당자의 행동 또는 위치 | 인계와 다음 상태 |
|---|---|---|
| 관리자 확인 대기를 제외한 `해석 진행 중` | 일정 등 보완과 다른 사유로 보류하고 사유 코드와 설명을 남긴다. 진행 중 변경 요청이 대기 중이어도 보류할 수 있다. | `보류`가 되며 보류한 담당자의 현재 처리 대상이 된다. 의뢰자와 관리자는 보류 상태를 조회한다. |
| 본인이 보류한 `보류` | 담당자가 재개한다. | 일반 `해석 진행 중`으로 돌아가 같은 담당자가 해석을 다시 처리한다. |
| 관리자가 보류한 `보류` | 담당자는 조회·대기하며 재개할 수 없다. | 관리자가 재개하면 일반 `해석 진행 중`으로 돌아가 현재 배정 담당자가 다음 처리자다. |
| 관리자가 재배정한 의뢰 | 기존 담당자는 더 이상 다음 처리를 책임지지 않는다. | 일반 진행 상태에서는 새 담당자가 처리 대상이 된다. 담당자가 보류한 의뢰를 재배정한 경우에는 새 담당자가 보류를 이어받아 재개할 수 있고, 이전 담당자는 더 이상 해당 의뢰를 보거나 재개할 수 없다. |

#### 취소 요청과 결과 등록

취소 요청이 대기 중인 의뢰는 관리자의 승인·거절만 가능하다. 담당자는 해석, 보완 요청, 보류·재개, 결과 등록 등 어떤 업무 행위도 할 수 없으며 관리자의 결정을 조회·대기한다. 승인되면 `취소`로 종료하고, 거절되면 요청 전 상태의 규칙에 따라 다음 처리자가 업무를 이어 간다.

| 시작 상태와 조건 | 담당자의 행동 | 인계와 다음 상태 |
|---|---|---|
| 대기 중인 요청이 없는 일반 `해석 진행 중` | 해석이 끝나면 결과 요약을 등록한다. | `결과 확인 필요`가 되고 의뢰자가 결과 확인 또는 재작업 요청의 다음 처리자다. 담당자는 결과 확인을 조회한다. |
| `결과 확인 필요`에서 의뢰자가 재작업 요청 | 담당자는 재작업 요청과 사유를 확인한다. | 일반 `해석 진행 중`으로 돌아가 같은 담당자가 해석을 다시 진행한다. |
| `결과 확인 필요`에서 의뢰자가 결과 확인 | 담당자는 완료 결과를 조회한다. | `완료`로 종료하며 이후에는 조회만 한다. |

#### 담당자 처리·조회 경계

| 상태 또는 대기 | 담당자의 위치 |
|---|---|
| 본인에게 배정된 일반 `해석 진행 중` | 해석 진행, 해석 단계 보완 요청, 보류, 결과 등록을 수행하는 현재 처리 대상. 대기 중인 요청이 있으면 허용된 행동만 할 수 있음 |
| 진행 중 변경 수락 대기 | 수락 또는 거절을 처리하는 현재 처리 대상. 보류만 병행할 수 있고, 보완 요청과 결과 등록은 할 수 없음 |
| 본인이 보류한 `보류` | 재개할 때까지 현재 처리 대상 |
| `해석 진행 중(관리자 확인 대기)`, 관리자가 보류한 `보류`, 취소 요청 대기 | 조회·대기 대상. 담당자 업무 행위는 할 수 없음 |
| `해석 중 보완 필요` | 의뢰자의 재제출을 기다리는 조회 대상. 관리자가 재배정할 수 있음 |
| `결과 확인 필요` | 의뢰자의 결과 확인 또는 재작업 요청을 기다리는 조회 대상 |
| `완료`, 배정 후 `취소` | 종료 상태로 조회만 가능 |
| `반려`, 배정 전 `취소` | 담당자에게 배정 이력이 없으므로 조회·처리 대상 아님 |

### 세 역할의 인계와 대기 대조 (1.6)

아래 대조는 앞선 세 역할 여정의 상태 변화마다 수행자, 다음 처리자와 대기·차단 역할이 하나로 읽히는지 확인한 결과다. 업무 행위의 수행 가능 상태는 업무정의서 3.2를 우선하며, 같은 상태라도 대기 요청의 종류에 따라 다음 처리자가 달라지는 경우를 분리한다.

#### 인계 지점 대조

| 시작 사건 | 수행자 | 다음 상태와 처리자 | 대기·차단 경계 |
|---|---|---|---|
| 제출 또는 검토 단계 재제출 | 의뢰자 | `검토 중`으로 바뀌며 관리자가 검토한다. | 의뢰자는 검토 결과를 조회·대기한다. |
| 검토 단계 보완 요청 | 관리자 | `보완 필요`가 되며 의뢰자가 보완·재제출한다. | 관리자는 재제출 뒤 검토를 이어서 처리한다. |
| 반려 | 관리자 | `반려`로 종료한다. | 의뢰자와 관리자는 조회만 하며 담당자는 배정 이력이 없다. |
| 접수·배정 | 관리자 | 일반 `해석 진행 중`이 되며 배정 담당자가 해석을 시작한다. | 의뢰자는 진행 상황을 조회한다. |
| 담당자 요청 해석 단계 보완 | 배정 담당자 | `해석 중 보완 필요`가 되며 의뢰자가 재제출한다. | 재배정이 없으면 재제출 뒤 같은 담당자가 이어서 처리한다. 재배정이 있었다면 다음 처리자는 `G-31` 확인 대상이다. |
| 관리자 요청 해석 단계 보완 | 관리자 | `해석 중 보완 필요`가 되며 의뢰자가 재제출한다. | 재제출 뒤 `해석 진행 중(관리자 확인 대기)`가 되어 관리자가 해석 계속·담당자 배정 또는 재보완 요청을 처리한다. 담당자는 해석·결과 등록을, 의뢰자는 변경·취소 요청을 할 수 없다. |
| 진행 중 변경 요청 | 의뢰자 | 상태는 일반 `해석 진행 중`으로 유지되고 배정 담당자가 수락·거절한다. | 취소 요청을 동시에 만들 수 없고, 담당자는 보완 요청·결과 등록을 할 수 없다. 보류는 가능하다. 재배정 뒤 수락·거절 처리자는 `G-30` 확인 대상이다. |

| 취소 요청 | 의뢰자 | 상태는 유지하되 관리자가 승인·거절한다. | 의뢰자와 담당자를 포함한 다른 역할은 승인·거절 전까지 모든 업무 행위를 할 수 없다. |
| 결과 등록 | 배정 담당자 | `결과 확인 필요`가 되며 의뢰자가 결과 확인 또는 재작업 요청을 한다. | 관리자와 담당자는 조회한다. |
| 결과 재작업 요청 | 의뢰자 | 일반 `해석 진행 중`으로 돌아가 같은 담당자가 해석을 다시 진행한다. | 의뢰자는 다음 결과 등록을 조회·대기한다. |
| 결과 확인 | 의뢰자 | `완료`로 종료한다. | 배정 이력이 있는 담당자와 관리자는 조회만 한다. |

| `해석 진행 중(관리자 확인 대기)` | 관리자 | 의뢰자와 담당자는 조회·대기한다. 의뢰자는 변경·취소 요청을, 담당자는 해석·결과 등록을 할 수 없다. |
| 담당자가 보류한 `보류` | 보류한 담당자 | 관리자는 재개·재배정할 수 있고, 의뢰자는 조회·대기한다. 의뢰자는 대기 중인 요청이 없을 때 취소 요청을 시작할 수 있다. |
| 관리자가 보류한 `보류` | 관리자 | 담당자는 재개할 수 없으며, 의뢰자는 조회·대기한다. 의뢰자는 대기 중인 요청이 없을 때 취소 요청을 시작할 수 있다. |
| 취소 요청 대기 | 관리자 | 의뢰자와 담당자는 조회·대기만 하며 다른 업무 행위는 모두 차단된다. |
| `결과 확인 필요` | 의뢰자 | 담당자와 관리자는 결과 확인 또는 재작업 요청을 기다리며 조회한다. |
| `완료`, `반려`, `취소` | 없음 | 종료 상태로 조회만 한다. 단, 담당자는 배정 이력이 있는 의뢰만 조회한다. |

`G-30`과 `G-31`은 재배정과 대기 요청이 겹치는 두 경우의 다음 처리자를 아직 확정하지 않은 항목이다. 이 두 경우를 제외하면 각 인계 지점의 수행자·다음 처리자·대기 역할은 세 역할 여정과 업무정의서 3.2~3.5에서 일치한다.

## 4. 보류 항목 적용 경계

설치 조건 세부와 CAD 전달 방식은 `확정 필요`이므로 입력 구조나 전달 수단을 이 기준서에서 정하지 않는다. 그 밖의 보류 항목은 상태와 책임만 표현하며, 임시 값, 검증 규칙, 인증 방식, 첨부 제약을 가정하지 않는다. 자세한 근거와 처리 원칙은 `docs/spec-gaps.md`의 `UX 착수 보류 항목 구분 (0.2)`를 따른다.

## 5. 화면 범위 및 정보 구조

### 공통 탐색 구조와 역할별 첫 화면 (2.1)

이 절은 역할별 업무를 어디에서 시작하고 찾는지의 책임만 정의한다. 여기의 `홈`, `내 할 일`, `의뢰함`, `의뢰 상세`는 탐색 책임을 설명하는 작업 명칭이며, 최종 메뉴명·탭·화면 분할을 확정하지 않는다. 탐색 항목의 시각 디자인, 메뉴 배치, 목록의 필드·필터·정렬, 상세 화면의 정보 구성은 후속 작업에서 다룬다. 역할과 소속 부서는 세션에서 제공된다는 전제를 따르며, 로그인·계정 관리 화면은 이 범위에 포함하지 않는다.

#### 공통 탐색 대상의 책임

| 탐색 대상 | 책임 | 포함하지 않는 책임 |
|---|---|---|
| 홈 | 현재 역할이 바로 처리하거나 확인해야 할 상황을 요약해 `내 할 일` 또는 필요한 의뢰 상세로 보낸다. 역할별 첫 진입점이다. | 전체 의뢰의 완전한 목록, 상태별 전체 작업 처리, 의뢰서 내용의 편집·판단을 맡지 않는다. |
| 내 할 일 | 업무정의서 3.5의 현재 처리 대상을 역할별로 모아, 다음 행동이 필요한 의뢰로 들어가는 목록이다. | 조회만 가능한 의뢰나 이미 다른 역할이 다음 처리를 맡은 의뢰를 할 일로 넣지 않는다. |
| 의뢰함 | 역할의 조회 범위 안에서 의뢰를 찾아 상태·진행 상황을 확인하고 상세로 들어가는 목록이다. 현재 처리 대상이 아니어도 포함할 수 있다. | 할 일 우선순위나 업무 행위 권한을 대신 결정하지 않는다. |
| 의뢰 상세 | 하나의 의뢰에 대해 상태, 현재 처리자, 이력과 역할·상태가 허용하는 업무 행위를 연결하는 기준점이다. 상태 변화 뒤에는 다음 처리자의 `내 할 일` 또는 조회·대기 상태로 이어진다. | 별도의 목록 탐색이나 역할별 업무 우선순위 결정을 맡지 않는다. |

공통 이동의 책임은 `홈 → 내 할 일 또는 의뢰함 → 의뢰 상세`이다. 의뢰자에게만 `홈 → 새 의뢰 시작 → 작성 중 상세`의 병렬 진입 경로가 있다. 의뢰 상세에서 업무 행위가 완료되면 이전 처리자는 해당 의뢰를 조회·대기하고, 다음 처리자에게 할 일이 생기는 경우 그 역할의 `내 할 일`에서 이어진다. 취소 요청 대기와 관리자 확인 대기에서는 현재 처리자인 관리자가 상세에서 각각 승인·거절 또는 해석 계속·담당자 배정·재보완 요청을 처리하며, 의뢰자와 담당자는 조회·대기한다.

#### 역할별 첫 화면과 목록 범위

| 역할 | 첫 화면의 목적 | 내 할 일에 모이는 대상 | 의뢰함의 조회 범위 |
|---|---|---|---|
| 의뢰자 | 새 의뢰를 시작해 `작성 중` 상세로 들어가거나, 작성 중 의뢰를 이어 작성하고 보완·결과 확인처럼 본인 응답이 필요한 의뢰를 빠르게 찾는다. 다른 처리자가 진행 중인 내 의뢰는 현황 확인으로 연결한다. | `작성 중`, `보완 필요`, `해석 중 보완 필요`, `결과 확인 필요` | 본인 의뢰와 같은 소속 부서 의뢰를 조회한다. 같은 부서의 다른 의뢰자가 만든 의뢰는 조회만 한다. 한 번도 제출하지 않은 의뢰와 제출 전 취소 의뢰는 작성자만 조회한다. |
| 해석관리자 | 검토, 취소 요청, 관리자 확인, 관리자 보류처럼 관리자의 판단이 멈춰 있는 의뢰를 빠르게 찾는다. | `검토 중`, 취소 요청 대기, `해석 진행 중(관리자 확인 대기)`, 관리자가 보류한 `보류` | 한 번 이상 제출된 전체 의뢰를 조회한다. 한 번도 제출하지 않은 의뢰와 제출 전 취소 의뢰는 조회하지 않는다. |
| 해석담당자 | 배정된 해석을 시작·재개하거나, 수락·거절이 필요한 진행 중 변경 요청을 빠르게 찾는다. | 본인에게 배정된 일반 `해석 진행 중`, 진행 중 변경 수락 대기, 본인이 보류한 `보류` | 본인에게 배정된 의뢰를 조회한다. 관리자 확인 대기 의뢰는 배정되어도 조회·대기 대상이며 할 일에는 넣지 않는다. |

같은 상태라도 대기 요청의 종류와 보류한 사람에 따라 `내 할 일`의 역할이 달라진다. 예를 들어 취소 요청 대기는 관리자에게만, 관리자 확인 대기는 관리자에게만, 담당자가 보류한 의뢰는 해당 담당자에게만, 관리자가 보류한 의뢰는 관리자에게만 들어간다.

#### 역할별 내 할 일의 업무 분류 기준

`내 할 일`은 역할별 현재 처리 대상을 업무 종류로 구분한다. 이 분류는 무엇을 처리해야 하는지 구분하는 기준이며, 하위 메뉴·탭·섹션의 이름과 배치는 2.2~2.4에서 정한다.

| 역할 | 업무 분류 | 포함 상태 또는 대기 |
|---|---|---|
| 의뢰자 | 작성 | `작성 중` |
| 의뢰자 | 보완 | `보완 필요`, `해석 중 보완 필요` |
| 의뢰자 | 결과 확인 | `결과 확인 필요` |
| 해석관리자 | 검토 | `검토 중` |
| 해석관리자 | 취소 요청 처리 | 취소 요청 대기 |
| 해석관리자 | 해석 계속 확인 | `해석 진행 중(관리자 확인 대기)` |
| 해석관리자 | 관리자 보류 | 관리자가 보류한 `보류` |
| 해석담당자 | 해석 진행 | 본인에게 배정된 일반 `해석 진행 중` |
| 해석담당자 | 변경 요청 판단 | 진행 중 변경 수락 대기 |
| 해석담당자 | 담당자 보류 | 본인이 보류한 `보류` |

#### 목록과 상세의 권한 경계

- `내 할 일`은 행위 책임을 기준으로 하고, `의뢰함`은 조회 권한을 기준으로 한다. 같은 의뢰가 두 목록에 함께 보일 수 있으나, 역할이 수행할 수 없는 업무 행위는 상세에서 제공하지 않는다.
- 다른 역할이 다음 처리를 맡은 상태는 의뢰자·관리자·담당자에게 각각 조회·대기 대상으로 보일 수 있으나, 현재 처리자의 할 일과 혼동하지 않는다.
- 종료 상태는 역할의 조회 범위 안에서만 상세를 열람한다. 담당자는 배정 이력이 있는 `완료`와 배정 후 `취소`만 조회하며, `반려`와 배정 전 `취소`는 담당자 대상이 아니다.
- `G-30`, `G-31`이 정해지기 전에는 재배정과 대기 요청이 겹친 의뢰의 다음 처리자를 특정 목록에 확정해 넣지 않는다. 상세에서는 확인 필요 상태임을 유지한다.

### 의뢰자 작성 상태·단계·변경 영향 (2.2.1)

이 절은 의뢰자가 의뢰서를 작성·보완·변경하는 단계의 책임과 구성 요소 사이의 선후 관계만 정의한다. 단계는 작업 책임을 구분하는 명칭이며, 최종 화면 수·메뉴·입력 필드·검증 메시지는 정하지 않는다. 의뢰 대상·의뢰 내용·제품·조건·Case의 세부 정보 구조는 각각 2.2.2~2.2.7에서 다룬다.

#### 작성 구성 요소와 선후 관계

의뢰자는 `작성 중`에서 아래 구성 요소를 준비하고 제출 조건을 갖춘 뒤 제출한다. 의뢰 대상 확정은 상태를 바꾸지 않지만, 이후 조건 구성과 Case 준비의 기준을 정하는 경계다. 의뢰자 정보와 제품 분류에 의존하지 않는 공통 개요는 대상 확정과 별도로 작성할 수 있다. 다만 개발 프로젝트 정보는 제품 분류의 제품 사업부가 정해진 뒤에 작성·확인한다.

```text
제품 분류 → 해석유형 → (RAC Window이면: 해석 범위 → [실내·실외 모두] 요청 방식·상황 설명; PCB발열이면: 냉각 방식) → 확정 → 조건 구성 → 조건 패키지
    └──────────────────────────────────────────────→ 의뢰 내용의 PMS 관련 확인
해석 제품(Base·비교) → 형상 축 ──────────────────────────────────────────────┐
조건 패키지 ────────────────────────────────────────────────────────────────┼→ Case → 제출 준비
의뢰 내용 ──────────────────────────────────────────────────────────────────┘
```

RAC Window 여부와 PCB발열 여부는 서로 독립된다. 둘 다 해당하면 해석 범위(필요 시 요청 방식·상황 설명)와 냉각 방식을 모두 정한 뒤 확정한다.

| 작성 단계의 정보 묶음 | 의뢰자의 책임 | 앞·뒤 단계와의 관계 |
|---|---|---|
| 의뢰 대상 | 제품 분류를 먼저 정한 뒤 해석유형, 해당될 때 해석 범위·냉각 방식을 정하고 확정한다. 해석 범위가 `실내·실외 모두`이면 해석 요청 방식과 상황 설명도 정한다. | 확정하면 의뢰번호가 발급되고 그 시점의 기준 데이터에 따라 조건 구성이 정해진다. 조건 패키지와 Case는 확정된 대상에 맞춰 준비한다. |
| 의뢰 내용 | 의뢰의 개요를 준비하고 의뢰 유형에 맞는 정보를 갖춘다. | 의뢰 유형은 PMS·개발 등급·NPI 단계의 필요 여부를 정한다. 제품 분류는 PMS 프로젝트의 대상 사업부를 정하므로, 제품 분류 변경 뒤에는 PMS 관련 선택을 다시 확인한다. |
| 해석 제품 | Base 제품 1개와 필요한 비교 제품을 준비한다. | 제품 순서로 형상 축이 생기며, 형상 축은 Case에서 선택할 형상 단위가 된다. |
| 조건 패키지 | 확정된 의뢰 대상의 조건 구성에 따라 활성 조건을 준비한다. | 조건 패키지는 Case에서 비교하는 조건 단위다. 대상 변경으로 조건 구성이 달라지면 패키지와 Case를 다시 확인한다. |
| Case | 형상 축과 활성 조건 패키지의 필요한 조합을 정한다. | 모든 구성 요소를 제출 준비에서 함께 대조한다. 구성 방식·재확인 저장 방식과 Case 세부 정보는 2.2.7 및 `G-28` 확인 전까지 정하지 않는다. |
| 제출 준비 | 위 구성 요소가 업무정의서 8장의 제출 조건을 충족하는지 의뢰자가 확인한다. | 제출하면 새 의뢰서 버전이 남고 `검토 중`으로 인계된다. 재제출과 진행 중 변경 수락 때도 새 버전이 남는다. |

#### 작성·보완·진행 중 변경의 수정 경계

의뢰서 내용은 의뢰자만 수정하며, 관리자와 담당자는 직접 수정하지 않는다. `작성 중`, `보완 필요`, `해석 중 보완 필요`에서는 의뢰자가 의뢰서 전체를 고치거나 내용 변경 없이 재제출할 수 있다. `해석 진행 중`에서는 원 의뢰서를 직접 고치지 않고, 제출 조건을 충족한 변경안을 변경 사유와 함께 진행 중 변경 요청으로만 낸다.

| 상태 또는 대기 | 의뢰자의 수정·재제출 책임 | 다음 인계와 차단 경계 |
|---|---|---|
| `작성 중` | 의뢰서 구성 요소를 작성·수정하고 저장해 이어 작성한다. 제출 준비가 끝나면 제출한다. | 제출하면 `검토 중`으로 가고 관리자가 검토한다. 제출 전 의뢰는 작성자만 조회한다. |
| `보완 필요` | 관리자 보완 요청에 따라 의뢰서 구성 요소를 수정하거나, 내용 변경 없이 재제출한다. | 재제출하면 `검토 중`으로 돌아간다. 수정의 범위는 보완 사유에 한정하지 않지만, 제출 조건은 다시 충족해야 한다. |
| `해석 중 보완 필요` | 담당자 또는 관리자의 해석 단계 보완 요청에 따라 의뢰서 구성 요소를 수정하거나, 내용 변경 없이 재제출한다. | 담당자 요청이면 일반 `해석 진행 중`으로 돌아간다. 관리자 요청이면 `해석 진행 중(관리자 확인 대기)`로 가며, 관리자가 해석 계속·담당자 배정 또는 재보완 요청을 처리할 때까지 의뢰자는 진행 중 변경·취소 요청을 할 수 없다. 담당자 요청 뒤 재배정된 경우의 다음 처리자는 `G-31` 확인 전까지 정하지 않는다. |
| 일반 `해석 진행 중` | 의뢰서 직접 수정·재제출은 할 수 없다. 범위나 조건을 바꾸려면 제출 조건을 충족한 변경안과 변경 사유로 진행 중 변경을 요청한다. | 상태는 유지하고 배정 담당자가 수락·거절한다. 수락하면 변경안이 새 버전으로 반영되고, 거절하면 원 의뢰서로 계속한다. 변경 요청 대기 중에는 취소 요청을 함께 만들 수 없으며 담당자는 보완 요청·결과 등록을 할 수 없다. 재배정이 겹친 수락·거절 처리자는 `G-30` 확인 전까지 정하지 않는다. |

취소 요청이 대기하면 위 표의 수정·재제출과 다른 모든 업무 행위가 차단되고, 관리자의 승인·거절만 가능하다. `보류`, `검토 중`, `결과 확인 필요`, 종료 상태는 의뢰자가 이 절의 작성·보완 수정이나 진행 중 변경 요청을 시작하는 상태가 아니다. 이 경계는 업무정의서 3.2~3.4의 수행 가능 상태를 따른다.

#### 원본 변경 뒤 재확인 범위

아래 표의 재확인은 앞 단계가 바뀐 뒤 의뢰자가 뒤 단계의 현재 선택과 제출 준비를 다시 대조하는 책임을 뜻한다. Case를 다시 확인해야 한다는 업무 규칙만 적용하며, 확인 사실을 어떤 데이터로 저장할지는 `G-28`이 정해질 때까지 정하지 않는다.

| 바뀌는 정보 묶음 | PMS·조건부 대상 항목 재확인 | 조건 구성·조건 패키지 재확인 | 형상 축 재확인 | Case 재확인 | 제출 준비 영향 |
|---|---|---|---|---|---|
| 제품 분류 | 선택한 PMS 프로젝트와 자동으로 채워진 PMS 정보를 비우고, 의뢰 유형이 개발 프로젝트이면 새 제품 사업부의 PMS 프로젝트를 다시 고른다. AIDC로 바뀌면 의뢰 유형을 비개발 유형으로 바꾸기 전에는 다시 확정하거나 제출할 수 없다. RAC Window가 아니게 되면 해석 범위·요청 방식·상황 설명을 비활성으로 보존하고, RAC Window가 되면 다시 확인한다. | 의뢰 대상을 다시 확정한 시점의 기준으로 조건 구성 전체를 다시 보고, 새 구성에 맞게 활성 조건 패키지를 확인한다. | 해석 제품 자체가 바뀌지 않는 한 이 변경만으로 형상 축을 새로 만들지는 않는다. | 조건 구성과 활성 조건이 달라질 수 있으므로 다시 확인한다. | 다시 확정한 시점의 기준 데이터를 적용하고, 의뢰 내용·조건·Case를 포함한 제출 조건을 다시 확인한다. |
| 해석유형 | 제품 분류가 그대로면 PMS 선택과 RAC Window 범위 정보는 유지한다. PCB발열이 아니게 되면 냉각 방식을 비활성으로 보존하고, PCB발열이 되면 다시 확인한다. | 의뢰 대상을 다시 확정한 시점의 기준으로 조건 구성 전체와 활성 조건 패키지를 다시 확인한다. | 해석 제품 자체가 바뀌지 않는 한 이 변경만으로 형상 축을 새로 만들지는 않는다. | 조건 구성과 활성 조건이 달라질 수 있으므로 다시 확인한다. | 새 해석유형과 다시 확정한 기준 데이터에 맞춰 조건·Case를 포함한 제출 조건을 다시 확인한다. |

| 모델명 | 의뢰 제목을 자동으로 다시 계산한다. | 조건 구성에는 직접 영향을 주지 않는다. | 직접 영향 없음 | 직접 영향 없음 | 모델명 필수 여부와 제목 형식을 다시 확인한다. |
| 냉각 방식 | 직접 영향 없음 | PCB발열의 냉각 방식이 바뀌면 PCB의 냉매 조건과 해당 조건 패키지를 다시 확인한다. | 직접 영향 없음 | 활성 조건이 달라질 수 있으므로 다시 확인한다. | 조건·Case 관련 제출 조건을 다시 확인한다. |
| 해석 제품의 추가·삭제·변경 | 직접 영향 없음 | 직접 영향 없음 | Base·비교 제품의 변화에 맞춰 형상 축을 다시 확인한다. | 형상 축이 바뀌므로 필요한 조합과 모든 형상 사용 여부를 다시 확인한다. | 제품·Case 관련 제출 조건을 다시 확인한다. |

의뢰 대상의 다시 확정은 의뢰서를 수정할 수 있는 세 상태에서만 가능하며, 처음 발급한 의뢰번호는 유지한다. 새 유형에 맞지 않는 기존 조건 값은 비활성으로 보존한다는 업무 규칙은 따르되, 비활성 값의 세부 표현과 조건별 입력 구조는 후속 작업에서 다룬다. 설치 조건 세부와 CAD 전달 방식은 `확정 필요`이므로 이 절에서 입력 구조나 전달 수단을 정하지 않는다.

### 의뢰 대상·의뢰 내용의 정보 구조 (2.2.2)

이 절은 의뢰 대상과 의뢰 내용에 포함되는 정보 묶음, 확정 순서, 조건부 관계 및 변경 영향을 정의한다. 작성·보완·진행 중 변경의 수정 경계와 공통 재확인 원칙은 2.2.1을 따르며, 조건 패키지·형상 축·Case의 상세 구조는 각각 2.2.3~2.2.7에서 다룬다. 최종 화면 수, 입력 컨트롤, 자동 채움의 표시 방식과 검증 문구는 여기서 정하지 않는다.

#### 의뢰 대상: 정보 묶음과 확정 순서

의뢰 대상은 제품 분류와 해석유형으로 요청 범위를 정하고, 적용되는 추가 선택을 마친 뒤 확정하는 하나의 묶음이다. 의뢰자는 아래 순서를 유지한다.

```text
제품 분류 → 해석유형 → (RAC Window이면: 해석 범위 → [실내·실외 모두] 요청 방식·상황 설명; PCB발열이면: 냉각 방식) → 확정
```

| 순서 | 정보 묶음 | 포함 정보와 조건부 관계 | 확정 전후의 책임 |
|---|---|---|---|
| 1 | 제품 분류 | 제품 사업부 → Product Line-up → Platform → Chassis의 등록된 조합을 고른다. Chassis 아래 단계는 두지 않으며, Chassis가 없는 경로는 비워 둔다. SAC·Chiller는 Platform을 목록에서 고르고, RAC·Air Care는 Product Line-up에서 Platform이 정해지며, AIDC는 Platform이 해당 없다. | 등록되지 않은 분류를 의뢰자가 새로 만들지 않는다. 이 제품 사업부가 PMS 프로젝트의 대상 사업부를 정한다. |
| 2 | 해석유형 | 지원하는 11종 중 하나를 고른다. | 해석유형은 뒤의 조건 구성을 정하는 기준이다. |
| 3 | 해석 범위 | 제품 분류가 `RAC > Window > Window`인 경우에만 실내측, 실외측, 실내·실외 모두 중 하나를 고른다. `실내·실외 모두`는 동시운전 또는 실내측·실외측 각각의 해석 요청 중 하나로 단정하지 않는다. 이 선택이면 아래 두 정보를 함께 남긴다. 그 밖의 제품 분류에는 이 항목을 적용하지 않으며, 별도 일반 운전 구분도 두지 않는다. | 해당되는 경우에만 확정 전 선택을 마친다. |
| 3-1 | 해석 요청 방식 | 해석 범위가 `실내·실외 모두`일 때만 필수다. `동시 운전` / `실내측·실외측 각각 해석` / `기타` 중 하나를 고른다. | 실제 RPM·풍량을 정하는 운전 조건과 구분하며, 해당 수치는 후속 해석조건에서 다룬다. |
| 3-2 | 해석 범위 상황 설명 | 해석 범위가 `실내·실외 모두`일 때만 필수다. 두 측을 함께 또는 각각 해석해야 하는 이유·관계·특이사항을 자유 입력으로 남긴다. | 선택값만으로 부족한 요청 상황을 전달하며, 자유 입력의 공통 200자 제한을 따른다. |
| 4 | 냉각 방식 | 해석유형이 PCB발열인 경우에만 공랭식 또는 수랭식을 고른다. | 수랭식이면 확정 뒤 PCB 조건의 냉매 조건이 적용되며, 그 세부 입력 구조는 2.2.6에서 다룬다. |
| 5 | 확정 | 앞선 선택을 고정한다. | 의뢰번호는 처음 확정할 때 발급되고, 확정 시점의 기준 데이터로 조건 구성이 정해진다. 이후에도 의뢰는 `작성 중`이며 의뢰 내용·제품·조건·Case를 준비한다. |

`의뢰자 소속 사업부`는 의뢰 내용의 의뢰자 정보이며, 제품 분류의 제품 사업부와 별도 정보다. 의뢰자 소속 사업부는 작성자 정보를 설명할 뿐 PMS 목록, 해석 범위 또는 제품 분류의 선택을 정하지 않는다.

#### 의뢰 내용: 정보 묶음과 조건부 관계

의뢰 내용은 의뢰자 정보와 의뢰 개요로 나눈다. 의뢰자 정보와 제품 분류에 의존하지 않는 공통 개요는 의뢰 대상 확정과 별도로 작성할 수 있다. 다만 개발 프로젝트 정보는 제품 분류의 제품 사업부가 정해진 뒤에 작성·확인하며, 제출하려면 그 사업부와 연결한 PMS 정보를 갖춰야 한다.

| 정보 묶음 | 포함 정보 | 관계와 제출 전 확인 |
|---|---|---|
| 의뢰자 정보 | 의뢰자 소속 사업부, 부서, 요청자, 직급 | 모두 필수다. 소속 사업부는 제품 사업부와 다른 독립 정보로 유지한다. |
| 의뢰 유형 | 개발 프로젝트, 품질 개선, 필드 이슈, 선행 검토 또는 기타(직접 입력) | 필수이며, 개발 프로젝트 여부가 PMS·개발 등급·NPI 단계의 필요 여부를 정한다. |
| 개발 프로젝트 정보 | 프로젝트명(PMS), 자동 PMS 정보(PMS Project Code·Region), 개발 등급, NPI 단계 | 개발 프로젝트일 때만 적용한다. 제품 사업부에 해당하는 PMS 프로젝트를 Project 또는 Rep Model로 찾아 하나 고르고, 선택 뒤 자동 PMS 정보가 채워진다. 프로젝트를 고르면 개발 등급과 NPI 단계도 필수가 된다. AIDC는 PMS 프로젝트가 없으므로 개발 프로젝트 의뢰를 만들 수 없다. 개발 프로젝트 의뢰가 AIDC로 제품 분류를 바꾸면, 의뢰 유형을 비개발 유형으로 바꾸기 전에는 다시 확정하거나 제출할 수 없다. PMS 기준 데이터에서 CAC는 제품 분류의 SAC에 대응한다. |
| 비개발 프로젝트 유형 | 품질 개선, 필드 이슈, 선행 검토 또는 기타(직접 입력) | PMS 프로젝트·자동 PMS 정보·개발 등급·NPI 단계는 적용하지 않는다. `기타`는 의뢰 유형을 직접 입력한다. |
| 의뢰 개요 공통 정보 | 모델명(Model Suffix), 희망 완료일, 해석을 요청하게 된 배경, 해석으로 확인하고 싶은 내용, 결과 활용 목적 | 모델명·희망 완료일·배경·확인 내용은 필수이고 결과 활용 목적은 선택이다. 희망 완료일은 의뢰 요청일보다 앞설 수 없다. |
| 자동 정보 | 의뢰 제목, 의뢰 요청일 | 제목은 `[해석유형] 모델명`이며 해석유형 또는 모델명이 바뀌면 자동으로 다시 계산한다. 요청일은 처음 제출한 날이며 제출 전에는 오늘로 본다. |

의뢰 유형과 관계없이 의뢰자 정보와 의뢰 개요 공통 정보는 유지한다. 개발 프로젝트와 비개발 프로젝트 유형의 구분은 PMS 관련 정보의 적용 여부만 정하며, 각 선택지의 값이나 입력 방식은 정하지 않는다.

#### 확정·변경 영향과 제출 경계

의뢰 대상은 `작성 중`, `보완 필요`, `해석 중 보완 필요`에서만 바꾸어 다시 확정할 수 있다. 처음 발급한 의뢰번호는 다시 확정해도 유지한다. 일반 `해석 진행 중`의 대상·내용 변경은 2.2.1의 진행 중 변경 요청으로만 제안하며, 담당자가 수락할 때 새 의뢰서 버전으로 반영한다. 취소 요청 대기와 관리자 확인 대기 등 2.2.1이 정한 차단 경계는 그대로 적용한다.

| 바뀌는 정보 | 즉시 다시 보는 정보 | 확정·제출에 미치는 영향 |
|---|---|---|
| 제품 분류 | 선택한 PMS 프로젝트와 자동 PMS 정보(PMS Project Code·Region)를 비운다. 개발 프로젝트이면 새 제품 사업부의 PMS 프로젝트를 다시 선택하고, 개발 등급·NPI 단계도 다시 확인한다. AIDC로 바뀌면 의뢰 유형을 비개발 유형으로 바꾸기 전에는 다시 확정하거나 제출할 수 없다. RAC Window가 아니게 되면 해석 범위·해석 요청 방식·상황 설명을 비활성으로 보존하고, RAC Window가 되면 해석 범위를 다시 확인한다. 의뢰자 소속 사업부는 이 변경으로 바꾸지 않는다. | 다시 확정하면 그 시점의 제품 분류·해석유형별 조건 매핑 등 기준 데이터를 적용한다. RAC Window로 다시 적용되면 `실내·실외 모두`일 때 요청 방식·상황 설명도 다시 확인한다. 조건 구성·활성 조건·Case와 의뢰 내용의 제출 조건을 2.2.1에 따라 다시 확인한다. |
| 해석유형 | 제품 분류가 유지되면 PMS 선택과 RAC Window 해석 범위는 유지한다. PCB발열이 아니게 되면 냉각 방식을 비활성으로 보존하고, PCB발열이 되면 냉각 방식을 다시 확인한다. | 다시 확정한 시점의 기준 데이터와 새 조건 구성에 맞춰 조건·Case·제출 준비를 다시 확인한다. |
| 해석 범위 | RAC Window 여부와 선택값을 다시 확인한다. `실내·실외 모두`이면 해석 요청 방식과 상황 설명도 다시 확인한다. 다른 범위로 바뀌면 두 값은 비활성으로 보존한다. | 해석유형과 제품 분류가 유지되는 한 PMS에는 직접 영향을 주지 않는다. 조건·Case에 미치는 상세 영향은 후속 조건·Case 작업에서 다룬다. |
| 냉각 방식 | PCB발열일 때의 선택값과, 수랭식이면 적용되는 PCB 냉매 조건을 다시 확인한다. | 활성 조건과 Case 재확인 책임은 2.2.1을 따른다. 냉매 조건의 세부 구조는 여기서 정하지 않는다. |
| 의뢰 유형 | 개발 프로젝트 여부와 PMS·자동 PMS 정보·개발 등급·NPI 단계의 필요 여부를 다시 확인한다. 개발 프로젝트가 아닌 유형으로 바꾸면 이 값들은 비활성으로 보존한다. | 개발 프로젝트로 되돌리면 해당 제품 사업부 PMS 프로젝트와 개발 등급·NPI 단계를 다시 확인해 갖춰야 하며, AIDC이면 이 의뢰 유형으로 진행할 수 없다. |
| 모델명 | 의뢰 제목을 자동으로 다시 계산한다. | 의뢰 내용의 공통 필수 항목과 제목 형식을 다시 확인한다. |

제출(재제출 포함)과 진행 중 변경 요청의 변경안은 의뢰 대상이 확정되어 있고, 의뢰 내용의 필수 항목을 모두 갖춰야 한다. 해석 범위가 `실내·실외 모두`이면 해석 요청 방식과 상황 설명도 갖춰야 한다. 개발 프로젝트라면 해당 제품 사업부 PMS 프로젝트, 개발 등급, NPI 단계를 모두 갖춰야 하며, AIDC는 개발 프로젝트 유형으로 제출할 수 없다. 이는 업무정의서 8장의 제출 조건이며, 대상·내용 외 제품·조건·Case 조건은 이 절에서 상세화하거나 대신 판정하지 않는다.

설치 조건 세부와 CAD 전달 방식은 `확정 필요`이므로 이 절에서 입력 구조나 전달 수단을 정하지 않는다. Case 재확인의 저장 방식(`G-28`)과 재배정 뒤 처리자(`G-30`, `G-31`)도 이 정보 구조에서 새로 정하지 않는다.

### 해석 제품·형상 축의 정보 구조 (2.2.3)

이 절은 해석 제품을 총조립 형상으로 식별하고, Base·비교 제품의 관계를 Case 입력 전제인 형상 축으로 연결한다. 작성·보완·진행 중 변경의 수정 경계와 원본 변경 뒤 재확인 책임은 2.2.1을 따른다. 제품명 입력 컨트롤, CAD 전달 수단, Case의 상세 구성·저장·재확인 저장 방식은 여기서 정하지 않는다.

#### 제품 목록: Base와 비교의 관계

해석 제품은 해석에 쓰는 **총조립 형상**의 목록이다. Base 제품은 기준 총조립 형상으로 정확히 1개이며, 비교 제품은 Base와 차이가 있는 총조립 형상을 0개 이상 둘 수 있다. 조립 상태의 차이를 같은 제품의 부가 설명으로 처리하지 않고, 서로 다른 총조립 형상으로 식별한다.

| 구분 | 개수와 역할 | 형상 식별과 필요한 정보 |
|---|---|---|
| Base 제품 | 정확히 1개. 비교 판단의 기준이 되는 총조립 형상이다. | 제품명과 이 총조립 형상을 식별하는 도면번호를 갖춘다. |
| 비교 제품 | 0개 이상. 각 제품은 Base 대비 차이를 설명한다. | 제품명, 자기 총조립 형상을 식별하는 도면번호, Base 대비 차이 설명을 갖춘다. 비교 제품끼리의 차이가 아니라 항상 Base와의 차이를 설명한다. |

부품의 각도·위치·배치(Arrangement)처럼 조립 상태가 달라지면 서로 다른 총조립 형상이다. 따라서 각 형상에는 서로 다른 도면번호를 사용하고, 비교 제품의 Base 대비 차이 설명에도 그 차이를 남긴다.

#### 총조립 도면번호의 경계

도면번호는 제품에 딸린 일반 참조값이 아니라, 해석에 사용하는 총조립 형상을 식별하는 값이다. 각 제품의 도면번호에는 아래 경계를 함께 적용한다.

| 확인 항목 | 적용 규칙 |
|---|---|
| 식별 대상 | Base와 모든 비교 제품은 해석에 쓰는 총조립 형상을 식별하는 도면번호를 사용한다. 단품·부품·하위 조립품 도면번호는 사용할 수 없다. |
| 형식 | 도면번호는 영문·숫자·하이픈으로만 구성한다. |
| 중복 | 제품끼리 같은 도면번호를 사용할 수 없다. 같은 도면번호로 형상만 다르게 비교할 수 없으며, 조립 상태가 다르면 별도 도면번호가 필요하다. |
| 임시값 | 앱에서 임시 도면번호를 새로 만들지 않는다. 사내에 이미 존재하는 임시 도면번호는 총조립 형상을 식별하고 형식·중복 금지 조건을 충족하면 사용할 수 있다. 도면번호의 존재 여부를 앱에서 확인할 수 없으므로, 의뢰자가 임의의 도면번호를 만들어 입력하는 데 쓰지 않는다. |

CAD 전달 방식은 `확정 필요`이다. 그러므로 도면번호로 총조립 형상을 식별하는 규칙만 여기서 다루며, CAD의 업로드·링크·외부 연동 등 전달 수단이나 이를 전제로 한 입력은 정하지 않는다.

#### 제품 순서와 형상 축

Base와 비교 제품을 포함한 제품 목록의 순서로 형상 축 `1..N`을 만든다. 형상 축의 각 위치는 하나의 제품과 그 제품의 총조립 형상에 대응하며, Case에서 선택할 형상 단위가 된다. 사용자가 지정한 제품명은 형상 축을 만들거나 표시할 때 바꾸지 않고 보존한다.

```text
Base 제품 1개 + 비교 제품 0개 이상
        │  (제품 순서)
        └────────────→ 형상 1 .. N → Case에서 선택하는 형상 단위
```

이 절은 형상 축이 Case 입력의 전제임을 정의할 뿐이다. 형상과 활성 조건 패키지를 어떤 조합으로 구성하는지, 모든 형상을 어떻게 사용했는지, 중복 Case를 어떻게 판단하는지와 재확인 사실의 저장 방식은 2.2.7 및 `G-28`에서 다룬다.

#### 제품 변경의 재확인과 제출 경계

제품의 추가·삭제·변경에는 Base·비교 관계, 총조립 도면번호, 형상 축을 함께 다시 대조한다. `작성 중`, `보완 필요`, `해석 중 보완 필요`에서는 의뢰자가 제품 정보를 직접 고칠 수 있다. 일반 `해석 진행 중`에서는 원 의뢰서를 직접 고치지 않고, 제출 조건을 충족한 변경안과 변경 사유를 진행 중 변경 요청으로 낸다. 취소 요청 대기와 관리자 확인 대기 등 2.2.1의 차단 경계도 그대로 적용한다.

| 제품 원본의 변경 | 즉시 다시 보는 제품·형상 정보 | Case·제출 준비에 미치는 영향 |
|---|---|---|
| Base 제품 변경 또는 삭제·교체 | Base가 정확히 1개인지, 새 Base의 총조립 도면번호와 모든 비교 제품의 Base 대비 차이 설명을 다시 확인한다. | 형상 축을 다시 확인하고, 바뀐 기준 형상에 맞춰 필요한 Case 조합과 모든 형상 사용 여부를 다시 확인한다. 제품·Case 제출 조건을 다시 대조한다. |
| 비교 제품 추가·삭제·변경 | 비교 제품마다 총조립 도면번호와 Base 대비 차이 설명을 다시 확인하고, 도면번호의 형식·중복 금지를 전체 제품 목록에 다시 적용한다. | 형상 축을 다시 확인하고, 필요한 Case 조합과 모든 형상 사용 여부를 다시 확인한다. 제품·Case 제출 조건을 다시 대조한다. |
| 조립 상태 또는 도면번호 변경 | 변경 후 형상이 별도 총조립 형상인지, 도면번호가 그 형상을 식별하는지와 제품명 보존을 다시 확인한다. | 형상 축을 다시 확인하고, 기존 Case의 형상 선택이 현재 축과 맞는지 다시 확인한다. Case 상세 구성·저장 방식은 이 절에서 정하지 않는다. |

제출(재제출 포함)과 진행 중 변경 요청의 변경안은 Base 제품이 정확히 1개이고, 모든 제품의 도면번호가 총조립 형상을 식별하며 형식에 맞고 중복되지 않아야 한다. 단품·부품·하위 조립품 도면번호는 사용할 수 없다. 사내에 이미 존재하는 임시 도면번호는 이 조건을 충족하면 사용할 수 있지만, 앱에서 새로 만들거나 임의로 입력할 수는 없다. 비교 제품마다 Base 대비 차이 설명이 있어야 한다. 형상 축 변경 뒤에는 2.2.1의 재확인 책임에 따라 Case를 다시 확인하며, Case 자체의 구성·저장·재확인 저장 방식은 2.2.7과 `G-28`에서 정한다.

### 해석조건의 공통 구조와 적용 매핑 (2.2.4)

이 절은 확정한 해석유형이 어떤 조건 그룹을 적용하는지, 적용된 조건이 어떻게 활성 조건 패키지와 Case 재확인으로 이어지는지를 정의한다. 각 조건군의 개별 필드·의존 관계·반복 입력은 2.2.5와 2.2.6에서, Case의 상세 구성·저장·재확인 저장 방식은 2.2.7과 `G-28`에서 다룬다. 따라서 이 절은 최종 화면, 입력 컨트롤, 설치 조건 세부, CAD 전달 수단 또는 조건군별 상세 검증을 정하지 않는다.

#### 조건 구성에서 활성 조건까지

의뢰 대상을 확정하면 그 시점의 해석유형별 조건 매핑으로 **조건 구성**이 정해진다. 조건 구성은 조건 그룹, 적용 필드, 필수·선택 여부의 조합이다. 의뢰자는 이 구성에 따라 조건을 준비하고, 실제로 적용되는 것을 **활성 조건**으로 만든다. 활성 조건 패키지는 형상 축과 함께 이후 Case에서 선택하는 전제다.

```text
의뢰 대상 확정
  → 해석유형별 조건 매핑
  → 조건 구성(그룹 · 적용 필드 · 필수/선택 여부)
  → 활성 조건과 조건 패키지
  → 형상 축과의 필요한 조합 확인
  → Case 재확인 · 제출 준비
```

해석유형별 조건 매핑은 확정 시점의 기준 데이터다. 제품 분류 또는 해석유형을 바꿔 다시 확정하면 2.2.1의 원본 변경 뒤 재확인 원칙에 따라 새 조건 구성과 활성 조건 패키지를 다시 보고, 그 영향이 있는 Case와 제출 준비를 다시 확인한다. 조건 패키지를 추가·삭제·수정해도 확정된 조건 구성 자체는 유지하지만, 활성 조건의 현재 상태, 필요한 Case 조합, 모든 값 사용 여부와 조건·Case 제출 조건을 다시 대조한다. 이 절은 Case 재확인이 필요하다는 책임만 연결하며, 재확인 사실의 저장 방법은 `G-28`이 확정될 때까지 정하지 않는다.

#### 매핑 기호와 활성 상태

| 기호 | 조건 구성에서의 의미 | 활성 조건·제출에 연결되는 원칙 |
|---|---|---|
| `●` | 필수 조건이다. | `없음`으로 건너뛸 수 없다. 활성 조건으로 준비하고 필수 내부 입력을 갖춰야 제출할 수 있다. 값이 모르면 `모름`으로 기록할 수 있으며 이는 입력을 채운 것으로 본다. `없음` 선택지를 표시·비활성화·제외하는 방식은 이 정보 구조에서 정하지 않는다. |
| `○` | 선택 조건이다. | 사용 또는 미사용을 명시한다. 미사용이면 활성 조건과 Case에서 제외한다. 사용 중 허용된 `없음`은 활성 조건 패키지의 유효한 대안으로 남아 해당 Case에서 조건이 없는 상태를 비교한다. |
| `—` | 해당 해석유형에 적용하지 않는 조건이다. | 이 의뢰의 조건 구성·활성 조건·Case 선택 대상에 넣지 않는다. 기존 값이 있더라도 새 유형에 적용하지 않는 비활성 값으로 보존하는 원칙은 2.2.1을 따른다. |

`없음`, 빈칸(누락), 미사용은 같은 상태가 아니다. `없음`은 사용 중인 `○` 조건에서 해당 조건이 없는 Case 대안을 명시하는 유효 상태이고, 미사용은 그 선택 조건군 전체를 이번 의뢰와 모든 Case에 적용하지 않는 상태다. `●` 조건은 `없음`을 선택해 건너뛸 수 없다. 어느 조건·필드에 `없음`을 둘 수 있는지와 선택 조건의 내부 입력 구조는 각 조건군의 업무정의서 조건 사전을 따른다.

`없음` 또는 미사용으로 바꿔도 이미 입력한 값은 지우지 않고 보존한다. 미사용 값은 활성 조건과 Case에서 제외한다. 반면 사용 중인 `○` 조건의 허용된 `없음`은 활성 패키지에 남아 Case에서 선택한다. 해석유형 변경 등으로 새 조건 구성에 적용하지 않게 된 값은 비활성으로 보존하고, 다시 적용되면 현재 조건 구성에 맞는지 재확인한다.

#### 반복 단위와 Case의 경계

조건 그룹 안에는 서로 다른 세 반복 단위가 있다. 반복의 위치를 구분해, 내부 입력을 늘린 것과 해석 실행 단위를 늘린 것을 혼동하지 않는다.

```text
조건 그룹
  └─ 조건 패키지 1..N ── Case에서 비교하는 단위
       └─ 물리적 대상 1..N ── 패키지 안의 실제 대상
            └─ 측정점·소자 1..N ── 대상 안의 데이터
```

조건 패키지는 같은 조건 그룹의 대안을 반복해 만든 세트이며, Case에서 비교하는 조건 단위다. 패키지 안의 물리적 대상과 그 대상 안의 측정점·소자는 각각 그보다 안쪽의 반복 단위다. 따라서 물리적 대상, 측정점 또는 소자를 추가·삭제·수정하는 것만으로 새 조건 패키지나 새 Case가 생기지 않는다. 반대로 패키지의 활성 상태 또는 패키지 자체가 바뀌면 2.2.1의 재확인 책임에 따라 Case와 제출 준비를 다시 대조한다. 필터 패키지 안 물리적 필터·측정점처럼 조건군별 예시와 반복 규칙은 2.2.5, PCB 소자 등 특수 조건군의 상세는 2.2.6에서 다룬다.

측정·판정 기준은 패키지·물리적 대상·측정점과 다른 공통 단위다. 현재 정의된 경우 의뢰 전체에 하나를 적용해 모든 Case가 같은 기준을 쓴다. 측정·판정 기준의 필수 여부, 표준값, `모름`일 때의 추가 처리나 상세 입력 구조는 `G-22` 및 업무정의서의 추후 정의 상태를 넘어서 이 절에서 정하지 않는다.

#### 값 상태와 제출 준비

모든 조건 필드는 다음 값 상태를 구분해 현재 입력 책임과 활성 여부를 읽는다.

| 값 상태 | 공통 의미 | 제출 준비에서의 처리 경계 |
|---|---|---|
| 입력됨 | 값이 있다. | 적용되는 필수 내부 입력인지 확인한다. |
| 누락 | 아직 입력하지 않았다. | 필수 또는 사용하기로 한 선택 조건의 필수 내부 입력이면 제출 조건을 충족하지 않는다. 별도 `생략` 상태나 선택지를 두지 않으므로 입력하지 않은 값은 모두 누락이다. |
| 모름 | 값을 모른다. | 값 상태로 기록할 수 있으며 칸을 채운 것으로 본다. 필수 칸이 `모름`이어도 제출을 막지 않는다. 담당자 확인 등 그 밖의 처리는 `G-21`과 업무정의서의 추후 정의 상태를 유지한다. |
| 없음 | 해당 조건이 없다고 명시했다. | 허용되는 `○` 조건·필드에서만 유효한 상태다. 해당 조건 패키지는 활성 상태로 남아 Case에서 선택하며, 그 Case에서 조건이 없는 대안을 뜻한다. `●` 조건에는 사용할 수 없다. 선택지를 어떻게 표현할지는 이 정보 구조에서 정하지 않는다. |

제출(재제출 포함)과 진행 중 변경 요청의 변경안은 필수(`●`) 조건, 사용하기로 한 선택(`○`) 조건의 필수 내부 필드, 조건부 필수, 조건 패키지 중복 금지와 Case 관련 조건을 함께 충족해야 한다. 조건 변경은 Case 재확인과 제출 준비에 영향을 주지만, 어떤 형상과 활성 조건 패키지를 한 Case에 조합할지, Case 중복·모든 값 사용·저장 방식은 2.2.7에서 다룬다. 이로써 2.2.1의 원본 변경 뒤 재확인 원칙을 따르면서도 이 절에서 Case 상세 규칙을 앞당겨 정하지 않는다.

### 일반 조건군의 정보 구조 (2.2.5)

이 절은 운전, 공간 환경, 취출 공기, 열교환기, 필터, 설치 조건의 적용 관계와 내부 반복 경계를 정의한다. 조건 그룹을 사용할지와 패키지 안의 값을 어떻게 구성할지는 구분한다. 조건 패키지는 같은 그룹의 대안을 나타내는 Case 비교 단위이고, 패키지 안 팬·필터·측정점 등은 그 패키지의 내부 구성이다. 내부 구성만 추가·삭제·수정해서 새 Case가 생기지는 않는다. 어떤 형상과 활성 패키지를 Case로 조합할지, 중복·모든 값 사용·재확인 저장 방식은 2.2.7과 `G-28`에서 다룬다.

#### 운전 조건: 대안 패키지와 동시 팬 구성

운전은 기류 패턴, 풍량, 이슬맺힘, 열교환기 유속 프로파일, 기류 도달 거리, PDB, 실사용 해석, 집진해석, PCB발열에서 `●`이고, 다상유동·냉매누설에서만 `○`이다. `●`인 유형은 운전 조건 전체를 `없음`으로 건너뛸 수 없다. `○`인 유형은 조건군 전체를 미사용으로 정해 Case에서 제외하거나, `운전 조건 없음`을 활성 패키지의 대안으로 선택해 해당 Case에서 운전 조건이 없는 상태를 비교할 수 있다. 이 선택은 패키지 내부에 `없음` 값을 넣는 것과 구분한다.

운전 조건 패키지는 서로 비교할 **운전 대안**이다. 서로 다른 운전 대안이면 `운전 1`, `운전 2`처럼 패키지를 반복한다. 반면 한 운전에서 동시에 도는 여러 팬은 하나의 운전 패키지 안에 둔다. 즉, 팬을 더 넣는 것은 운전 대안을 하나 더 만드는 일이 아니며 새 Case를 만들지 않는다.

| 운전 패키지의 판단 순서 | 적용 관계 |
|---|---|
| RPM을 해석에 쓰는 경우 | 팬 개수(1~10)와 팬 회전수 설정 방식이 필요하다. `모든 팬 동일`이면 공통 RPM을, `팬별 설정`이면 활성 팬별 RPM을 받는다. RPM 숫자가 우연히 같아도 팬별 설정을 동일 설정으로 바꾸지 않는다. 팬 위치는 팬별 설정일 때만 의뢰자가 말한 표현 그대로 기록한다. |
| 제품 풍량을 입력한 경우 | 제품 풍량은 CMM으로 입력하며, 풍량 활용 목적은 반드시 `해석에 반영 요청` 또는 `참고 정보로 제공` 중 하나다. |
| 풍량만 있고 `해석에 반영 요청`인 경우 | 해석에는 풍량을 쓰고 팬 개수는 무시한다. 이 경우 팬 개수와 팬 회전수 설정 방식도 받지 않는다(`G-23`). |
| RPM과 풍량이 모두 있는 경우 | 풍량을 해석에 반영 요청하면 풍량을 쓰고 RPM은 참고 정보다. 풍량을 참고 정보로 제공하면 RPM을 쓰고 풍량은 참고 정보다. 둘의 수치가 달라도 오류가 아니다. |
| 풍량만 있고 `참고 정보로 제공`인 경우 | 허용하지 않는다. RPM이 필요하다. |
| RPM과 풍량이 모두 없는 경우 | 운전이 `●`이면 불가하다. 운전이 `○`이면 운전 조건을 적용하지 않을지를 정해야 한다. |

이 관계는 패키지마다 독립적으로 적용한다. 풍량 활용 목적은 풍량을 입력한 경우에만 열리는 조건부 필드이고, 팬 위치는 `팬별 설정`일 때만 열리는 조건부 필드다. 제품 분류의 RAC Window 해석 범위·요청 방식은 실제 RPM·풍량을 대신 정하지 않으므로 운전 조건과 구분한다.

#### 공간 환경·취출 공기: 해석유형별 필드와 패키지

공간 환경과 취출 공기는 각각 조건 패키지를 반복해 대안을 만든다. 한 패키지 안에는 해당 해석유형에 매핑된 필드만 둔다. 패키지 반복은 대안의 반복이며, 온도·습도·압력처럼 패키지 안 필드를 추가·변경하는 일은 대안을 새로 만들지 않는다.

| 조건군·필드 | `●` 적용 해석유형 | `○` 적용 해석유형 | `없음` 허용 및 미적용 경계 |
|---|---|---|---|
| 공간 온도 | 이슬맺힘, PDB, 실사용 해석, PCB발열 | 기류 패턴, 기류 도달 거리 | `○`이면 값 또는 `없음`이다. `●`에는 `없음`을 둘 수 없다. 표에 없는 유형에는 적용하지 않는다. |
| 공간 상대습도(RH) | 이슬맺힘 | 없음 | 이슬맺힘에서만 적용하며 필수다. 다른 유형에는 적용하지 않는다. |
| 입구·출구 압력 | 없음 | 기류 패턴, 풍량, 열교환기 유속 프로파일 | 공간 압력이 `○`인 경우 각 값 또는 `없음`이다. 다른 유형에는 적용하지 않는다. |
| 취출 온도 | 이슬맺힘, PDB, 실사용 해석 | 기류 패턴, 기류 도달 거리, PCB발열 | `○`이면 값 또는 `없음`이다. 표에 없는 유형에는 적용하지 않는다. |
| 취출 상대습도(RH) | 이슬맺힘 | 없음 | 이슬맺힘에서만 적용하며 `없음`을 둘 수 없다. 다른 유형에는 적용하지 않는다. |

선택(`○`) 조건군을 미사용으로 정하면 그 조건군은 활성 조건과 Case에서 제외한다. 반대로 사용 중인 공간·취출 패키지 안에서 위 표가 허용하는 개별 필드를 `없음`으로 표시하면, 그 패키지는 활성 조건으로 남아 Case에서 선택한다. 이 Case는 해당 온도·압력 조건이 없는 대안을 비교하며, 조건군 전체 미사용과 다르다(`G-32`).

#### 열교환기: Catalog 사양과 필터의 분리

열교환기는 이슬맺힘과 열교환기 유속 프로파일에서 `●`이고, 그 밖의 지원 해석유형에서는 `○`이다. 사용 중인 열교환기 패키지는 사양 대안으로 반복한다. 유형은 `Fin&Tube` 또는 `Micro-Channel`이며, 유형 자체에 `없음` 선택지를 두지 않는다. `○`인 해석유형에서만 `열교환기 없음`을 활성 패키지의 대안으로 선택할 수 있고, 이 대안은 Case에서 열교환기가 없는 상태를 비교한다. `●`인 유형은 그렇게 건너뛸 수 없다.

| 사양 의존 관계 | 적용 규칙 |
|---|---|
| 관 직경(Pi) 또는 채널 폭 → 유형 | 관 직경 값이 `W`로 시작하면 Micro-Channel로 분류한다. |
| Micro-Channel → Fin type | Fin type은 Flat 계열(`Flat(MCE)`, `Flat(MCC)`)로 고정되며 관 직경에 따라 하나로 정해진다. |
| 관 직경·Fin type·열 수·FPI/FPDM | 네 값의 조합은 확정 시점의 열교환기 Catalog에 등록된 실제 조합이어야 한다. 비표준 표시는 사용 제한이 아니며, Catalog 원본 표기를 그대로 사용한다(`G-13`, 9장). |

열교환기는 필터와 별도 조건군이다. 열교환기 사양 패키지를 바꾸거나 `열교환기 없음`을 선택한 사실만으로 필터의 사용 여부·필터 패키지·물리적 필터를 대신 정하지 않는다. `열교환기 없음` 대안에는 Catalog 사양 조합을 적용하지 않는다. 사양 또는 `없음` 대안의 변경은 해당 열교환기 패키지의 변경이므로 Case 재확인과 제출 준비에 영향을 준다. 실제 Case의 추가·교체·중복 판단은 2.2.7에서 다룬다.

#### 필터: 사용 여부와 세 단계 반복 경계

필터는 모든 지원 해석유형에서 `○`이다. 이번 의뢰에서 `미사용`, `필터 있음`, `필터 없음`을 구분한다. `미사용`이면 필터 조건은 Case에서 제외한다. `필터 없음`은 활성 조건 패키지의 명시적 대안으로 Case에서 선택하며, 그 Case에서 필터가 없는 상태를 비교한다. 필터 유무는 제품의 고정 속성이 아니라 이번 의뢰의 선택이다.

```text
필터 있음
  └─ 필터 조건 패키지 1..N (`필터 1`, `필터 2`) ── Case에서 비교하는 단위
       └─ 물리적 필터 1..N ── 패키지 안 실제 필터, 패키지마다 개수는 다를 수 있음
            └─ 측정점 1..N ── 각 물리적 필터의 유속(m/s)·압력손실(Pa) 쌍, 1개 이상
```

필터 패키지는 대안과 Case 비교 단위다. 물리적 필터와 그 측정점은 각각 안쪽 반복 단위이므로, 물리적 필터 또는 측정점을 추가·삭제·수정하는 것만으로 새 필터 패키지나 새 Case가 생기지 않는다. `필터 없음` 대안에는 물리적 필터와 측정점을 만들지 않는다. 필터를 미사용으로 정하는 것은 조건군 전체를 적용하지 않는 선택이고, `필터 없음`과 사용 중인 패키지 안의 측정값 상태와는 구분한다. 필터 패키지의 상세 Case 조합과 모든 값 사용 검사는 2.2.7에서 다룬다.

#### 설치 조건: 적용 여부와 단일 시나리오 경계

설치는 기류 도달 거리, PDB, 실사용 해석, 집진해석에서 `●`이고, 나머지 지원 해석유형에서는 `○`이다. `○`이면 설치 조건을 사용할지 정하며, 미사용이면 활성 조건과 Case에서 제외한다. `●`이면 설치 조건을 반드시 설정하고 건너뛸 수 없다. 설치 조건은 단일 시나리오 `설치 1`까지만 둔다.

설치 조건의 세부 필드, 입력 구조, 반복 단위, 요약 기준과 예시 값은 `UX-1`에 따라 `확정 필요`다. 따라서 이 절은 `설치 1` 안에 무엇을 입력하는지, 여러 설치 시나리오를 어떻게 추가하는지, 또는 Case에 어떻게 저장하는지를 정하지 않는다.

### 특수 조건군·공통 측정 기준의 정보 구조 (2.2.6)

이 절은 누설·입자·PCB·다상 조건과 측정·판정 기준의 적용 관계, 의존 관계 및 반복 경계를 정의한다. 조건 패키지는 Case에서 비교하는 단위이고, 패키지 안의 물리적 대상·소자·내부 입력은 그보다 안쪽 단위다. 측정·판정 기준은 이들과 다른 의뢰 전체 공통 단위다. 어떤 형상과 활성 조건 패키지를 Case로 조합할지, 중복·모든 값 사용·재확인 저장 방식은 2.2.7 및 `G-28`에서 다루므로 이 절에서 정하지 않는다.

#### 특수 조건군의 적용과 패키지 경계

해석유형별 조건 매핑에서 누설·입자·PCB·다상은 해당 해석유형에만 `●`으로 적용된다. 해당하지 않는 해석유형에는 `—`이므로 조건 구성·활성 조건·Case 선택 대상에 넣지 않는다. 각 `●` 조건은 `없음`으로 건너뛸 수 없고, 의뢰자는 필요한 내부 입력을 준비한다. 값이 `모름`이면 필수 칸을 채운 것으로 보아 제출을 막지 않으며, 입력하지 않은 값은 별도 `생략`이 아니라 `누락`이다.

| 조건군 | `●` 적용 해석유형 | 조건 패키지 경계 | 패키지 안의 반복·내부 경계 |
|---|---|---|---|
| 누설 | 냉매누설 | `누설 1`, `누설 2`처럼 누설 조건 패키지를 반복할 수 있다. 각 패키지는 냉매 종류, 누설 위치·량·크기/면적·압력·온도·시간과 선택 참고사항을 한 누설 대안으로 묶는다. | 업무정의서가 별도 물리적 대상이나 측정점의 반복을 정의하지 않는다. 따라서 누설 위치 등 패키지 안 필드를 독립 패키지나 독립 Case로 읽지 않는다. |
| 입자 | 집진해석(먼지거동) | `입자 1`, `입자 2`처럼 입자 조건 패키지를 반복할 수 있다. 각 패키지는 입자 밀도·직경·발생 시간·총 발생량을 한 입자 대안으로 묶는다. | 업무정의서가 별도 물리적 대상이나 측정점의 반복을 정의하지 않는다. 패키지 안 필드를 늘리거나 고치는 일만으로 새 패키지나 새 Case가 생기지 않는다. |
| PCB | PCB발열 | PCB 조건은 하나의 패키지다. PCB 이미지, 소자, 접촉저항, 재료물성 및 해당할 때 냉매 조건은 모두 이 단일 PCB 패키지에 속한다. | 소자와 재료물성은 패키지 안의 내부 반복이다. 소자는 여러 개 둘 수 있으나 모든 소자에는 `온도(°C)` 또는 `발열량(W)` 중 같은 기준 하나를 쓴다. 재료물성은 1개 이상이며, 접촉저항은 고려할 때만 내부 입력을 연다. 이 내부 항목을 추가·삭제·수정해도 새 PCB 패키지나 새 Case가 생기지 않는다. |
| 다상 | 다상유동 | `다상 1` 등 다상 조건 패키지를 반복할 수 있다. 각 패키지는 냉매(작동유체) 종류, 초기 상태, 질량유량, 입구 상태와 선택 기상·액상 측 값·참고사항을 한 다상 대안으로 묶는다. | 업무정의서가 별도 물리적 대상이나 측정점의 반복을 정의하지 않는다. 패키지 안 필드는 독립 Case 단위가 아니다. |

누설·입자·다상 표의 필드는 모두 자유 입력이며, 자유 입력의 공통 200자 제한을 따른다. 선택 참고사항은 해당 패키지의 내부 입력일 뿐 별도 패키지나 Case 단위가 아니다.

누설·입자·다상 패키지의 추가·삭제·수정과 PCB 단일 패키지의 수정은 조건 패키지 원본 변경이다. 따라서 2.2.1의 기존 책임대로 활성 조건, Case 재확인 및 제출 준비를 다시 대조한다. 다만 그 변경을 어떤 Case 행에 반영하는지, 새 Case가 필요한 조합인지, 재확인 사실을 어떻게 저장하는지는 이 절에서 판단하지 않는다.

#### PCB 냉각 방식과 냉매 조건

PCB 조건의 냉각 방식은 패키지 안에서 고르는 값이 아니라 의뢰 대상에서 PCB발열일 때 정하는 값이다. 따라서 적용 관계는 다음과 같이 고정한다.

```text
해석유형 = PCB발열
  → 의뢰 대상에서 냉각 방식 선택
     ├─ 공랭식: PCB 냉매 조건은 적용하지 않음
     └─ 수랭식: 단일 PCB 패키지 안의 냉매 조건이 적용되며 필수
```

수랭식의 냉매 조건은 냉매 종류, 질량유량, 입구 온도, 입구 압력, 입구 상태(건도/상분율)로 이루어진다. 이는 PCB 냉각을 위한 PCB 패키지 내부 조건이며, 다상유동의 다상 조건과 별개다. 공랭식에서 냉매 조건은 `없음`으로 선택해 건너뛰는 조건이 아니라 적용하지 않는 조건이다. 냉각 방식이 바뀌면 PCB 냉매 조건의 적용 여부와 PCB 패키지의 현재 입력을 다시 확인하고, 2.2.1의 기존 원칙에 따라 활성 조건·Case 재확인·제출 준비의 영향을 다시 대조한다. Case의 상세 조합이나 저장 구조는 정하지 않는다.

#### 패키지·내부 요소·의뢰 전체 공통 기준의 반복 경계

특수 조건군에서도 반복의 위치를 구분한다. 조건 패키지는 비교 단위이지만, 그 안의 물리적 대상·소자·내부 입력은 패키지의 구성이다. 측정·판정 기준은 어느 조건 패키지에도 속하지 않는 의뢰 전체 단위다.

```text
특수 조건군
  ├─ 누설·입자·다상 조건 패키지 1..N ── Case에서 비교하는 단위
  └─ PCB 조건 패키지 1 ──────────────── Case에서 비교하는 단위
       └─ PCB 소자 1..N · 재료물성 1..N ── 패키지 안 내부 요소

의뢰 전체
  └─ 측정·판정 기준 1 ───────────────── 모든 Case에 공통 적용
```

PCB 소자·재료물성처럼 패키지 내부 요소를 추가·삭제·수정하는 것은 패키지의 내용 변경이지 새 조건 패키지나 새 Case의 생성이 아니다. 이는 공통 구조의 물리적 대상·측정점·소자 경계와 같다. 내부 요소가 바뀌면 기존 원칙상 조건 변경의 재확인은 필요하지만, Case 수·조합·중복을 이 절에서 결정하지 않는다.

#### 측정·판정 기준: 의뢰 전체 공통 단위

측정·판정 기준은 현재 아래 해석유형에만 정의되어 있으며, 적용될 때 의뢰 전체에 하나만 둔다. 조건 패키지·물리적 대상·측정점·소자의 반복과 분리해, 의뢰 안의 모든 Case가 같은 최종 기준을 적용한다.

| 해석유형 | 의뢰 전체 공통 기준 |
|---|---|
| 기류 도달 거리 | 기류 측정 유속: 이 유속까지 도달한 거리를 도달 거리로 본다. |
| 실사용 해석 | 기류 속도 또는 온도 측정 위치 |
| PDB | 온도 측정 기준, 기류 속도 기준 |
| PCB발열 | 허용 온도 기준 |

측정·판정 기준은 Case마다 복제하거나 Case 선택 대상으로 만들지 않으며, 기준 안의 항목을 추가·변경해 새 Case를 만들지 않는다. 다른 해석유형에는 이 기준군을 적용하지 않는다.

기준의 필수 여부, 해석팀 표준값, PCB 허용 온도 기준, 표준값을 바꾼 사실의 기록 및 `모름` 뒤의 추가 처리는 `G-22`와 업무정의서 5.3.11의 추후 정의 상태를 그대로 유지한다. 따라서 이 절은 표준값을 제시하거나, 기준을 반드시 입력해야 한다는 규칙, 변경 기록 방식 또는 추가 검토 행동을 새로 정하지 않는다.

측정·판정 기준 표준값은 업무정의서 9장의 기준 데이터이나 값 자체는 추후 정의다. 기준 데이터는 의뢰 대상 확정 시점의 것을 따르며, 이후 변경이 이미 확정한 의뢰의 공통 기준을 Case별로 다르게 바꾸지 않는다.

### Case·재확인·제출의 정보 구조 (2.2.7)

이 절은 4.1·4.5·4.6의 형상 축과 5장의 활성 조건 패키지를 Case 실행 단위로 연결한다. Case는 형상 하나와 활성 조건 패키지의 필요한 조합이며, 의뢰자가 필요한 조합만 직접 구성한다. 모든 가능한 조합을 자동으로 만들지 않는다. 최종 화면, 행 추가 방식, 선택 컨트롤, 검증 문구와 `G-28`의 저장 구조·해시·재확인 저장 방식은 여기서 정하지 않는다.

#### Case 축과 조합 경계

```text
해석 제품 (Base 1 · 비교 제품 0..N)
  └─ 형상 축 1..N ──────────────┐
                                      ├─ Case 1..200 ── 해석 실행 단위
활성 조건 그룹                         │
  └─ 조건 패키지 1..N ───────────┘

의뢰 전체 공통 측정·판정 기준 1 ─────── 모든 Case에 공통 적용
```

| 구분 | Case와의 관계 |
|---|---|
| 형상 축 | Base와 비교 제품의 총조립 형상으로 만든 형상 1..N이다. Case 하나에는 형상 하나를 지정하며, 형상마다 최소 1개 Case가 있어야 한다. |
| 활성 조건 패키지 | 해석유형에 적용되고 현재 사용하는 조건 그룹의 패키지가 Case 비교 축이다. Case마다 활성 조건 그룹별로 해당 Case에 쓸 패키지를 지정한다. |
| 미사용·`없음` 조건 | 미사용으로 정한 선택 조건과 적용하지 않는(`—`) 조건은 Case 선택 대상에서 제외한다. 반면 사용 중인 `○` 조건에서 허용된 `없음`은 활성 조건 패키지의 명시적 대안으로 남아 해당 Case에서 조건이 없는 상태를 비교한다(`G-32`). |
| 패키지 내부 요소 | 물리적 대상·측정점·필터·PCB 소자·재료물성 등은 선택한 패키지의 내용이다. 내부 요소의 추가·삭제·수정만으로 새 조건 패키지나 새 Case를 만들지 않는다. |
| 측정·판정 기준 | 의뢰 전체에 하나를 적용하는 공통 기준이다. Case마다 복제하거나 선택 대상으로 만들지 않으며, 기준 항목의 변경만으로 Case를 만들지 않는다. 필수 여부와 표준값은 `G-22`의 추후 정의 상태를 유지한다. |

활성 조건 패키지는 모두 하나 이상의 Case에서 사용해야 한다. 형상과 각 활성 조건 패키지를 어떻게 조합할지는 의뢰자가 비교 목적에 맞게 정하며, 패키지 안의 여러 물리적 대상·측정점·소자나 의뢰 전체 공통 측정·판정 기준을 곱집합 축으로 늘리지 않는다.

#### Case 구성의 일관성 경계

Case 구성은 아래 업무정의서 6장의 관계를 함께 만족하는지 대조한다. 이는 Case의 정보 구조 경계이며, 입력 방식이나 별도 오류 규칙을 추가하지 않는다.

| 대조 항목 | 유지할 관계 |
|---|---|
| 최소 구성과 상한 | 형상마다 최소 1개 Case가 있고, 의뢰 전체 Case 수는 최대 200개다. |
| 활성 조건 선택 | 모든 Case에는 형상이 있고 활성 조건 그룹의 패키지 선택이 빠지지 않는다. 사용 중인 `○` 조건의 허용된 `없음`도 유효한 패키지 선택이다. |
| 중복 금지 | 형상과 모든 활성 조건 값이 같은 Case를 둘 수 없다. `없음` 대안은 값이 있는 대안과 다른 조건 값이다. |
| 모든 값 사용 | 입력한 모든 형상과 활성 조건 패키지는 최소 한 Case에서 사용한다. `없음` 대안도 활성 패키지로 입력했으면 최소 한 Case에서 사용한다. 패키지 내부의 물리적 대상·측정점·소자와 의뢰 전체 공통 측정·판정 기준은 이 Case 축의 별도 값으로 세지 않는다. |

#### 원본 변경 뒤 Case 재확인

형상 또는 조건 원본이 바뀌면 현재 Case 구성을 다시 확인해야 한다. 형상 축이나 활성 조건 패키지가 추가·삭제·수정되거나, 조건 그룹의 사용 여부·활성 상태가 바뀐 경우에는 없어진 선택을 Case에서 비우고, 현재 형상·활성 조건 패키지 기준으로 최소 구성, 활성 조건 선택, 중복 금지, 모든 값 사용 및 200개 상한을 다시 대조한다. 패키지 내부 요소의 변경은 새 Case를 자동으로 만들지 않지만, 선택된 패키지의 내용 변경이므로 같은 재확인 책임을 발생시킨다.

재확인이 끝나기 전에는 Case 영역이 8장의 Case 제출 조건을 충족한 것으로 보지 않는다. 따라서 제출·재제출은 할 수 없고, 8장의 제출 조건을 적용하는 진행 중 변경 요청의 변경안도 같은 Case 재확인을 마쳐야 한다. 재확인이 필요하다는 업무 흐름만 정의하며, 이를 어떻게 기록·판별·저장하는지는 `G-28`의 확인 필요 상태로 남긴다.

#### 제출 조건과의 연결

제출 준비는 8장의 모든 영역을 함께 대조하는 단계다. 이 절은 그중 Case 영역을 다음 관계로만 연결하며, 측정·판정 기준의 필수 여부, 설치 조건의 세부, CAD 전달 방식 또는 새 검증 규칙은 정하지 않는다.

| 8장 영역 | Case·재확인과의 연결 |
|---|---|
| 해석 제품 | Base 1개, 총조립 형상을 식별하는 유효한 도면번호와 비교 제품의 차이 설명이 형상 축의 전제다. |
| 해석조건·열교환기 | 필수·사용 조건의 입력 완료, 조건부 필수, 조건 패키지 중복 금지와 사양을 선택한 열교환기 패키지의 Catalog 조합은 활성 조건 패키지가 Case 선택 대상이 되기 전의 조건이다. 허용된 `없음` 대안에는 해당 내부 입력이나 Catalog 사양을 요구하지 않는다. |
| Case | 1행 이상, 모든 행의 형상·활성 조건 선택, 중복 없음, 입력한 모든 형상·활성 조건 패키지(허용된 `없음` 대안 포함) 사용 및 재확인 완료를 함께 대조한다. |
| 나머지 제출 영역 | 의뢰 대상·의뢰 내용·희망 완료일·자유 입력은 각자의 8장 조건을 그대로 적용하며, Case 구조가 이를 대체하거나 새 조건을 더하지 않는다. |

### 관리자 화면 범위와 검토·배정 정보 구조 (2.3)

이 절은 2.1의 공통 탐색 안에서 관리자가 처리하거나 관리·조회하는 의뢰에 필요한 정보 경계를 정한다. 목록의 배치, 화면 전환, 버튼·입력 컨트롤 및 검증 문구는 정하지 않는다. 관리자는 한 번 이상 제출된 전체 의뢰를 조회하되 의뢰서 원문을 직접 수정하지 않으며, `검토 중`, 취소 요청 대기, `해석 진행 중(관리자 확인 대기)`, 관리자가 보류한 의뢰만 현재 처리 대상으로 둔다.

#### 관리자 처리 범위와 상세 정보 묶음

아래 표는 현재 처리 대상과 관리·조회 대상을 함께 구분한다. 일반 진행 의뢰도 관리·조회 대상으로 남지만, 현재 처리 대상이라는 뜻은 아니다. 한 번도 제출하지 않은 의뢰와 제출 전 취소 의뢰는 관리자 범위에서 제외하며, 완료·반려·취소는 조회만 한다.

| 관리자 대상 | 처리 책임 | 상세에서 함께 확인할 정보 |
|---|---|---|
| `검토 중` | 검토 단계 보완 요청, 반려 또는 접수·배정 중 하나를 결정한다. | 현재 의뢰서 버전, 이전 버전 대비 변경, 제출 충족 상태, 현재 배정 없음 상태 |
| `해석 진행 중` (관리·조회) | 필요한 때 해석 단계 보완 요청, 재배정 또는 보류를 관리한다. | 현재 의뢰서·Case, 담당자·배정 이력, 진행 중 대기 요청, 보류 여부와 사유 |
| `해석 중 보완 필요` (관리·조회) | 의뢰자의 재제출을 조회하고, 수행 가능 상태에서 재배정한다. | 보완 요청 주체·사유·설명, 재제출 전후 버전, 현재 담당자·배정 이력 |
| `보류` | 관리자가 보류한 경우 현재 처리 대상으로 재개하며, 그 밖의 보류도 수행 가능 상태에서 관리·조회와 재배정 대상이다. | 보류한 사람, 사유 코드·설명, 현재 담당자, 취소 요청 대기 여부 |
| `해석 진행 중(관리자 확인 대기)` | 해석 계속·담당자 배정 또는 재보완 요청을 결정한다. | 관리자가 요청한 보완의 사유·설명, 재제출 버전과 이전 버전 대비 변경, 현재 담당자·배정 이력 |
| 취소 요청 대기 | 취소 요청을 승인하거나 거절한다. | 요청 사유, 요청 직전 상태, 현재 담당자·보류 정보, 취소 요청의 수행자·시각 |

관리자 상세는 아래 정보 묶음 사이의 관계를 보존한다. 의뢰서와 Case는 검토·판단의 근거이고, 상태·대기 요청·배정·사유는 어떤 행위를 할 수 있는지와 다음 처리자를 설명한다.

```text
현재 상태 · 대기 요청 · 현재 버전
  ├─ 의뢰서 원문 · Case · 제출 충족 상태 ── 검토·판단 근거
  ├─ 이전 버전 대비 변경 ─────────────────── 재제출·변경안의 비교 근거
  ├─ 담당자 · 배정 이력 · 보류 정보 ──────── 접수·배정·재배정·재개 근거
  └─ 요청·사유·설명 ─────────────────────── 보완·반려·보류·취소 판단 근거
       └─ 현재 상태와 함께 가능한 관리자 행위 범위를 결정
```

#### 의뢰서·버전·Case·제출 상태의 검토 경계

관리자는 현재 처리 중인 의뢰서 버전을 기준으로 다음 정보 묶음을 읽고 판단한다. 이는 2.2.1~2.2.7의 작성 정보 구조를 반복하지 않는 관리자용 참조 경계다.

| 검토 정보 | 관리자 판단과의 관계 |
|---|---|
| 의뢰 대상·의뢰 내용 | 제품 분류, 해석유형, 해당 시 범위·냉각 방식, 의뢰 배경·확인 내용·결과 활용 목적 등 요청 범위와 목적을 본다. 지원 범위, 보완 또는 반려 판단의 근거가 된다. |
| 해석 제품·조건 | Base·비교 제품과 차이, 총조립 형상, 적용 조건과 패키지 내용을 함께 읽는다. 관리자는 이 내용을 고치지 않고, 정보 부족이면 보완 요청으로 돌린다. |
| Case | 형상과 활성 조건 패키지의 필요한 조합, Case 수·선택 상태와 재확인 필요 여부를 제출된 버전의 일부로 본다. 사용 중인 `○` 조건에서 허용된 `없음`은 활성 Case 대안이며, 미사용과 적용하지 않는(`—`) 조건만 Case 대상에서 제외한다(`G-32`). |
| 제출 충족 상태 | 제출·재제출·진행 중 변경 수락으로 남은 버전이 8장의 제출 조건을 충족해 제출된 사실과, 각 영역의 현재 충족·재확인 필요 상태를 검토에 연결한다. 관리자의 접수 판단이 의뢰서 직접 수정이나 별도 제출 검사 규칙을 대체하지 않는다. |
| 이전 버전 대비 변경 | 제출, 재제출, 진행 중 변경 수락마다 남은 버전을 비교한다. 변경된 요청 범위, 제품·조건·Case 및 재확인 영향은 검토·관리자 확인 판단에 쓰며, 변경이 없더라도 재제출할 수 있다. |

측정·판정 기준은 의뢰 전체 공통 정보로서 현재 값·상태를 다른 의뢰서 정보와 함께 열람할 수 있다. 다만 그 값의 필수 여부나 판정 기준은 `G-22`의 추후 정의 상태를 유지하며, 관리자 정보 구조에서 필수 충족 여부로 확정하거나 표준값을 제시하지 않는다. Case 재확인이 필요하다는 업무 흐름은 보이되, 재확인 사실의 저장·판별 방식은 `G-28` 확인 전까지 노출하지 않는다.

#### 사유·설명과 배정 정보의 경계

보완 요청, 반려, 보류는 사유 코드 하나와 설명을 함께 남긴다. 사유 코드 목록과 판단 기준은 업무정의서 3.7의 검토 대상 상태를 그대로 따르며, 설명에는 길이 제한을 새로 두지 않는다. 취소 요청 거절에는 거절 사유를 남기고, 재배정에는 사유를 남긴다. 접수·배정과 관리자 확인의 해석 계속·담당자 배정에는 담당자 지정이 필수다.

| 배정 정보 | 적용 경계 |
|---|---|
| 현재 담당자와 배정 이력 | 접수·배정, 재배정, 해석 계속·담당자 배정의 결과와 이전·새 담당자 관계를 조회한다. 상태 유지 행위도 이력으로 남는다는 3.4-7을 적용한다. |
| 접수·배정 | `검토 중`에서 담당자 한 명을 지정해 `해석 진행 중`으로 인계한다. |
| 일반 재배정 | `해석 진행 중(관리자 확인 대기 제외)`, `해석 중 보완 필요`, `보류`에서만 한다. 새 담당자는 현재 담당자와 달라야 하며 사유를 남기고 상태는 유지한다. |
| 관리자 확인 뒤 담당자 배정 | `해석 진행 중(관리자 확인 대기)`에서 해석을 계속시킬 담당자를 지정한다. 기존 담당자와 같아도 되며, 일반 재배정과 구분한다. |
| 보류 중 재배정 | 담당자가 보류한 의뢰는 새 담당자가 보류와 재개 책임을 이어받는다. 관리자가 보류한 의뢰는 재배정해도 관리자의 보류로 남는다. |

진행 중 변경 요청 대기 중 재배정한 뒤 변경 수락·거절의 처리자(`G-30`), 담당자가 요청한 해석 단계 보완 뒤 재배정하고 재제출했을 때 해석을 이어갈 처리자(`G-31`)는 미정이다. 이 두 경우에는 관리자 상세의 담당자·배정 정보와 이력은 보되, 다음 처리자를 특정하거나 특정 목록에 넣지 않는다.

#### 상태별 관리자 행위와 차단 경계

| 상태 또는 대기 | 가능한 관리자 행위 | 차단 또는 처리하지 않는 행위 |
|---|---|---|
| `검토 중` | 검토 단계 보완 요청, 반려, 접수·배정 | 해석 단계 관리 행위, 의뢰서 직접 수정 |
| 일반 `해석 진행 중` | 해석 단계 보완 요청, 재배정, 보류 | 진행 중 변경 수락·거절, 결과 등록 등 담당자 행위 |
| `해석 중 보완 필요` | 재배정 | 의뢰자 재제출 전 해석 계속·담당자 배정, 일반 해석 단계 보완 요청 |
| `보류` | 재개, 재배정 | 정보 부족을 보류 사유로 처리, 담당자나 의뢰자의 차단된 행위 대행 |
| `해석 진행 중(관리자 확인 대기)` | 해석 계속·담당자 배정, 재보완 요청 | 일반 재배정, 보류, 새 해석 단계 보완 요청. 담당자의 해석·결과 등록과 의뢰자의 진행 중 변경·취소 요청도 이 대기 동안 차단된다. |
| 취소 요청 대기 | 취소 요청 승인 또는 거절 | 승인·거절 외의 모든 업무 행위와 의뢰서 수정. 거절하면 요청 전 상태와 다음 처리자를 그대로 복원한다. |
| `결과 확인 필요` | 없음(관리·조회) | 취소·취소 요청을 포함한 관리자 업무 행위 |
| `완료`, `반려`, `취소` | 없음(조회만) | 모든 업무 행위 |

해석 단계의 정보 부족은 보류가 아니라 보완 요청으로 처리한다. 취소 요청 승인 때에는 `취소`로 종료하고, 보류 중이었다면 보류 정보도 함께 없어진다. 승인·거절과 상태 유지 행위도 수행자, 이전·이후 상태, 사유, 시각의 이력 관계에 포함한다.

### 담당자 화면 범위와 진행·결과 정보 구조 (2.4)

이 절은 2.1의 공통 탐색 안에서 담당자가 배정받아 해석을 진행하거나 결과를 회신할 때 필요한 정보 경계를 정한다. 목록의 배치, 화면 전환, 버튼·입력 컨트롤, 해석 수행 방법 및 결과 요약의 서식은 정하지 않는다. 관리자의 접수·배정 또는 관리자 확인 뒤 해석 계속·담당자 배정이 끝나면 지정 담당자는 일반 `해석 진행 중` 의뢰를 수신한다. 담당자는 현재 자신에게 배정된 의뢰만 조회하며 의뢰서 원문을 직접 고치지 않는다. 재배정되면 이전 담당자는 해당 의뢰의 조회·재개·처리 범위에서 제외되고, 새 담당자에게만 현재 배정과 그 배정 이력이 이어진다.

#### 담당자 처리 범위와 상세 정보 묶음

담당자의 현재 처리 대상은 본인에게 배정된 일반 `해석 진행 중`, 진행 중 변경 수락 대기, 본인이 보류한 `보류`다. 관리자 확인 대기, 취소 요청 대기, 관리자 보류와 의뢰자의 보완·결과 확인 대기는 처리 대상이 아니라 상태와 이력을 읽는 경계다. `반려`와 배정 전 `취소`는 담당자에게 배정 이력이 없으므로 범위 밖이다.

| 담당자 대상 | 처리 책임 또는 조회 경계 | 상세에서 함께 확인할 정보 |
|---|---|---|
| 본인에게 배정된 일반 `해석 진행 중` | 해석 진행, 해석 단계 보완 요청, 보류, 결과 등록 | 현재 의뢰서·Case·제출 충족 상태, 이전 버전 대비 변경, 현재 상태·대기 요청, 현재 담당자·배정 이력 |
| 진행 중 변경 수락 대기 | 변경안을 수락하거나 거절한다. 보류는 가능하다. | 현재 의뢰서와 별도인 변경 제안 의뢰서, 변경 사유, 이전 의뢰서 대비 변경, 수락·거절 이력 |
| 담당자가 요청한 `해석 중 보완 필요` | 의뢰자의 재제출을 조회·대기한다. | 보완 사유 코드·설명, 요청한 사람·시각, 재제출 전후 의뢰서 버전, 현재 담당자·배정 이력 |
| 본인이 보류한 `보류` | 재개하거나, 관리자 재배정 전까지 보류 상태를 책임진다. | 보류한 사람, 사유 코드·설명, 보류 시점의 상태·대기 요청, 현재 담당자·배정 이력 |
| 관리자 확인 대기·관리자가 보류한 `보류`·취소 요청 대기 | 상태·요청·이력만 조회한다. | 각 대기의 주체와 사유·설명, 현재 담당자·배정 이력, 허용된 다음 처리자 |
| `결과 확인 필요`·`완료` | 의뢰자의 결과 확인 또는 재작업 요청, 완료를 조회한다. | 결과 회차, 현재 결과, 결과 재작업 요청 사유(있을 때) |

담당자 상세는 해석 판단에 쓰는 현재 의뢰 정보와, 지금 할 수 있는 업무 행위를 정하는 진행 정보를 분리해 함께 읽는다. 진행 중 변경의 제안 의뢰서는 아직 현재 의뢰서가 아니며, 수락될 때만 새 의뢰서 버전이 된다.

```text
현재 상태 · 대기 요청 · 현재 배정
  ├─ 현재 의뢰서 · Case · 제출 충족 상태 ───── 해석 착수·보완 판단 근거
  ├─ 이전 버전 대비 변경 ───────────────────── 재제출·수락 뒤 영향 확인
  ├─ 진행 중 변경 제안 · 변경 사유 ─────────── 수락·거절 판단 근거
  ├─ 보완·보류 사유 코드 · 설명 ────────────── 중단·재개 맥락
  ├─ 현재 담당자 · 배정 이력 ───────────────── 인계·재배정·조회 범위
  └─ 결과 회차 · 현재 결과 · 재작업 요청 ───── 결과 회신·재작업 맥락
       └─ 현재 상태와 함께 가능한 담당자 행위 범위를 결정
```

#### 의뢰서·Case·버전·제출 상태의 해석 경계

담당자는 현재 의뢰서 버전을 기준으로 다음 묶음을 해석 판단에 사용한다. 이는 2.2.1~2.2.7의 의뢰자 작성 구조를 반복하지 않는 담당자용 참조 경계이며, 담당자가 이 정보를 수정한다는 뜻은 아니다.

| 해석 판단 정보 | 담당자 화면에서의 관계 |
|---|---|
| 현재 의뢰서·Case | 의뢰 대상·의뢰 내용, Base·비교 제품과 차이, 적용 조건 패키지, 형상과 활성 조건 패키지의 Case 조합을 함께 본다. 해석 착수와 정보 부족 판단의 근거이며, 직접 수정할 수 없다. |
| 제출 충족 상태 | 제출·재제출·진행 중 변경 수락으로 남은 버전이 8장의 제출 조건을 충족해 제출된 사실과, 각 영역의 현재 충족·재확인 필요 상태를 확인한다. 담당자 판단이 별도 제출 검사나 의뢰서 수정을 대신하지 않는다. |
| 이전 버전 대비 변경 | 제출, 재제출, 진행 중 변경 수락 때 남은 버전의 요청 범위·제품·조건·Case 변경을 비교한다. 내용이 바뀌지 않은 재제출도 버전으로 남는다는 경계를 유지한다. |
| 진행 중 변경 제안 | 대기 중에는 현재 의뢰서와 분리해 제안 의뢰서·변경 사유·이전 의뢰서 대비 변경을 확인한다. 수락하면 제안 의뢰서가 새 버전이 되고, 거절하면 원래 의뢰서로 해석을 계속하되 제안과 거절 사유는 이력에 남긴다. |
| 측정·판정 기준과 Case 재확인 | 측정·판정 기준은 의뢰 전체 공통 정보로 현재 값·상태를 열람한다. 다만 기준의 필수 여부나 판정 기준은 `G-22`의 추후 정의 상태를 유지한다. 형상·조건 변경 뒤 Case 재확인이 필요한 흐름은 보이되, 그 저장·판별 방식은 `G-28` 확인 전까지 노출하지 않는다. |

사용 중인 선택(`○`) 조건에서 허용된 `없음`은 활성 조건 패키지의 유효한 Case 대안이다. 미사용과 적용하지 않는(`—`) 조건만 Case 대상에서 제외하며, `●` 조건에는 `없음`을 두지 않는다(`G-32`).

#### 진행·대기·재배정의 행위 경계

보완 요청과 보류에는 사유 코드 하나와 설명을 함께 남긴다. 설명에는 길이 제한을 새로 두지 않는다. 정보 부족은 보류가 아니라 해석 단계 보완 요청으로 처리한다. 모든 상태 변화와 요청, 상태를 유지하는 수락·거절·재배정·보류·재개는 수행자, 이전·이후 상태, 사유와 시각의 이력 관계로 읽는다.

| 상태 또는 대기 | 담당자에게 가능한 행위 | 차단 또는 처리하지 않는 행위 |
|---|---|---|
| 대기 요청과 관리자 확인 대기가 없는 일반 `해석 진행 중` | 해석 진행, 해석 단계 보완 요청, 보류, 결과 요약 등록 | 의뢰서 직접 수정, 진행 중 변경 요청·취소 요청의 대행 |
| 진행 중 변경 수락 대기 | 변경안을 먼저 수락 또는 거절, 보류 | 해석 단계 보완 요청, 결과 등록. 보류 뒤에도 변경안은 대기 상태로 남아 재개 뒤 수락·거절한다. |
| 담당자 요청 `해석 중 보완 필요` | 의뢰자의 재제출을 조회·대기 | 재제출 전 해석 진행·결과 등록·새 보류. 재제출 뒤 일반 `해석 진행 중`의 처리자는 재배정이 없을 때 기존 담당자다. |
| `해석 진행 중(관리자 확인 대기)` | 관리자 결정을 조회·대기 | 해석 진행, 해석 단계 보완 요청, 보류, 결과 등록. 관리자가 해석 계속·담당자 배정 또는 재보완 요청을 처리할 때까지 담당자 업무를 하지 않는다. |
| 본인이 보류한 `보류` | 재개 | 해석 진행, 결과 등록. 재개하면 일반 `해석 진행 중`에서 같은 담당자가 처리한다. |
| 관리자가 보류한 `보류` | 조회·대기 | 재개. 관리자가 재개하면 현재 배정 담당자가 일반 `해석 진행 중`을 처리한다. |
| 취소 요청 대기 | 조회·대기 | 해석, 보완 요청, 보류·재개, 결과 등록을 포함한 모든 담당자 업무 행위. 관리자만 승인·거절할 수 있다. |
| `결과 확인 필요` | 결과 확인 또는 재작업 요청을 조회 | 결과 추가 등록, 취소·취소 요청. 재작업 요청이 오면 같은 담당자가 일반 `해석 진행 중`에서 다시 처리한다. |
| `완료`, `취소` | 조회만 | 모든 업무 행위 |

일반 재배정은 `해석 진행 중(관리자 확인 대기 제외)`, `해석 중 보완 필요`, `보류`에서 관리자가 처리하며 상태는 유지한다. 새 담당자는 현재 담당자와 달라야 하고 사유가 남는다. 담당자가 보류한 의뢰가 재배정되면 새 담당자가 보류와 재개 책임을 이어받지만, 관리자가 보류한 의뢰는 재배정되어도 관리자 보류로 남는다. 관리자 확인 대기에서의 해석 계속·담당자 배정은 일반 재배정과 별도이며 기존 담당자를 다시 지정할 수도 있다.

진행 중 변경 요청 대기와 재배정이 겹친 뒤 수락·거절을 누가 처리하는지(`G-30`), 담당자 요청 보완 뒤 재배정하고 의뢰자가 재제출했을 때 누가 해석을 이어가는지(`G-31`)는 미정이다. 이 두 경우에는 담당자 상세에 현재 담당자·배정 이력·대기 요청을 보되, 다음 처리자를 특정하거나 특정 담당자의 할 일 목록에 넣지 않는다.

#### 결과 등록·재작업 정보 경계

결과는 배정된 담당자가 대기 중인 요청이 없는 일반 `해석 진행 중`에서 요약 텍스트로 등록한다. 결과의 상세 형식이나 별도 산출물 전달 방식은 이 정보 구조에서 정하지 않는다. 등록하면 `결과 확인 필요`가 되고 의뢰자가 다음 처리자다.

| 결과 정보 | 담당자 화면에서의 관계 |
|---|---|
| 결과 회차 | 결과 등록마다 남는 회차이며, 이전 회차는 결과 이력으로 보존한다. |
| 현재 결과 | 마지막으로 등록한 결과다. 현재 결과와 이전 회차를 구분해 의뢰자의 확인·재작업 판단 맥락을 유지한다. |
| 결과 재작업 요청 | 의뢰자가 `결과 확인 필요`에서 남긴 사유를 현재 결과와 함께 확인한다. 요청하면 같은 담당자에게 일반 `해석 진행 중`이 다시 인계되며, 이전 결과는 지우지 않는다. |
| 결과 확인 | 의뢰자가 현재 결과를 확인하면 `완료`가 되고 담당자는 종료 결과를 조회만 한다. |

### 공통 상세·이력·결과·읽기 전용 정보 구조 (2.5)

이 절은 2.1의 `의뢰 상세`를 세 역할이 같은 의뢰를 서로 다른 권한으로 읽는 공통 기준점으로 정의한다. 의뢰자 작성 정보(2.2.1~2.2.7), 관리자 검토·배정 정보(2.3), 담당자 진행·결과 정보(2.4)의 세부 구조를 반복하거나 바꾸지 않는다. 목록 배치, 탭·버튼·비교 방식, 결과 요약의 서식과 화면 전환은 정하지 않는다.

#### 공통 상세의 정보 묶음과 연결

공통 상세는 현재 처리에 필요한 최신 정보와, 그 정보를 현재 상태까지 이르게 한 이전 기록을 분리해 연결한다. `현재`는 행위 판단의 기준이고, 이전 버전·이력·결과 회차는 삭제하거나 현재 정보로 바꾸지 않는 열람 기록이다.

```text
상태 · 대기 요청 · 현재 처리 경계
  ├─ 현재 의뢰서 버전 · 이전 버전 대비 변경 · 제출 충족 상태
  │   └─ 해석 제품 · 조건 · Case · 의뢰 전체 공통 측정·판정 기준
  ├─ 진행 중 변경 제안 · 변경 사유 · 수락·거절 기록
  ├─ 현재 담당자 · 배정 이력 · 보완·보류·취소 요청 정보
  ├─ 결과 회차 · 현재 결과 · 결과 재작업 요청
  └─ 상태 변화·요청·상태 유지 행위 이력
       └─ 역할별 조회 권한과 현재 처리/조회·대기 경계를 함께 결정
```

| 공통 정보 묶음 | 상세에서 유지할 관계 |
|---|---|
| 상태·대기 요청·현재 처리 경계 | 현재 상태와 진행 중 변경·취소 요청·관리자 확인 대기 여부를 함께 읽어, 현재 처리자와 조회·대기 역할을 구분한다. 상태만으로 대기 요청을 생략하지 않으며, 대기 요청이 있을 때의 차단 범위도 함께 남긴다. |
| 현재 의뢰서 버전·이전 버전 대비 변경 | 제출, 재제출, 진행 중 변경 수락으로 남은 마지막 버전을 현재 의뢰서로 연결한다. 이전 버전과의 요청 범위·제품·조건·Case 차이는 비교 근거로 남기며, 내용이 바뀌지 않은 재제출도 버전으로 남는다. |
| 진행 중 변경 제안 | 대기 중인 변경안은 현재 의뢰서와 분리해 제안 의뢰서, 변경 사유, 이전 의뢰서 대비 변경, 요청자·시각과 수락·거절 결과를 연결한다. 수락 때만 제안안이 새 현재 버전이 되며, 거절한 제안안과 거절 사유도 이력에 남는다. |
| Case·제출 충족 상태 | 현재 의뢰서 버전의 형상·활성 조건 패키지 조합과 8장 제출 조건의 충족·재확인 필요 상태를 함께 참조한다. 사용 중인 `○` 조건에서 허용된 `없음`은 활성 Case 대안이고, 미사용과 적용하지 않는(`—`) 조건만 Case에서 제외한다(`G-32`). |
| 담당자·배정 이력 | 현재 담당자와 접수·배정, 일반 재배정, 관리자 확인 뒤 해석 계속·담당자 배정의 이력을 구분해 연결한다. 일반 재배정은 이전 담당자와 다른 새 담당자를 남기고, 관리자 확인 뒤 지정은 기존 담당자와 같을 수 있는 별도 행위다. |
| 보완·보류·취소 요청 정보 | 보완 요청에는 단계·요청 주체·사유 코드·설명, 보류에는 보류 주체·사유 코드·설명, 취소 요청에는 사유·요청 직전 상태·요청자·시각과 승인·거절 결과를 함께 남긴다. |
| 결과 회차·현재 결과 | 결과 등록마다 회차를 남기고 마지막 등록 결과를 현재 결과로 연결한다. 결과 재작업 요청 사유와 그 뒤의 다음 회차를 이전 결과를 지우지 않고 연결하며, 결과 확인은 현재 결과를 확인한 종료 기록으로 남긴다. |

측정·판정 기준은 의뢰 전체 공통 정보로 현재 값·상태를 열람할 수 있으나, 필수 여부·표준값·판정 기준은 `G-22`의 추후 정의 상태로 유지한다. Case 재확인 필요 여부는 보이되, 저장·판별 방식은 `G-28` 확인 전까지 공통 상세에 노출하거나 확정하지 않는다.

#### 역할별 조회와 읽기 전용 경계

공통 상세를 열 수 있는 범위와 상세 안에서 행위를 할 수 있는 범위는 다르다. 같은 소속 부서 의뢰자의 조회와 종료 상태의 열람은 어떤 업무 행위도 열지 않는다.

| 역할 | 공통 상세 조회 범위 | 읽기 전용 또는 범위 밖 경계 |
|---|---|---|
| 의뢰자 | 자기 의뢰 전체와 같은 소속 부서의 다른 의뢰자가 만든 의뢰를 조회한다. 한 번도 제출하지 않은 의뢰와 제출 전 취소 의뢰는 작성자만 조회한다. | 같은 소속 부서의 다른 의뢰는 항상 조회만 한다. 자기 의뢰도 다음 처리자가 다른 역할이면 조회·대기이며, 종료 상태는 조회만 한다. |
| 해석관리자 | 한 번 이상 제출된 전체 의뢰를 조회한다. | 한 번도 제출하지 않은 의뢰와 제출 전 취소 의뢰는 범위 밖이다. 완료·반려·취소는 조회만 한다. |
| 해석담당자 | 현재 본인에게 배정된 의뢰를 조회한다. 종료 뒤에는 배정 이력이 있는 완료와 배정 후 취소를 조회한다. | 재배정된 이전 담당자는 진행 중·보완·보류·결과 확인 등 종료 전 의뢰의 조회·재개·처리 범위에서 제외된다. 새 담당자에게만 현재 배정과 그 배정 이력이 이어진다. 반려와 배정 전 취소는 배정 이력이 없으므로 담당자 범위 밖이다. |

완료·반려·취소는 공통 상세에서 역할의 위 조회 범위 안에서만 열람하는 종료 상태다. 따라서 담당자의 종료 조회 예외는 본인에게 배정 이력이 있었던 완료와 배정 후 취소에만 적용하며, 재배정으로 현재 처리 권한이나 재개 권한이 이전 담당자에게 돌아가는 뜻이 아니다.

#### 현재 처리와 조회·대기 경계

공통 상세는 아래 현재 처리 대상을 할 일로 바꾸지 않는다. 현재 처리자가 아닌 역할에는 같은 정보를 조회·대기 맥락으로 연결하며, 상세에서 허용하지 않은 행위를 제공하지 않는다.

| 상태 또는 대기 | 현재 처리 대상 | 다른 역할의 공통 상세 경계 |
|---|---|---|
| `작성 중` | 의뢰자 | 한 번도 제출하지 않은 의뢰는 작성자만 조회·수정·제출 또는 취소할 수 있으며, 관리자·담당자와 같은 소속 부서 의뢰자는 범위 밖이다. |
| `검토 중` | 관리자 | 의뢰자는 조회·대기한다. |
| `보완 필요` | 의뢰자 | 관리자는 재제출을 조회·대기한다. 의뢰자는 수정·재제출 또는 직접 취소 중 해당 상태에서 허용된 행위만 한다. |
| 일반 `해석 진행 중` | 배정 담당자 | 의뢰자는 진행 상황을 조회하며 대기 요청이 없을 때만 진행 중 변경·취소 요청을 시작할 수 있다. 관리자는 관리·조회한다. |
| 진행 중 변경 수락 대기 | 배정 담당자 | 의뢰자와 관리자는 변경 제안·사유·대기 상태를 조회한다. 담당자는 수락·거절을 먼저 처리해야 하며, 그 전에는 보완 요청과 결과 등록을 할 수 없다. 보류만 병행할 수 있고 변경 요청은 대기한 채로 남는다. |
| `해석 중 보완 필요` | 의뢰자 | 담당자와 관리자는 보완 요청·사유·재제출 전후 버전을 조회한다. 대기 요청이 없을 때 의뢰자는 취소 요청을 시작할 수 있고, 담당자 요청 뒤 재배정이 없으면 기존 담당자가 재제출 뒤 이어서 처리한다. |
| `해석 진행 중(관리자 확인 대기)` | 관리자 | 의뢰자와 담당자는 재제출·보완 요청·이전 버전 대비 변경을 조회·대기한다. 관리자가 해석 계속·담당자 배정 또는 재보완 요청을 마칠 때까지 담당자의 해석 진행·결과 등록과 의뢰자의 진행 중 변경·취소 요청은 차단된다. |
| 담당자가 보류한 `보류` | 보류한 담당자 | 의뢰자와 관리자는 조회·대기한다. 대기 요청이 없을 때 의뢰자는 취소 요청을 시작할 수 있다. 재배정되면 새 담당자에게 보류·재개 책임이 넘어가고 이전 담당자는 범위에서 제외된다. |
| 관리자가 보류한 `보류` | 관리자 | 의뢰자와 담당자는 조회·대기한다. 대기 요청이 없을 때 의뢰자는 취소 요청을 시작할 수 있고, 재배정되어도 관리자 보류와 재개 책임은 유지된다. |
| 취소 요청 대기 | 관리자 | 요청 사유와 요청 직전 상태를 모두 조회·대기한다. 관리자 승인·거절 외 모든 업무 행위와 의뢰서 수정은 모든 역할에서 차단된다. 거절하면 요청 전 상태와 그 상태의 다음 처리 경계를 그대로 따른다. |
| `결과 확인 필요` | 의뢰자 | 현재 결과·이전 회차와 재작업 요청 이력을 조회한다. 의뢰자는 결과 확인 또는 재작업 요청만 판단하고, 관리자와 담당자는 조회한다. |
| `완료`, `반려`, `취소` | 없음 | 역할별 조회 범위 안에서만 조회한다. 어떤 업무 행위도 하지 않는다. |

진행 중 변경 요청 대기와 재배정이 겹친 경우의 수락·거절 처리자(`G-30`), 담당자 요청 해석 단계 보완 뒤 재배정되고 재제출된 경우의 다음 처리자(`G-31`)는 미정이다. 두 경우에도 공통 상세는 현재 상태, 대기 요청, 현재 담당자와 배정 이력을 남기되, 다음 처리자나 특정 역할의 할 일 목록을 임의로 특정하지 않는다.

#### 공통 이력의 기록 경계

공통 이력은 상태 변화뿐 아니라 요청과 상태 유지 행위까지 시간순으로 연결한다. 각 기록에는 수행자, 이전·이후 상태, 사유 또는 설명, 시각을 남긴다. 사유가 없는 행위에는 임의의 사유를 만들지 않는다.

| 이력 종류 | 함께 남기는 정보 |
|---|---|
| 상태 변화 | 수행자, 이전 상태, 이후 상태, 시각과 해당 행위의 사유·설명(있는 경우)을 남긴다. 제출·재제출·보완 요청·반려·결과 등록·결과 확인·결과 재작업 요청과 취소 승인은 상태 변화로 연결한다. |
| 요청과 대기 | 진행 중 변경·취소 요청에는 요청자, 제안 또는 요청 내용·사유, 요청 시각, 대기 여부와 최종 수락·거절 또는 승인·거절 결과를 남긴다. 진행 중 변경이 거절되어도 제안 의뢰서 내용은 이력에 보존한다. |
| 상태 유지 행위 | 재배정, 해석 계속·담당자 배정, 진행 중 변경 수락·거절, 취소 요청 거절은 상태가 유지되어도 수행자, 이전·이후 상태, 사유·설명 또는 지정 정보, 시각을 남긴다. |
| 배정·보류·보완 맥락 | 접수·배정과 재배정의 이전·새 담당자, 보류한 사람과 사유, 보완 요청의 단계·요청자·사유 코드·설명을 연결해 이후 조회자가 인계와 중단 이유를 읽을 수 있게 한다. |
| 결과 이력 | 결과 회차별 등록자·등록 시각·요약과 현재 결과 여부, 결과 재작업 요청 사유와 결과 확인 시각을 연결한다. |

사유 코드 목록과 판단 기준은 업무정의서 3.7·3.8의 검토 대상 규칙을 그대로 따르고, 설명에는 길이 제한을 새로 두지 않는다. 이력은 다음 처리자나 업무 행위 권한을 새로 만들지 않으며, 현재 상태·대기 요청·배정 경계가 허용하는 행위만 공통 상세에 연결한다.

### 화면 목록과 업무 행위 대응 (2.6)

이 절은 2.1~2.5에서 정한 탐색, 작성, 관리자, 담당자 및 공통 상세의 책임을 업무정의서 3.2의 모든 업무 행위에 대조한다. 새 화면·와이어프레임·버튼 배치나 입력 컨트롤을 정하지 않는다. 아래의 `진입`은 행위를 시작할 수 있는 역할별 화면 또는 맥락이고, `처리`는 해당 상세에서 함께 확인할 정보이며, `결과 확인`은 상태 변화 뒤 다음 처리자 또는 조회자가 확인하는 위치다.

#### 화면 목록과 책임 대조

| 화면 또는 정보 구조 | 2.6에서 확인하는 책임 | 다른 구조와의 경계 |
|---|---|---|
| 홈 | 역할별 첫 진입점으로서 지금 처리하거나 확인할 의뢰를 `내 할 일`, `의뢰함`, 또는 의뢰자만의 새 의뢰 시작으로 보낸다. | 특정 의뢰의 판단·입력·결과 확인을 직접 처리하지 않는다. |
| 내 할 일 | 3.5의 현재 처리 대상에서 해당 의뢰 상세로 들어간다. 의뢰자(작성·보완·결과 확인), 관리자(검토·취소 요청·관리자 확인·관리자 보류), 담당자(일반 진행·변경 요청 판단·담당자 보류)의 책임을 구분한다. | 조회만 가능한 의뢰나 다른 역할이 다음 처리자인 의뢰를 행위 책임으로 만들지 않는다. |
| 의뢰함 | 역할의 조회 범위 안에서 의뢰를 찾고 공통 상세로 들어간다. 현재 처리 대상이 아닌 관리 행위의 진입과 결과·종료 상태의 열람도 여기서 가능하다. | `내 할 일`을 대신해 다음 처리자나 우선순위를 정하지 않는다. |
| 의뢰자 작성·보완·변경안 정보 구조 | 의뢰자만 의뢰서를 작성·수정·제출 준비 또는 진행 중 변경안을 준비한다. 작성 중·보완 필요·해석 중 보완 필요의 원 의뢰서와 일반 해석 진행 중의 변경안을 구분한다. | 관리자·담당자는 의뢰서 원문이나 변경안을 직접 수정하지 않는다. |
| 관리자 검토·배정 정보 구조 | 검토, 접수·배정, 해석 단계 관리, 재배정, 관리자 확인, 취소 요청 판단을 위해 의뢰서·Case·버전·사유·배정 정보를 함께 읽는다. | 일반 진행 상태의 담당자 해석·결과 등록이나 의뢰자 작성 책임을 대신하지 않는다. |
| 담당자 진행·결과 정보 구조 | 배정 수신 뒤 해석 진행, 해석 단계 보완, 변경 수락·거절, 보류·재개, 결과 등록을 위해 현재 의뢰서·제안 변경안·배정·결과 정보를 함께 읽는다. | 관리자 확인 대기와 취소 요청 대기에는 담당자 처리 구조를 행위 진입으로 열지 않는다. |
| 공통 상세·이력·결과·읽기 전용 정보 구조 | 현재 상태·대기 요청·현재 담당자, 버전·Case, 보완·보류·취소 요청, 배정 이력, 결과 회차와 현재 결과를 역할별 권한에 따라 함께 읽고, 상태가 바뀐 뒤 결과를 확인한다. | 목록 탐색·할 일 우선순위·작성 세부 입력을 중복해서 맡지 않는다. |

따라서 공통 탐색은 `홈 → 내 할 일 또는 의뢰함 → 의뢰 상세`이고, 의뢰자만 `홈 → 새 의뢰 시작 → 작성 중 상세`로 병렬 진입한다. 상세의 행위가 끝나면 다음 처리자가 있으면 그 역할의 `내 할 일`과 상세에서 이어지고, 다음 행위가 없으면 역할별 조회 범위 안의 `의뢰함`·공통 상세에서 결과와 이력을 열람한다.

#### 업무 행위별 진입·처리·결과 확인

| 업무 행위(3.2) | 역할별 진입 화면 또는 맥락 | 처리 기준 화면 또는 공통 상세에서 함께 확인할 정보 | 처리 뒤 상태·다음 처리자·결과 확인 위치 |
|---|---|---|---|
| 제출 | 의뢰자가 홈의 새 의뢰 시작 또는 `내 할 일`의 `작성 중`에서 작성 상세로 들어간다. | 의뢰 대상·내용·제품·활성 조건·Case와 8장 제출 충족 상태를 의뢰자 작성 구조에서 함께 확인한다. | `검토 중`; 관리자의 `내 할 일(검토)`과 관리자 상세로 인계된다. 의뢰자는 공통 상세에서 조회·대기한다. |
| 보완 요청 (검토 단계) | 관리자가 `내 할 일(검토)` 또는 `의뢰함`의 `검토 중` 상세로 들어간다. | 현재 의뢰서·이전 버전 대비 변경·제출 충족 상태와 검토 판단, 사유 코드·설명을 관리자 상세과 공통 이력에서 함께 확인한다. | `보완 필요`; 의뢰자의 `내 할 일(보완)`과 작성 상세에서 재제출을 처리한다. 관리자는 공통 상세에서 재제출을 조회한다. |
| 반려 | 관리자가 `내 할 일(검토)`의 `검토 중` 상세에서 처리한다. | 의뢰서와 이전 버전 대비 변경, 지원 범위·검토 판단, 반려 사유 코드·설명과 이력을 함께 확인한다. | `반려` 종료; 의뢰자와 관리자는 역할별 `의뢰함`·공통 상세에서 조회만 한다. 담당자는 배정 이력이 없어 대상이 아니다. |
| 접수·배정 | 관리자가 `내 할 일(검토)`의 `검토 중` 상세에서 처리한다. | 현재 의뢰서·Case·제출 충족 상태, 해석유형·담당자 상황과 현재 배정 없음 상태를 관리자 상세에서 함께 확인한다. | 일반 `해석 진행 중`; 배정 담당자의 `내 할 일(해석 진행)`과 담당자 상세로 인계된다. 의뢰자는 공통 상세에서 진행을 확인한다. |
| 재제출 (검토 단계) | 의뢰자가 `내 할 일(보완)`의 `보완 필요`에서 작성 상세로 들어간다. | 검토 보완 요청의 사유·설명, 수정한 의뢰서와 Case, 8장 제출 충족 상태·이전 버전을 함께 확인한다. | `검토 중`; 관리자의 `내 할 일(검토)`과 관리자 상세에서 다시 판단한다. 의뢰자는 공통 상세에서 조회·대기한다. |
| 재제출 (해석 단계·담당자 요청) | 의뢰자가 `내 할 일(보완)`의 담당자 요청 `해석 중 보완 필요`에서 작성 상세로 들어간다. | 요청 주체·사유 코드·설명, 수정 의뢰서와 Case, 제출 충족 상태·이전 버전을 함께 확인한다. | 일반 `해석 진행 중`; 재배정이 없으면 기존 담당자의 `내 할 일(해석 진행)`과 담당자 상세로 이어진다. 재배정이 겹친 경우(`G-31`)에는 공통 상세에서 배정 이력과 대기 맥락만 확인하며 다음 처리자·특정 할 일 목록을 정하지 않는다. |
| 재제출 (해석 단계·관리자 요청) | 의뢰자가 `내 할 일(보완)`의 관리자 요청 `해석 중 보완 필요`에서 작성 상세로 들어간다. | 관리자 보완 요청의 사유 코드·설명, 수정 의뢰서·Case, 제출 충족 상태·이전 버전을 함께 확인한다. | `해석 진행 중(관리자 확인 대기)`; 관리자의 `내 할 일(해석 계속 확인)`과 관리자 상세로 인계된다. 의뢰자·담당자는 공통 상세에서 조회·대기한다. |
| 보완 요청 (해석 단계) | 배정 담당자는 `내 할 일(해석 진행)`의 일반 진행 상세에서, 관리자는 `의뢰함` 또는 관리·조회 중인 일반 진행 상세에서 시작한다. | 현재 의뢰서·Case·버전, 현재 담당자·배정 이력, 정보 부족 판단과 사유 코드·설명을 각 역할 상세 및 공통 이력에서 함께 확인한다. | `해석 중 보완 필요`; 의뢰자의 `내 할 일(보완)`과 작성 상세로 인계된다. 요청자가 담당자면 재제출 뒤 일반 진행으로, 관리자면 관리자 확인 대기로 돌아가는 구분을 공통 상세에서 유지한다. |
| 해석 계속·담당자 배정 | 관리자가 `내 할 일(해석 계속 확인)`의 관리자 확인 대기 상세에서 처리한다. | 관리자 요청 보완의 사유·설명, 재제출 버전과 이전 버전 대비 변경, 현재 담당자·배정 이력을 관리자 상세에서 함께 확인한다. | 일반 `해석 진행 중`; 지정 담당자의 `내 할 일(해석 진행)`과 담당자 상세로 인계된다. 기존 담당자를 다시 지정할 수도 있으며, 의뢰자는 공통 상세에서 진행 상태를 조회한다. |
| 재보완 요청 (해석 단계) | 관리자가 `내 할 일(해석 계속 확인)`의 관리자 확인 대기 상세에서 처리한다. | 관리자 요청 보완의 재제출 버전·이전 버전 대비 변경, 재보완 판단과 사유 코드·설명을 함께 확인한다. | `해석 중 보완 필요`; 의뢰자의 `내 할 일(보완)`과 작성 상세로 다시 인계된다. 담당자는 공통 상세에서 조회·대기한다. |
| 보류 | 배정 담당자는 `내 할 일(해석 진행)` 또는 변경 요청 수락 대기의 담당자 상세에서, 관리자는 일반 진행의 관리·조회 상세에서 시작한다. | 현재 상태·대기 요청, 보류가 정보 부족이 아닌 일정 등의 사유인지, 사유 코드·설명, 현재 담당자·배정 이력을 함께 확인한다. | `보류`; 담당자 보류면 그 담당자의 `내 할 일(담당자 보류)`, 관리자 보류면 관리자의 `내 할 일(관리자 보류)`에서 재개한다. 공통 상세에서 보류 주체와 결과를 조회한다. 진행 중 변경 요청 대기에도 보류만 병행할 수 있고 요청은 대기한 채 남는다. |
| 재개 | 보류한 담당자는 `내 할 일(담당자 보류)`에서, 관리자는 자신이 보류한 의뢰 또는 관리·조회 중 보류의 상세에서 처리한다. | 보류 주체·사유·보류 전 상태, 현재 담당자·배정 이력과 대기 요청을 함께 확인한다. | 일반 `해석 진행 중`; 담당자 보류는 현재 담당자의 `내 할 일(해석 진행)`으로, 관리자 보류도 현재 담당자의 같은 목록으로 인계된다. 진행 중 변경 요청이 남아 있으면 수락·거절 우선 경계를 공통 상세에서 다시 적용한다. |
| 재배정 | 관리자가 일반 `해석 진행 중`, `해석 중 보완 필요`, `보류`의 `의뢰함` 또는 관리·조회 상세에서 시작한다. | 현재·새 담당자가 다른지, 재배정 사유, 보류 주체·대기 요청, 현재 담당자와 배정 이력을 함께 확인한다. | 상태는 유지한다. 일반 진행이면 새 담당자의 `내 할 일(해석 진행)`으로, 담당자 보류면 새 담당자의 `내 할 일(담당자 보류)`로 책임이 이어진다. 관리자 보류는 관리자 할 일에 남는다. 이전 담당자는 종료 전 조회·재개·처리 범위에서 제외된다. `G-30`·`G-31`의 겹침은 다음 처리자나 특정 목록을 정하지 않는다. |
| 진행 중 변경 요청 | 의뢰자가 `의뢰함` 또는 공통 상세의 대기 요청 없는 일반 `해석 진행 중`에서 변경안 작성 맥락으로 들어간다. | 현재 의뢰서와 분리된 변경안, 변경 사유, 이전 버전 대비 변경, 변경안의 8장 제출 충족 상태를 함께 확인한다. | 상태는 일반 `해석 진행 중`으로 유지하고 담당자 수락 대기가 된다. 원칙상 배정 담당자의 `내 할 일(변경 요청 판단)`과 담당자 상세에서 수락·거절한다. 재배정이 겹친 `G-30`은 처리자·특정 목록을 정하지 않는다. |
| 진행 중 변경 수락·거절 | 배정 담당자가 `내 할 일(변경 요청 판단)`의 일반 진행 상세에서 처리한다. | 현재 의뢰서, 제안 의뢰서·변경 사유·이전 버전 대비 변경, 현재 배정·대기 요청과 거절 사유(거절 시)를 함께 확인한다. | 수락하면 제안안이 새 버전이 되고, 거절하면 원 의뢰서가 유지된 일반 `해석 진행 중`이다. 담당자는 해석을 계속하고 의뢰자는 공통 상세·이력에서 결과를 확인한다. 대기 중에는 보완 요청·결과 등록을 막고 보류만 가능하다. `G-30` 겹침은 처리자를 특정하지 않는다. |
| 취소 | 의뢰자는 `작성 중`에서는 작성 상세에서, `보완 필요`에서는 `내 할 일(보완)`의 작성 상세에서, `검토 중`에서는 `의뢰함`·공통 상세에서 직접 처리한다. | 현재 상태와 본인 의뢰 여부를 공통 상세에서 확인한다. 특히 `검토 중`은 관리자가 현재 처리자여도 의뢰자의 직접 취소가 허용되는 경계다. | `취소` 종료; 역할별 조회 범위 안의 `의뢰함`·공통 상세에서만 결과를 확인한다. 제출 전 취소는 작성자만, 배정 후 취소는 배정 이력이 있는 담당자도 조회한다. |
| 취소 요청 | 의뢰자가 대기 요청 없는 일반 `해석 진행 중`, `해석 중 보완 필요`, `보류`의 `의뢰함`·공통 상세에서 시작한다. | 취소 사유, 요청 직전 상태, 현재 담당자·보류 정보와 다른 대기 요청이 없는지를 함께 확인한다. | 상태는 유지하고 취소 요청 대기가 된다. 관리자의 `내 할 일(취소 요청 처리)`과 관리자 상세로만 인계되며, 의뢰자·담당자는 공통 상세에서 조회·대기한다. |
| 취소 요청 승인·거절 | 관리자가 `내 할 일(취소 요청 처리)`의 취소 요청 대기 상세에서 처리한다. | 요청 사유·요청 직전 상태·요청자·시각, 현재 담당자·보류 정보와 거절 사유(거절 시)를 함께 확인한다. | 승인하면 `취소` 종료, 거절하면 요청 전 상태를 유지한다. 승인·거절 결과는 공통 상세·이력에서 확인하며, 거절 뒤에는 요청 전 상태의 다음 처리 위치로만 돌아간다. 대기 중에는 이 행위 외 모든 업무 행위와 의뢰서 수정이 차단된다. |
| 결과 등록 | 배정 담당자가 대기 요청과 관리자 확인 대기가 없는 일반 `해석 진행 중`의 `내 할 일(해석 진행)`과 담당자 상세에서 처리한다. | 현재 의뢰서·Case·버전, 현재 담당자, 결과 회차와 결과 요약을 함께 확인한다. | `결과 확인 필요`; 의뢰자의 `내 할 일(결과 확인)`과 공통 상세의 현재 결과로 인계된다. 관리자·담당자는 결과 회차와 현재 결과를 조회한다. |
| 결과 재작업 요청 | 의뢰자가 `내 할 일(결과 확인)`의 공통 상세에서 처리한다. | 현재 결과·이전 결과 회차, 결과 재작업 요청 사유와 현재 담당자를 함께 확인한다. | 일반 `해석 진행 중`; 같은 담당자의 `내 할 일(해석 진행)`과 담당자 상세로 인계된다. 이전 결과는 이력으로 남고 의뢰자는 다음 결과를 공통 상세에서 기다린다. |
| 결과 확인 | 의뢰자가 `내 할 일(결과 확인)`의 공통 상세에서 처리한다. | 현재 결과, 이전 회차, 결과 재작업 요청 이력과 결과 확인 대상임을 함께 확인한다. | `완료` 종료; 의뢰자·관리자와 배정 이력이 있는 담당자는 역할별 `의뢰함`·공통 상세에서 조회만 한다. |

#### 대기·종료·조회 범위의 누락 점검

| 경계 | 화면 목록과 업무 행위 대응에서 유지한 결과 |
|---|---|
| 진행 중 변경 요청 대기 | 담당자 상세에서 수락·거절이 우선이며, 보완 요청·결과 등록은 진입·처리 대상에서 제외한다. 보류만 가능하고, 재개 뒤에도 같은 변경 요청을 먼저 처리한다. |
| 관리자 확인 대기 | 관리자 `내 할 일`과 관리자 상세에서만 해석 계속·담당자 배정 또는 재보완 요청을 처리한다. 담당자 상세는 해석 진행·보완 요청·보류·결과 등록을, 의뢰자 측은 진행 중 변경·취소 요청을 제공하지 않고 조회·대기만 연결한다. |
| 취소 요청 대기 | 관리자 `내 할 일`과 상세의 승인·거절만 처리 경로로 둔다. 모든 역할의 다른 업무 행위와 의뢰서 수정은 차단하고, 거절 뒤에만 요청 전 상태의 기존 처리 경로를 다시 연결한다. |
| 직접 취소와 검토 중 | `작성 중`·`검토 중`·`보완 필요`에서 의뢰자의 직접 취소를 각각 작성 또는 공통 상세의 처리 경로에 연결했다. `검토 중`의 관리자 할 일과 의뢰자 직접 취소 권한을 혼동하지 않는다. |
| 재배정과 이전 담당자 | 일반 재배정 뒤 이전 담당자는 종료 전 의뢰의 `의뢰함`·상세 조회, 재개, 처리 경로에서 제외된다. 새 담당자에게만 현재 배정과 배정 이력이 이어지며, 담당자 보류의 재개 책임도 함께 넘어간다. |
| 종료 상태 | `완료`·`반려`·`취소`은 역할별 조회 범위 안의 의뢰함·공통 상세에서만 열람한다. 담당자는 배정 이력이 있는 `완료`와 배정 후 `취소`만 조회하며, `반려`와 배정 전 취소는 대상이 아니다. |
| `G-30`, `G-31` | 재배정과 진행 중 변경 수락·거절, 또는 담당자 요청 보완 재제출이 겹친 경우는 상세에 현재 상태·대기 요청·배정 이력만 남긴다. 다음 처리자나 특정 담당자의 `내 할 일`을 임의로 만들지 않는다. |
| `G-22`, `G-28`, `G-32` | 처리 화면은 측정·판정 기준의 현재 값·상태와 Case 재확인 필요 여부만 참조한다. 기준의 필수 여부·판정 기준 및 Case 저장·재확인 저장 방식은 노출하거나 확정하지 않는다. 사용 중인 `○` 조건의 허용된 `없음`은 활성 Case 대안이며, 미사용과 `—`만 Case에서 제외하고 `●`에는 `없음`을 두지 않는다. |
