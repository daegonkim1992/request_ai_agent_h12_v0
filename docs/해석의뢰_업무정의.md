# 해석의뢰 업무정의서

- 목적: 해석의뢰 업무의 역할, 흐름, 의뢰서·조건·Case·결과 기준을 정의한다.
- 표기: **[추후 정의]**는 업무 항목은 정했으나 기준을 나중에 정한다는 뜻이고, **[검토 필요]**는 업무 규칙의 확정이 필요하다는 뜻이다.

---

## 1. 업무 개요

### 1.1 정의

해석의뢰 업무는 다음 과정 전체를 말한다.
1. 기구설계 엔지니어(의뢰자)가 해석이 필요한 문제를 의뢰서로 작성해 제출한다.
2. 해석관리자가 검토해 접수하고 해석담당자를 배정한다.
3. 해석담당자가 해석을 수행하고 결과를 회신한다.
4. 의뢰자가 결과를 확인하면 의뢰가 완료된다.

### 1.2 목표

의뢰자가 목적, 대상 제품, 해석 조건을 빠짐없이 전달해서, 해석담당자가 **별도 재문의 없이 착수 여부를 판단**할 수 있게 한다.

### 1.3 범위

| 구분 | 내용 |
|---|---|
| 범위 안 | 의뢰서 작성, 제출, 검토와 보완, 접수와 배정, 해석 진행 관리(보류, 진행 중 변경, 재배정), 결과 등록, 결과 확인, 취소와 반려 |
| 범위 밖 | 해석 수행 자체. 메시, 솔버, 접촉 알고리즘, 수렴 기준처럼 해석자가 판단하는 항목은 의뢰자 입력에서 제외한다 |
| 지원 분야 | 유동(CFD) 해석 11종 (부록 A) |

## 2. 역할

| 역할 | 책임 | 할 수 있는 일 | 볼 수 있는 의뢰 |
|---|---|---|---|
| **의뢰자** | 착수 가능한 의뢰서를 작성하고 결과를 확인한다 | 의뢰 작성·제출, 보완 후 재제출, 진행 중 변경 요청, 취소·취소 요청, 결과 재작업 요청, 결과 확인 | 자기 의뢰, 같은 소속 부서에서 만든 의뢰(조회만) |
| **해석관리자** | 의뢰를 검토해 접수하고 담당자를 배정한다 | 보완 요청(검토 단계, 해석 단계), 반려, 접수·배정, 재배정, 보류·재개, 취소 요청 승인·거절 | 전체 (한 번도 제출하지 않은 의뢰는 제외) |
| **해석담당자** | 해석을 수행하고 결과를 회신한다 | 보완 요청(해석 단계), 보류·재개, 진행 중 변경 수락·거절, 결과 등록 | 배정받은 의뢰 |

- 사용자는 역할과 소속 부서를 하나씩 가진다.
- 새 의뢰는 의뢰자만 만들 수 있다.
- **같은 부서 의뢰 조회:** 의뢰자는 자기와 소속 부서가 같은 사용자가 만든 의뢰를 볼 수 있다.
  - 조회만 가능하며 업무 행위를 수행할 수 없다.
  - 소속 부서를 기준으로 조회 권한을 판단한다.
- **제출 전 의뢰의 조회:** 한 번도 제출하지 않은 의뢰(작성 중, 제출 전에 취소한 의뢰)는 작성자만 본다. 같은 부서 의뢰자와 해석관리자도 보지 않는다.

## 3. 업무 흐름

### 3.1 상태

| 상태 | 의미 | 종료 여부 |
|---|---|---|
| 작성 중 | 의뢰자가 의뢰서를 작성하고 있다. 작성 내용을 보존하고 이어서 작성할 수 있다 | |
| 검토 중 | 제출 또는 재제출되어 관리자의 검토를 기다린다 | |
| 보완 필요 | 관리자가 검토 단계에서 보완을 요청했다 | |
| 해석 진행 중 | 접수되어 배정된 담당자가 해석하고 있다. 관리자가 요청한 해석 단계 보완을 재제출한 뒤에는 관리자의 확인이 끝날 때까지 담당자의 해석을 멈춘다 | |
| 해석 중 보완 필요 | 담당자나 관리자가 해석 단계에서 정보 보완을 요청했다. 해석은 멈춘다 | |
| 보류 | 일정 등의 사유로 해석을 잠시 멈췄다 | |
| 결과 확인 필요 | 담당자가 결과를 등록해 의뢰자의 확인을 기다린다 | |
| 완료 | 의뢰자가 결과를 확인했다 | 종료 |
| 반려 | 관리자가 보완으로 해결할 수 없다고 판단했다 | 종료 |
| 취소 | 의뢰자가 취소했거나 취소 요청이 승인되었다 | 종료 |

### 3.2 업무 행위와 수행 가능 상태

**각 업무 행위는 표의 수행 가능 상태에서만 할 수 있다.** 취소 요청이 대기 중이면 아래 표의 상태와 관계없이 관리자의 취소 요청 승인·거절만 할 수 있다(3.4-4).

| 업무 행위 | 수행자 | 수행 가능 상태 | 결과 상태 | 필수 입력 |
|---|---|---|---|---|
| 제출 | 의뢰자 | 작성 중 | 검토 중 | 제출 조건 충족 (8장) |
| 보완 요청 (검토 단계) | 관리자 | 검토 중 | 보완 필요 | 사유 코드, 설명 (3.7) |
| 반려 | 관리자 | 검토 중 | 반려 | 사유 코드, 설명 (3.7) |
| 접수·배정 | 관리자 | 검토 중 | 해석 진행 중 | 담당자 |
| 재제출 (검토 단계) | 의뢰자 | 보완 필요 | 검토 중 | 의뢰서. 내용이 바뀌지 않아도 재제출할 수 있다 |
| 재제출 (해석 단계·담당자 요청) | 의뢰자 | 해석 중 보완 필요 (담당자 요청) | 해석 진행 중 | 의뢰서. 내용이 바뀌지 않아도 재제출할 수 있다 |
| 재제출 (해석 단계·관리자 요청) | 의뢰자 | 해석 중 보완 필요 (관리자 요청) | 해석 진행 중 (관리자 확인 대기) | 의뢰서. 내용이 바뀌지 않아도 재제출할 수 있다 |
| 보완 요청 (해석 단계) | 배정된 담당자, 관리자 | 해석 진행 중 (대기 중인 요청과 관리자 확인 대기가 없을 때) | 해석 중 보완 필요 | 사유 코드, 설명 (3.7) |
| 해석 계속·담당자 배정 | 관리자 | 해석 진행 중 (관리자 확인 대기) | 해석 진행 중 | 해석을 계속할 담당자 |
| 재보완 요청 (해석 단계) | 관리자 | 해석 진행 중 (관리자 확인 대기) | 해석 중 보완 필요 | 사유 코드, 설명 (3.7) |
| 보류 | 배정된 담당자, 관리자 | 해석 진행 중 (관리자 확인 대기 제외) | 보류 | 사유 코드, 설명 (3.7) |
| 재개 | 보류한 사람, 관리자 | 보류 | 해석 진행 중 | |
| 재배정 | 관리자 | 해석 진행 중 (관리자 확인 대기 제외), 해석 중 보완 필요, 보류 | 상태 유지 | 새 담당자(현재 담당자와 달라야 한다), 사유 |
| 진행 중 변경 요청 | 의뢰자 | 해석 진행 중 (대기 중인 요청이 없을 때) | 상태 유지 (담당자 수락 대기) | 변경한 의뢰서(제출 조건 충족, 8장), 변경 사유 |
| 진행 중 변경 수락·거절 | 배정된 담당자 | 해석 진행 중 (변경 요청이 대기 중일 때) | 해석 진행 중 | 거절이면 사유 |
| 취소 | 의뢰자 | 작성 중, 검토 중, 보완 필요 | 취소 | |
| 취소 요청 | 의뢰자 | 해석 진행 중, 해석 중 보완 필요, 보류 (대기 중인 요청이 없을 때) | 상태 유지 (관리자 승인 대기) | 사유 |
| 취소 요청 승인·거절 | 관리자 | 취소 요청이 대기 중일 때 | 승인하면 취소, 거절하면 상태 유지 | 거절이면 사유 |
| 결과 등록 | 배정된 담당자 | 해석 진행 중 (대기 중인 요청이 없을 때) | 결과 확인 필요 | 결과 요약 |
| 결과 재작업 요청 | 의뢰자 | 결과 확인 필요 | 해석 진행 중 (같은 담당자) | 사유 |
| 결과 확인 | 의뢰자 | 결과 확인 필요 | 완료 | |

- 사유와 설명(자유 입력)에는 길이 제한을 두지 않는다. 200자 제한(5.1)은 의뢰서의 자유 입력에만 적용한다.

### 3.3 상태 흐름

```
작성 중 ─제출→ 검토 중 ─접수·배정→ 해석 진행 중 ─결과 등록→ 결과 확인 필요 ─결과 확인→ 완료
              │   ↑                 │   ↑   │   ↑                │
         보완 요청  재제출       보완 요청  재제출  보류  재개      결과 재작업 요청
              ↓   │                 ↓   │   ↓   │                └──→ 해석 진행 중
            보완 필요           해석 중 보완 필요  보류

해석 진행 중 ─담당자 보완 요청→ 해석 중 보완 필요 ─담당자 요청 재제출→ 해석 진행 중
해석 진행 중 ─관리자 보완 요청→ 해석 중 보완 필요 ─관리자 요청 재제출→ 해석 진행 중 (관리자 확인 대기)
해석 진행 중 (관리자 확인 대기) ─해석 계속·담당자 배정→ 해석 진행 중
해석 진행 중 (관리자 확인 대기) ─재보완 요청→ 해석 중 보완 필요

검토 중 ─반려→ 반려 (종료)

해석 진행 중 (관리자 확인 대기 제외) · 해석 중 보완 필요 · 보류 ─취소 요청→ 관리자 승인 → 취소 (종료)
해석 진행 중 (관리자 확인 대기 제외) · 해석 중 보완 필요 · 보류 ─재배정→ 상태 유지
해석 진행 중 ─진행 중 변경 요청→ 담당자 수락 → 해석 진행 중 (새 의뢰서 버전)
```

### 3.4 공통 규칙

1. **수정 가능 상태:** 의뢰서 내용은 작성 중, 보완 필요, 해석 중 보완 필요 상태에서만 의뢰자가 고칠 수 있다. 해석 진행 중에는 진행 중 변경 요청으로만 바꾼다. 담당자와 관리자는 의뢰서 내용을 직접 고치지 않는다.
2. **보완 요청의 구분:** 검토 단계 보완은 관리자가, 해석 단계 보완은 배정된 담당자나 관리자가 요청한다. 검토 단계 보완 또는 담당자가 요청한 해석 단계 보완은 재제출하면 각각 관리자 검토 또는 담당자 해석으로 돌아간다. 관리자가 요청한 해석 단계 보완을 재제출하면 관리자의 확인 대기가 된다. 관리자는 해석을 계속할 담당자를 배정하거나 다시 보완을 요청한다. 정보 부족은 보류가 아니라 보완 요청으로 처리하고, 보류는 일정 등 다른 사유에만 쓴다.
3. **진행 중 변경과 보완의 구분:** 진행 중 변경은 의뢰자가 의뢰 내용(조건, 범위)을 바꾸려는 것이다. 담당자가 수락하면 반영되고, 거절하면 원래 내용으로 계속한다. 정보 부족에 따른 보완은 담당자나 관리자가 시작하는 해석 단계 보완 요청이다.
4. **대기 요청은 하나만:** 한 의뢰에 진행 중 변경 요청과 취소 요청이 동시에 대기할 수 없다. 요청이 대기 중이면 결과 등록을 막는다.
   - **취소 요청 대기:** 의뢰는 취소 대기로 올라간다. 관리자가 승인하거나 거절하기 전에는 다른 업무 행위(재제출, 보완 요청, 보류·재개, 재배정, 결과 등록 등)와 의뢰서 수정을 막는다. 거절되면 요청 전 상태에서 그대로 이어 간다.
   - **진행 중 변경 요청 대기:** 담당자가 변경 요청을 먼저 수락하거나 거절해야 해석 단계 보완을 요청할 수 있다. 보완 후 재제출하면 대기 중인 변경안이 이전 의뢰서를 기준으로 남기 때문이다. 보류는 할 수 있으며, 변경 요청은 대기한 채로 남아 재개한 뒤 수락·거절한다.
   - **관리자 확인 대기:** 관리자가 요청한 해석 단계 보완을 의뢰자가 재제출하면 관리자가 해석을 계속시킬지, 다시 보완을 요청할지, 해석을 계속할 담당자를 누구로 할지 결정한다. 확인이 끝날 때까지 담당자는 해석을 진행하거나 결과를 등록할 수 없고, 의뢰자도 진행 중 변경·취소 요청을 할 수 없다. 이때 배정하는 담당자는 기존 담당자와 같아도 된다. 일반 재배정은 기존처럼 현재 담당자와 다른 사람만 지정할 수 있다.
5. **의뢰서 버전:** 제출, 재제출, 진행 중 변경 수락 때마다 의뢰서 버전을 새로 남긴다. 관리자와 담당자는 이전 버전과 달라진 부분을 확인할 수 있다.
6. **결과 회차:** 결과 재작업 요청 후 다시 등록한 결과는 회차별로 쌓인다. 마지막 결과를 현재 결과로 본다.
7. **이력:** 모든 상태 변화와 요청은 수행자, 이전·이후 상태, 사유, 시각과 함께 기록한다. 상태를 유지하는 기능(재배정, 해석 계속·담당자 배정, 진행 중 변경 요청·수락·거절, 취소 요청·거절)도 기록한다. 진행 중 변경 요청은 거절되더라도 제안한 의뢰서 내용을 이력에 남긴다.
8. **종료 상태:** 완료, 반려, 취소 상태에서는 조회만 할 수 있다.
9. **의뢰번호 [검토 필요]:** 의뢰 대상을 확정할 때 `CFD-YYYYMMDD-NNN` 형식으로 발급한다(NNN은 날짜별 일련번호). 취소된 번호는 다시 쓰지 않는다.
10. **기준 데이터 변경:** 의뢰는 의뢰 대상을 확정한 시점의 기준 데이터(해석유형별 조건 매핑, 제품 분류, 열교환기 Catalog, 측정·판정 기준 표준값)를 따른다. 나중에 기준 데이터가 바뀌어도 이미 확정한 의뢰에는 영향을 주지 않는다. 의뢰서를 고칠 수 있는 상태(3.4-1)에서 의뢰 대상을 바꿔 다시 확정하면, 다시 확정한 시점의 기준 데이터 기준을 적용한다.
11. **결과 확인 필요 상태의 종료:** 결과 확인 필요 상태에서는 취소와 취소 요청을 할 수 없다. 의뢰자는 결과를 확인해 완료하거나 결과 재작업을 요청한다(의도한 규칙).
12. **보류 중 재배정:** 담당자가 보류한 의뢰를 재배정하면 보류한 사람도 새 담당자로 넘어간다. 새 담당자가 재개할 수 있고 할 일 목록에도 들어간다. 이전 담당자는 더 이상 의뢰를 보지 않으므로 재개할 수 없다. 관리자가 보류한 의뢰는 재배정해도 관리자의 보류로 남는다. 보류 중에 취소 요청이 승인되면 보류 정보도 함께 지운다.

### 3.5 역할별 현재 처리 대상

현재 처리 대상은 해당 역할이 다음 처리를 책임지거나 작업을 재개해야 하므로 할 일 목록에 들어가는 의뢰다. 조회 범위나 업무 행위 권한과는 구분한다.

| 역할 | 할 일에 들어가는 의뢰 |
|---|---|
| 의뢰자 | 작성 중, 보완 필요, 해석 중 보완 필요, 결과 확인 필요 |
| 해석관리자 | 검토 중, 취소 요청 대기, 해석 진행 중 (관리자 확인 대기), 관리자가 보류한 의뢰 |
| 해석담당자 | 본인에게 배정된 해석 진행 중 (관리자 확인 대기 제외), 진행 중 변경 수락 대기, 본인이 보류한 의뢰 |

- 취소 요청이 대기 중인 의뢰는 관리자의 할 일에만 들어간다. 의뢰자와 담당자는 그동안 할 수 있는 일이 없다(3.4-4).
- **관리·조회 대상:** 현재 처리 대상이 아니더라도 역할의 조회 범위에 속해 열람하거나, 3.2의 수행 가능 상태에서 업무 행위를 할 수 있는 의뢰다. 이 대상이라고 해서 할 일 목록에 자동으로 들어가지는 않는다. 예를 들어 의뢰자는 해석 진행 상황을 조회하고 허용된 상태에서 변경·취소 요청을 시작할 수 있으며, 관리자는 진행 중 의뢰를 조회해 필요할 때 재배정·보완 요청·보류를 할 수 있다. 담당자는 본인 배정 의뢰가 관리자 확인 대기일 때 조회할 수 있으나 그 대기가 끝날 때까지 해석을 진행할 수 없다.

### 4.2 의뢰 대상

| 항목 | 규칙 |
|---|---|
| 제품 분류 | 사업부 → Product Line-up → Platform → Chassis 순서로 등록된 조합에서만 고른다. Chassis 아래 단계는 두지 않는다. 등록되지 않은 분류는 만들 수 없고 기준 데이터 담당자에게 추가를 요청한다 |
| 사업부별 Platform 선택 | SAC·Chiller는 목록에서 고르고, RAC·Air Care는 Product Line-up에서 자동으로 정해지며, AIDC는 해당 없음 |
| Chassis | Chassis가 없는 경로는 비워 둔다. "NA"는 Duct(Multi V)와 Duct(Single CAC)에서만 실제 값이다 |
| 해석유형 | 11종 중 하나 (부록 A) |
| 해석 범위 | RAC Window 제품(사업부 RAC, Line-up Window, Platform Window)일 때만 고른다. 실내측 / 실외측 / 실내·실외 모두. "실내·실외 모두"는 동시운전이 아니라 두 측을 모두 해석해 달라는 뜻이며 **의뢰 한 건**으로 다룬다. 실내·실외 운전을 구분하는 제품은 RAC Window뿐이라 별도의 운전 구분 항목은 두지 않는다 |
| 냉각 방식 | PCB발열일 때만 고른다. 공랭식 / 수랭식. 수랭식이면 PCB 조건에 냉매 조건이 생긴다 |
| 확정 | 위 항목을 확정하면 의뢰 대상이 잠기고, 의뢰번호를 발급하며, 해석유형에 맞는 조건 구성이 정해진다 |
| 의뢰 대상 변경 | 의뢰서를 고칠 수 있는 상태(3.4-1)에서 의뢰 대상을 바꿔 다시 확정할 수 있다. 의뢰번호는 처음 확정할 때 발급하고 다시 확정해도 그대로 둔다. 확인을 받은 뒤 새 조건 구성을 적용한다. 새 유형에 맞지 않는 조건 값은 지우지 않고 비활성으로 보존한다. 다시 확정하면 그 시점의 기준 데이터 기준을 적용한다(3.4-10). 제품 분류가 바뀌면 선택한 PMS 프로젝트를 비우고 다시 고르게 한다(4.4) |

| 개발 프로젝트 | 프로젝트명(PMS), 개발 등급, NPI 단계 | 의뢰 대상의 제품 사업부에 해당하는 PMS 프로젝트를 반드시 골라야 한다. 프로젝트를 고르면 개발 등급과 NPI 단계도 필수가 된다. PMS 프로젝트는 제품 사업부에 종속되므로, 의뢰 대상의 제품 분류가 바뀌면 선택한 프로젝트와 자동으로 채운 PMS Project Code, Region을 비우고 다시 고르게 한다. AIDC는 PMS 프로젝트가 없으므로 개발 프로젝트로 의뢰할 수 없다 |
| 품질 개선 | 없음 | |
| 필드 이슈 | 없음 | |
| 선행 검토 | 없음 | |
| 기타 | 의뢰 유형 직접 입력 | |

### 4.5 해석 제품

| 규칙 | 내용 |
|---|---|
| 총조립 형상 기준 | 해석 제품은 해석에 쓸 총조립 형상이다. Base 제품과 비교 제품의 도면번호는 해석에 사용하는 총조립 형상을 식별하는 도면번호여야 하며, 단품·부품·하위 조립품의 도면번호는 사용할 수 없다 |
| 조립 상태가 다르면 다른 제품 | 부품의 각도, 위치, 배치(Arrangement)가 다르면 다른 총조립 형상이므로 각각 다른 도면번호가 필요하다 |
| Base 제품 | 정확히 1개 |
| 비교 제품 | 0개 이상. 각 비교 제품에는 Base 대비 차이 설명이 필수다 |
| 도면번호 | 제품마다 필수. 영문·숫자·하이픈 형식이며 제품끼리 중복될 수 없다. 같은 도면번호로 형상만 다르게 비교할 수 없고, 임시 도면번호는 만들지 않는다 |
| 형상 축 | 제품 순서대로 형상 1..N을 만든다. 사용자가 지정한 제품명은 보존한다 |

### 4.6 구성 요소의 선후 관계 [검토 필요]

필드 하나하나의 선후 관계는 조건 사전(5.3)과 매핑표(5.2)의 적용·필수 규칙으로 정의한다. 여기서는 구성 요소 단위의 의존 관계와 의존 규칙의 종류만 정의한다.

**구성 요소 단위 의존 관계**

```
제품 분류 → 해석유형 → (해석 범위 · 냉각 방식) → [확정] → 조건 구성 → 조건 패키지 입력 ─┐
의뢰 유형 → PMS · 개발 등급 · NPI 단계 (PMS 목록은 제품 분류의 사업부를 따른다)           ├→ Case → 제출
해석 제품 (Base · 비교) → 형상 축 ──────────────────────────────────────────────────┘
의뢰자 정보, 배경, 확인하고 싶은 내용, 희망 완료일, 결과 활용 목적: 다른 항목에 의존하지 않는다
```

**의존 규칙의 종류**

조건 사전의 모든 의존 관계는 아래 다섯 가지 중 하나에 해당한다.

| 유형 | 의미 | 예 |
|---|---|---|
| ① 결정이 구성을 정한다 | 앞의 선택이 뒤에서 무엇을 받을지 정한다 | 해석유형 → 조건 그룹·필드·필수 여부. 의뢰 유형 → PMS 입력. 제품 사업부 → PMS 프로젝트 목록 |
| ② 제품 속성이 항목을 연다 | 제품 분류에 따라 항목이 생긴다 | RAC Window → 해석 범위. PCB발열 → 냉각 방식 → (수랭식) 냉매 조건 |
| ③ 값이 다른 필드를 필수로 만든다 | 어떤 값을 넣으면 다른 칸이 필수가 된다 | 풍량 → 활용 목적. PMS 선택 → 개발 등급·NPI 단계. 비교 제품 → 차이 설명. 팬별 설정 → 팬 위치 |
| ④ 사용 여부가 내부 입력을 연다 | 선택 조건을 쓰기로 하면 내부 칸이 필수가 된다 | 필터 있음, 설치 조건 있음, 접촉저항 고려, 선택(○) 조건 사용 |
| ⑤ 앞이 바뀌면 뒤를 다시 본다 | 앞 단계 변경이 뒤 단계에 영향을 준다 | 아래 변경 영향 표 |

**변경 영향**

| 바뀌는 것 | 다시 봐야 하는 것 |
|---|---|
| 제품 분류, 해석유형 | 조건 구성 전체, Case |
| 제품 분류 | PMS 프로젝트 (비우고 다시 선택) |
| 다시 확정 | 확정 시점의 기준 데이터 기준 (3.4-10) |
| 의뢰 유형 | PMS, 개발 등급, NPI 단계 |
| 해석 제품 추가·삭제 | 형상 축, Case |
| 조건 패키지 추가·삭제·수정 | Case |
| 냉각 방식 | PCB의 냉매 조건 |

### 5.3 조건 사전

#### 5.3.1 운전 조건

| 필드 | 형식·단위 | 필수 | 규칙 |
|---|---|---|---|
| 팬 개수 | 1~10 | 필수 | 한 운전 조건에 팬은 최대 10개 |
| 팬 회전수 설정 방식 | 모든 팬 동일 / 팬별 설정 | 필수 | 팬별 설정이면 팬마다 RPM을 받는다. RPM 숫자가 같다는 이유만으로 "동일"로 보지 않는다 |
| 팬 위치 | 자유 입력 | 팬별 설정일 때 | 의뢰자가 말한 위치 표현을 그대로 쓴다 |
| 팬 회전수 (RPM) | 숫자, rpm | 아래 적용 규칙 | 활성 팬마다 입력 |
| 제품 풍량 | 숫자 | 선택 | 지원 단위는 [추후 정의] |
| 풍량 활용 목적 | 해석에 반영 요청 / 참고 정보로 제공 | 풍량을 입력하면 필수 | 다른 선택지는 두지 않는다 |
| 운전 조건 없음 | 선택 | 운전이 `○`인 유형만 | 선택하면 운전 조건을 적용하지 않는다(다상유동, 냉매누설) |

**RPM과 풍량의 적용 규칙**

| RPM | 풍량 | 활용 목적 | 해석에 쓰는 값 | 참고 정보 |
|---|---|---|---|---|
| 있음 | 없음 | — | RPM | — |
| 없음 | 있음 | 해석에 반영 | 풍량 (팬 개수는 무시) | — |
| 있음 | 있음 | 해석에 반영 | 풍량 | RPM |
| 있음 | 있음 | 참고 정보 | RPM | 풍량 |
| 없음 | 있음 | 참고 정보 | 허용하지 않음. RPM을 입력해야 한다 | — |
| 없음 | 없음 | — | `●`이면 불가, `○`이면 운전 조건을 적용하지 않음을 정해야 함 | — |

- RPM과 풍량 값이 서로 달라도 오류가 아니다.
- **운전 조건 패키지는 운전 대안이다.** 여러 값이 서로 다른 운전 대안이면 운전 조건 패키지를 여러 개 만들고, 패키지마다 RPM은 하나다. 한 운전 조건 안에 동시에 도는 여러 팬이면 패키지 하나 안에 팬을 여러 개 둔다.

#### 5.3.2 공간 환경 조건

| 필드 | 형식·단위 | 규칙 |
|---|---|---|
| 공간 온도 | °C | `○`이면 값 또는 `없음` |
| 공간 상대습도 (RH) | % | 매핑된 유형에서만 적용한다(이슬맺힘은 필수) |
| 입구 압력 | 정압·계기압, Pa | 공간 압력이 `○`인 유형에서 값 또는 `없음` |
| 출구 압력 | 정압·계기압, Pa | 공간 압력이 `○`인 유형에서 값 또는 `없음` |

- 패키지를 반복해 공간 조건 대안을 만든다.
- 매핑에 없는 필드는 적용하지 않는다.

| FPI (또는 FPDM) | Catalog 값 | |

#### 5.3.9 PCB 조건 (PCB발열 필수)

PCB 조건은 패키지 하나다. 냉각 방식은 의뢰 대상(4.2)에서 정한 값을 따른다.

| 구성 | 필드 | 규칙 |
|---|---|---|
| PCB 이미지 | 이미지 | 필수 |
| 소자 | 소자 이름, 값 | 필수. 소자를 여러 개 추가할 수 있다. 모든 소자에 같은 기준 하나를 쓴다: `온도 (°C)` 또는 `발열량 (W)`. 이름과 값은 필수 |

## 6. Case 구성

| 규칙 | 내용 |
|---|---|
| 구성 방식 | 형상과 활성 조건 패키지를 의뢰자가 직접 조합한다. 모든 조건을 자동 곱집합으로 만들지 않는다 |
| 최소 구성 | 형상마다 최소 1개의 Case가 있어야 하며, 필요한 조합만 추가한다 |
| 구성 단위 | Case는 형상과 해석유형에서 활성인 조건 패키지를 지정한다. 필터는 패키지 단위로 비교하며, 패키지 안의 물리적 필터나 측정점은 독립 Case 단위가 아니다. 측정·판정 기준은 의뢰 전체에 하나를 적용한다 |
| 선택 필수 | 활성 조건 패키지는 모두 Case에 지정해야 한다 |
| 미사용·없음 | 미사용이거나 `없음`인 조건은 Case에서 제외한다 |
| 중복 금지 | 형상과 모든 활성 조건 값이 같은 Case는 둘 수 없다 |
| 모든 값 사용 | 입력한 형상과 조건 패키지는 최소 한 Case에 쓰여야 한다 |
| Case 수 상한 | Case는 200개까지 |
| 원본 변경 | 형상이나 조건이 바뀌면 없어진 선택은 비우고, Case 구성을 다시 확인받는다 |

## 7. 결과 회신

- 결과는 배정된 담당자가 **요약 텍스트**로 등록한다.
- 결과 재작업 요청 후 다시 등록하면 회차별로 쌓이고, 마지막 결과가 현재 결과다.

## 8. 제출 조건

아래 조건을 모두 충족해야 제출(재제출 포함)할 수 있다. 충족하지 못하면 제출할 수 없다.

| 영역 | 조건 |
|---|---|
| 의뢰 대상 | 확정되어 있다 |
| 의뢰 내용 | 필수 항목을 모두 입력했다(4.3). 개발 프로젝트면 해당 사업부의 PMS 프로젝트를 골랐고 개발 등급과 NPI 단계를 입력했다(4.4) |
| 희망 완료일 | 의뢰 요청일보다 앞서지 않는다 |
| 해석 제품 | Base 제품이 1개 있다. 모든 제품의 도면번호는 해석에 사용하는 총조립 형상을 식별하고 형식에 맞으며 중복되지 않는다. 단품·부품·하위 조립품의 도면번호는 사용할 수 없다. 비교 제품마다 Base 대비 차이가 있다 |
| 해석조건 | 필수(●) 조건과, 사용하기로 한 선택(○) 조건의 필수 내부 필드를 모두 입력했다. 조건부 필수(예: 풍량을 입력하면 활용 목적)를 채웠다. 같은 내용의 조건 패키지가 중복되지 않는다 |
| 열교환기 | 사양 조합이 Catalog에 있다 |
| Case | 1행 이상이고, 모든 행에 형상이 있으며, 활성 열을 모두 선택했다. 중복이 없고, 입력한 모든 값이 쓰였다 |
| 자유 입력 | 200자를 넘지 않는다 |

## 10. 성과 지표

모두 상태 변화 이력(3.4-7)만으로 계산하며, 별도 입력 없이 자동으로 집계한다.

| 지표 | 정의 | 보는 것 |
|---|---|---|
| 1차 접수율 | 보완 요청 없이 접수된 의뢰 ÷ 접수된 의뢰 | 의뢰서가 처음부터 착수 가능했는지 (핵심 지표) |
| 의뢰당 보완 요청 횟수 | 보완 요청 수 ÷ 의뢰 수. 검토 단계와 해석 단계를 나누고 사유 코드(3.7)별로 본다 | 무엇이 자주 빠지는지 |
| 해석 단계 보완 요청률 | 해석 단계 보완 요청이 있었던 의뢰 ÷ 접수된 의뢰 | 검토 단계에서 놓친 정보 |
| 검토 소요 시간 | 제출(재제출 포함)부터 접수·보완 요청·반려까지 | 검토 지연 |
| 해석 소요 시간 | 접수부터 결과 등록까지 (보류와 해석 중 보완 대기 기간 제외) | 해석 처리 속도 |
| 희망 완료일 준수율 | 희망 완료일 안에 결과가 등록된 의뢰의 비율 | 일정 |
| 결과 재작업률 | 결과 재작업 요청이 있었던 의뢰의 비율 | 결과가 목적에 맞았는지 |
| 진행 중 변경률 | 진행 중 변경이 수락된 의뢰의 비율 | 착수 후 의뢰 내용이 흔들린 정도 |
| 반려율·취소율 | 반려 또는 취소된 의뢰의 비율. 반려는 사유 코드별로 본다 | 범위 밖 의뢰, 불필요한 의뢰 |

전화나 메일처럼 앱 밖에서 오간 문의는 이력에 남지 않으므로 지표에 잡히지 않는다.

개인별 순위나 평가용 점수는 성과 지표 범위에 포함하지 않는다.

## 부록 B. 용어집 [검토 필요]

**업무와 역할**

| 용어 | 정의 |
|---|---|
| 해석의뢰 | 의뢰서 작성부터 결과 확인까지의 업무 전체 |
| 의뢰자 | 의뢰서를 작성하고 결과를 확인하는 사람 (기구설계 엔지니어) |
| 해석관리자 | 의뢰를 검토해 접수하고 담당자를 배정하는 사람 |
| 해석담당자 | 배정받은 의뢰를 해석하고 결과를 등록하는 사람 |
| 접수 | 관리자가 의뢰를 해석하기로 받아들이는 것. 담당자 배정과 함께 이루어진다 |
| 배정 / 재배정 | 담당자를 정하는 것 / 이미 정한 담당자를 바꾸는 것 |
| 착수 | 배정된 담당자가 해석을 시작하는 것. 상태로는 해석 진행 중이다 |

**흐름**

| 용어 | 정의 |
|---|---|
| 상태 | 의뢰가 업무 흐름에서 있는 위치 (3.1의 10개) |
| 종료 상태 | 완료, 반려, 취소. 조회만 할 수 있다 |
| 보완 요청 (검토 단계) | 관리자가 검토 중에 의뢰서 보완을 요청하는 것 |
| 보완 요청 (해석 단계) | 담당자나 관리자가 해석 중에 정보 보완을 요청하는 것. 해석이 멈춘다 |
| 재제출 | 보완한 의뢰서를 다시 제출하는 것. 검토 단계 또는 담당자가 요청한 해석 단계 보완은 요청한 쪽의 처리로 돌아가며, 관리자가 요청한 해석 단계 보완은 해석 진행 중(관리자 확인 대기)이 된다 |
| 반려 | 관리자가 보완으로 해결할 수 없다고 보고 의뢰를 종료하는 것 |
| 취소 / 취소 요청 | 착수 전에 의뢰자가 바로 종료하는 것 / 착수 후에 관리자 승인을 받아 종료하는 것 |
| 보류 / 재개 | 일정 등의 사유로 해석을 잠시 멈추는 것 / 다시 시작하는 것 |
| 진행 중 변경 | 해석 중에 의뢰자가 의뢰 내용을 바꾸는 것. 담당자가 수락해야 반영된다 |
| 대기 요청 | 상대방의 응답을 기다리는 요청(진행 중 변경, 취소 요청). 한 의뢰에 하나만 둘 수 있다. 취소 요청이 대기 중이면 관리자가 답하기 전까지 다른 기능을 모두 막는다 |
| 취소 대기 | 취소 요청이 대기 중인 의뢰의 처지. 상태는 그대로이고 관리자의 승인·거절만 할 수 있다 |
| 결과 등록 | 담당자가 결과 요약을 올리는 것 |
| 결과 재작업 요청 | 의뢰자가 결과에 이의를 제기해 해석을 되돌리는 것 |
| 결과 확인 | 의뢰자가 결과를 받아들여 의뢰를 완료하는 것 |
| 의뢰서 버전 | 제출, 재제출, 진행 중 변경 수락 때마다 남기는 의뢰서 버전 |
| 이력 | 모든 상태 변화와 요청의 기록 (누가, 언제, 무엇을, 왜) |
| 사유 코드 | 보완 요청, 반려, 보류의 이유를 분류한 코드 (3.7) |
| 판단 지점 | 규칙으로 정할 수 없고 사람이 골라야 하는 곳 (3.8) |
